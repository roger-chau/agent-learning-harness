The real problem

A GPU issues instructions in order. If the next instruction needs a value that isn't ready, that warp stalls, and only other warps can fill the gap. Part 0's answer was "more warps". The compiler's answer is put independent work between a producer and its consumer, so even a single warp keeps issuing. With few warps (big register tiles, low occupancy), that ordering is most of the performance.

The smallest idea: dependences and latency

An instruction may move anywhere, as long as every dependence still points forward. Three kinds of register dependence, plus memory:

KindExampleMust wait
Read after write (true)ld %x … add %s, %s, %xThe producer's full latency
Write after read (anti)add %s, %a, 1 … mov %a, 0Just stay after it
Write after write (output)two writes to %aJust stay after it
Memorya store and a load or store to the same bufferStay in order (unless addresses provably differ)

Anti and output dependences only exist because names are reused. Renaming (or SSA form) removes them, at the cost of registers: the scheduling–allocation tension in one sentence.

Add one block: list scheduling

The standard algorithm for a basic block:

  1. Build the dependence graph, with latencies on the true-dependence edges.
  2. Give each instruction a priority: the longest latency path from it to the end of the block (its critical path).
  3. Simulate cycles. Each cycle, among instructions whose predecessors have all completed, issue the one with the highest priority.

It isn't optimal (that problem is NP-hard), but with critical-path priorities it's close for real code, and it's what production compilers build on. The effect: long-latency loads float to the top, their consumers sink, and independent work fills the gap.

Try it: with one warp, the loop as written spends almost all its time waiting on each load. Hoisting the loads lets one warp overlap them; adding warps lets the scheduler overlap warps instead. Both fill the same idle slots.

The whole machine: beyond one block

  • Loops are where time goes, but a loop body is short. Unrolling (next chapter) makes a bigger block to schedule; software pipelining overlaps iterations, issuing iteration k+1's loads during iteration k's math. You did this by hand as double buffering in Part 4.
  • On NVIDIA GPUs, ptxas also encodes the schedule into each instruction's control bits: how many cycles to stall before the next instruction, and which dependency barrier to wait on for variable-latency loads.
  • Scheduling for fewer stalls usually lengthens live ranges (more registers), which can cost occupancy. Real schedulers track register pressure as they go.

Reality

  • You can't reorder SASS by hand in normal toolchains; you influence it through source: unrolling, explicit prefetch into registers, splitting loads from uses.
  • Read the stall reasons per instruction in a profiler's source view: a stall pinned on the instruction right after a load means the schedule had nothing to put in between.
  • C5 asks you to do the compiler's job by hand in GWX: allocate, schedule, unroll and pipeline a GEMM inner loop.
