The real problem

Graphs (road networks, social networks, the web, circuits, the dependency graph of a build) are the least GPU-friendly data there is. Degrees vary from 1 to millions, neighbours are scattered across memory, and the amount of work changes from one step to the next. Yet breadth-first search, shortest paths and PageRank on billion-edge graphs are routinely run on GPUs. How?

The smallest idea: level-synchronous BFS

BFS from a source visits vertices in order of distance. In parallel, process one whole level at a time: all vertices at distance d are independent, so one kernel launch expands all of them, producing the vertices at distance d + 1. The kernel boundary is the barrier between levels (Chapter 3.4).

The simplest version is vertex-centric: every level, launch a thread for every vertex; a thread whose vertex is at the current level marks its unvisited neighbours. Correct, but each level touches all n vertices, so a graph with D levels costs $O(nD)$ work even though BFS needs only $O(n + e)$.

Add one block: frontiers

Keep the current level's vertices in a frontier queue, and launch threads only for them. Each thread expands its vertex's neighbours; a neighbour u is claimed by whichever thread first changes level[u] from −1, with atomicCAS, so every vertex enters the next frontier exactly once; the claimer appends it with atomicAdd on the queue's counter. Total work is now $O(n + e)$.

The appends are the contention point: every discovered vertex does one atomic on the same counter. The fix is Chapter 3.3's: privatise the queue per block in shared memory (append there, then reserve space in the global queue once per block with one atomic and copy the block's batch out). PMPP's privatised frontier does exactly that.

The whole machine: imbalance and direction

  • Degree imbalance. One thread per frontier vertex means a hub with a million neighbours keeps one thread busy while its warp waits (divergence, Chapter 1.4). Fixes: assign a warp or a block to high-degree vertices, or flatten the work to one thread per edge using a scan of the frontier's degrees plus a binary search (the co-rank idea again), as in load-balanced BFS libraries.
  • Direction optimisation. When the frontier is a large fraction of the graph, it's cheaper to go bottom-up: each unvisited vertex checks whether any neighbour is in the frontier, and stops at the first one found. Beamer's direction-optimising BFS switches between top-down and bottom-up per level, often cutting edge examinations several-fold on social graphs.
  • Memory. Every neighbour access is a gather; BFS is latency- and bandwidth-bound, with intensity near zero. Graph reordering, so that neighbours have nearby ids, is the main lever for cache hits.

Reality

  • GPU graph libraries (Gunrock, NVIDIA's cuGraph) are built on these primitives: frontiers, advance (expand edges), filter (compact the next frontier) and load-balanced edge assignment.
  • Results such as BFS levels are deterministic, but the order of vertices in the frontier queue isn't: atomics append in timing order. Algorithms that need a specific order sort or scan instead.
  • For graphs that don't fit in one GPU's memory, frontiers are exchanged between GPUs each level, and communication dominates: a multi-GPU and distributed topic, beyond this course.

Companion reading: PMPP 4th ed., Chapter 15 (Graph traversal); S. Beamer, K. Asanović, D. Patterson, "Direction-Optimizing Breadth-First Search", SC 2012.

Worked examples

Example 1: one BFS level, traced

Graph: edges 0–1, 0–2, 1–3, 2–3, 3–4. Source 0. Level 0 frontier: [0].

Level 0 launch (1 thread): neighbours 1 and 2: both CAS from −1 to 1 succeed; next frontier [1, 2] (order depends on timing).

Level 1 (2 threads): thread for 1 sees 0 (level 0, skip) and 3 (CAS succeeds, level 2, appended); thread for 2 sees 0 (skip) and 3 (CAS fails: already 2). Next frontier [3]. Level 2: 3's neighbours 1, 2 (visited) and 4 (level 3). Level 3: 4 has nothing new. Four launches, each vertex appended once, levels [0, 1, 1, 2, 3].

Example 2: the cost of a hub

Social graph: one vertex has 2 × 10⁶ followers. When it enters the frontier, a thread-per-vertex kernel gives it one thread: 2 × 10⁶ sequential iterations, about a millisecond on its own while everything else finishes in microseconds. Fix: classify frontier vertices by degree (a scan and compaction, Part 3): small ones a thread each, medium a warp, huge ones a whole block or several blocks over edge ranges. Gunrock and similar libraries implement exactly this "TWC" (thread–warp–CTA) mapping.
