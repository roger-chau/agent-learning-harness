Scenario · The metric that wouldn't match
After moving a monitoring pipeline to a new GPU, a dashboard metric doubled. On the old GPU it was steady, but its last digits changed from run to run. Fix it, for good.
The metric
For an array of sensor readings and a threshold, the count of readings above the threshold and their sum. Both are computed by runShipped in the starter, a fast kernel using ballots, shuffles and atomics.
The machines
The old GPU has 32-lane warps; the new one has 64-lane wavefronts (new GPUSim.Device({ warpSize: 64 })). Block scheduling order varies from run to run (the tests pass launchOpts with a shuffled block order: spread it into every launch).
Goal
runMetric(dev, x, n, th, launchOpts) returning { count, sum, stats }: the count exact; the sum within 10⁻⁶ relative of the exact sum and bit-for-bit identical on both GPUs and for every block order; and no slower (total cycles) than the shipped version on the old GPU.

Two bugs, one root

There are two separate problems here, one from Chapter 9.1 and one from 9.2, and a fix for one can easily break the other. A reduction that's reproducible on one GPU can still differ between a 32-lane and a 64-lane one if its order depends on the warp size. Find an order that depends on nothing but the data's indices.

"No slower" rules out the lazy fix of one thread summing everything. Chapter 3's reductions and Chapter 5's diagnosis are what get you there.

The write-up is the incident report: root causes, why each fix works, the measurements, and what test would have caught this before release.
