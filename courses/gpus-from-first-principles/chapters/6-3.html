The real problem

PTX has as many registers as the program wants; an SM has 65,536, shared by every resident thread. Each register a thread uses is one fewer warp the SM can hold (Chapter 2.6). The compiler has to map an unbounded number of values onto a small, fixed set of names, without changing what the program computes, and in doing so it decides your occupancy.

The smallest idea: a value only needs a register while it's live

A value is live from where it's computed to its last use. Two values that are never live at the same time can share a register. In straight-line code each value's life is an interval:

0  ld.global %a, X[%tid]     %a: [0, 2)
1  ld.global %b, Y[%tid]     %b: [1, 2)
2  add       %c, %a, %b      %c: [2, 3)    %a and %b die here: %c can reuse one of their registers
3  mul       %d, %c, %c      %d: [3, 4)
4  st.global OUT[%tid], %d

The number of registers needed is the largest number of intervals that overlap at any point: maximum live, also called register pressure. Here it's 2, though the program names 4 values.

Linear scan allocation walks intervals in order of their start, hands each one a free register, and returns a register to the free pool when its interval ends. For straight-line code it achieves exactly the maximum-live count.

Add one block: when registers run out

If the pressure exceeds what the compiler may use (255 per thread, or less if you ask for more occupancy), it must spill: store a value to local memory and reload it later. Local memory is per-thread DRAM, cached in L1/L2: a spill in a hot loop can turn a compute-bound kernel into a memory-bound one. Alternatives the compiler tries first:

  • Rematerialisation: recompute a cheap value (an address, a constant) instead of keeping it alive.
  • Rescheduling: move a use earlier or a definition later to shorten an interval.

And there's a knob in the other direction: __launch_bounds__(maxThreads, minBlocks) or -maxrregcount tell the compiler to use fewer registers to reach a target occupancy, accepting spills or worse code. Whether that's a good trade is Volkov's question from Part 2, and only measurement answers it.

The whole machine: loops and real allocators

  • With branches and loops, liveness becomes a dataflow problem: a value used in the next iteration is live around the back edge. Compilers solve it iteratively over the control-flow graph, usually on SSA form, where each value is defined exactly once (as in this chapter's exercise).
  • Production allocators use graph colouring (values are nodes, overlapping lives are edges, registers are colours) or refined linear scan. GPU allocators also respect register banks (the Volta paper's bank conflicts), vector-register alignment for 64- and 128-bit values, and per-warp allocation granularity (256 registers per warp on recent NVIDIA GPUs).
  • Occupancy from registers: warps per SM = min(hardware limit, ⌊65536 / (32 × registers per thread)⌋), before allocation granularity.

Reality

  • -Xptxas -v prints each kernel's registers and spill bytes. Check it whenever performance surprises you.
  • Register pressure is the main reason large unroll factors and big register tiles stop paying off (Part 4). C5 makes you live inside a register budget.
  • Kernels that use 255 registers aren't wrong: GEMMs often do, deliberately, at low occupancy.
