The real problem

You write y[i] = a * x[i] + y[i]; the GPU executes something quite different: address arithmetic, loads with particular widths and cache hints, a fused multiply-add, a store, all in registers the hardware actually has, in an order chosen to hide latency. Everything you measured in Parts 4 and 5 (instruction counts, FMA share, stalls) is a property of that code, not of your source. A GPU performance engineer reads it; a GPU compiler engineer writes the program that produces it.

The smallest idea: compilers lower in stages

A compiler translates through a series of languages, each closer to the machine. NVIDIA's toolchain for CUDA C++:

  1. Front end (Clang-based in modern toolchains): C++ to an LLVM-based IR called NVVM IR. Classic optimisations happen here: inlining, constant folding, loop unrolling, common subexpressions.
  2. NVVM back end: IR to PTX, a virtual instruction set. PTX has unlimited typed virtual registers (%r1, %f7, ...), explicit memory spaces (ld.global, ld.shared), and is stable across GPU generations.
  3. ptxas: PTX to SASS, the real machine code for one architecture. This is where registers are allocated to the physical register file, instructions are scheduled, and the hardware-specific encoding (including scheduling control bits) is produced.

Binaries usually carry SASS for the GPUs they were built for plus PTX, which the driver can compile just in time for newer GPUs. That's why PTX exists: a portable contract between the compiler and the hardware.

Add one block: GWX, our PTX

For this Part, the simulator has an assembly language modelled on PTX, GWX, and a cycle-level model of one SM that runs it. Like PTX, it has unlimited virtual registers (%anything), one value per lane, and explicit memory spaces:

  mov     %i, 0
loop:
  ld.global %x, X[%i]        // memory operand: BUFFER[%reg + imm]
  fma     %acc, %a, %x, %acc
  add     %i, %i, 1
  setp.lt %p, %i, $n         // $n: a launch parameter
  @%p bra loop               // predicated branch
  st.global Y[%tid], %acc

Run it with GWX.run(text, { warps, buffers, params }). You get the cycles, the instruction mix and the stall reasons. Latencies: 4 cycles for ALU and FMA, 24 for ld.shared, 400 for ld.global. One warp instruction issues per cycle, and an instruction waits until its source registers are ready (a scoreboard). GWX.assemble(text) parses a program into instructions, if you want to analyse one.

The first job of a back end is code generation: walk the expression tree and emit three-address instructions, one temporary per intermediate value. The second is instruction selection: noticing patterns the machine does in one instruction. A multiply whose only use is an add becomes one fma: half the instructions, and one rounding instead of two.

Tools: nvcc -ptx writes PTX, cuobjdump -sass and nvdisasm show SASS, -Xptxas -v prints registers and spills, and Nsight Compute's source view lines SASS up with your source and its stalls. Compiler Explorer (godbolt.org) shows PTX and SASS live as you type.

Reality

  • SASS isn't officially documented beyond an instruction list. Engineers learn it by reading compiler output and from microbenchmark studies like the Volta paper in Part 5.
  • Other GPU compilers follow the same shape: AMD's compiles through LLVM to its ISA, and ML compilers (Triton, XLA, MLIR-based stacks) add tile-level IRs above it (the Triton paper at the end of this Part).
  • FMA contraction changes rounding. nvcc fuses by default (--fmad=true), which is why GPU and CPU results can differ in the last bits.
