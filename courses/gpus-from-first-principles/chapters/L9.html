Why this lab

The earlier labs assume a clean machine: addition is addition, the clock is the clock, and the same input gives the same output. On real hardware none of these holds exactly. Training runs that won't reproduce, a benchmark that drifts by 15% after a minute, and a "regression" that is really a warmer room are all daily problems on GPU teams. Telling them apart from real bugs is a senior skill. This lab makes each one happen on your card.

What to do

Open labs/L9-reality/l9.cu.

  • A. Determinism. sum_atomic adds each block's partial sum into one float with atomicAdd. Run it 30 times and count the distinct answers. Then write sum_partials and sum_finish: partial sums in a fixed slot per block, added in a fixed order. You should get one answer in 30 runs, at the same speed. This is how PyTorch's deterministic mode works, and why it rules out some kernels.
  • B. Accuracy. chunk_sum_plain gives each thread 8,192 consecutive values near 0.1 to add up. Predict the relative error from the rounding of each addition (Chapter 9.1). Then write chunk_sum_kahan with compensated summation, and check in the SASS (make sass) that the compiler kept the compensation. With --use_fast_math it is allowed to remove it. Try it.
  • C. Clocks and power. Given. A compute kernel runs for 20 seconds while a host thread samples the SM clock, power and temperature through NVML every 200 ms. The results go to clocks.csv. Plot throughput, clock and temperature against time. Before running, read your card's base clock, boost clock and power limit (nvidia-smi -q -d CLOCK,POWER), and predict what happens.

Questions for the report

  • A: why do the atomic results differ, given that every block's partial is the same every run? Would your deterministic version give the same answer with a different grid size, or on a different GPU? What would it take to guarantee that?
  • B: your predicted error against the measured one, for both versions. Why is Kahan's cost nearly zero here? Think about what bounds this kernel.
  • C: did the clock drop, and when? Is the drop caused by power or by temperature? How should a benchmark be run so that A-against-B comparisons are fair (Chapter 5.1)?

Going further

  • Make A deterministic and independent of the grid size: give each block a fixed-size slice of the data, so the reduction tree depends only on n.
  • Sum the same data in FP16 and in BF16 (convert on the GPU) with FP32 accumulation, then with FP16 accumulation. Where does each break?
  • Repeat C with locked clocks (sudo nvidia-smi -lgc <MHz>, if your driver allows it) and with a lower power limit (-pl). Measure GFLOP/s per watt at each setting.
  • Run Lab 4's best GEMM after C's 20 seconds of warm-up, and again from cold. Report both numbers and say which one you'd publish.

Passing

The deterministic sum gives one answer in 30 runs, is accurate, runs at least 0.9× the atomic version's speed, and reaches at least 70% of peak bandwidth. Kahan summation reduces the error at least 10×. The sustained-load run completes, and the report includes the plot from clocks.csv with your explanation.
