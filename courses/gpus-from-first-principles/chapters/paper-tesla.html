The paper
E. Lindholm, J. Nickolls, S. Oberman, J. Montrym. "NVIDIA Tesla: A Unified Graphics and Computing Architecture." IEEE Micro, vol. 28, no. 2, 2008.
Find it on Google Scholar · It's often available as a PDF from university course pages. Read this chapter first, then the paper.

The problem

Before 2006, GPUs had separate hardware for different stages of the graphics pipeline: vertex processors to transform geometry and pixel (fragment) processors to shade it. Each was sized for an "average" game. But real frames are lopsided: a scene with huge triangles is pixel-heavy, a scene with dense geometry is vertex-heavy. One kind of unit sat idle while the other was the bottleneck.

At the same time, people were abusing those pixel processors for general computation, disguising arrays as textures and computations as shading. It worked, but it was painful: no arbitrary memory writes, no way for threads to cooperate, and graphics APIs in the way.

The key idea

Replace the specialised units with one unified array of programmable processors, and expose that array directly for general computing. Vertex, geometry and pixel work all run as threads on the same processors, so load balancing is automatic. A new programming model, CUDA, lets you launch those threads directly.

Everything in Part 0 and Part 1 of this course traces back to the design described here:

  • The SM. The paper's GeForce 8800 has 16 streaming multiprocessors, each with 8 scalar "streaming processor" (SP) cores, two special-function units, a multithreaded instruction unit and 16 KB of shared memory.
  • Massive multithreading. Each SM keeps up to 768 threads resident and schedules among them with zero overhead. That's Chapter 0.3's latency-hiding design.
  • SIMT and the warp. The paper names it: the SM creates, manages, schedules and executes threads in groups of 32 parallel threads called warps, and calls the model single-instruction, multiple-thread. Divergent threads are handled by the hardware, as in Chapter 1.4.
  • Cooperative thread arrays. Threads are grouped into blocks that share memory and synchronise with barriers: Chapter 0.4's blocks.

With 8 SPs per SM and 32 threads per warp, one warp instruction occupies the SPs for $32/8 = 4$ cycles. Narrow hardware runs a wide warp over several cycles, which also gives the pipeline time to fetch the next instruction.

Reading guide

  1. Introduction and the unified-architecture overview. Read closely. Note the motivation (load balancing, programmability) and the top-level block diagram: texture/processor clusters, SMs, the interconnect, memory partitions.
  2. The graphics pipeline sections. Skim. Understand that vertex, geometry and pixel work become threads on the same SMs. The details of rasterisation aren't needed for this course.
  3. The streaming multiprocessor and SIMT sections. Read very closely; this is the heart of it. Find the sentences that define warps and SIMT, and compare them with SIMD as described in the paper. Notice how divergence and reconvergence are described.
  4. The parallel computing architecture and CUDA sections. Read closely. Map their terms (thread blocks / cooperative thread arrays, grids, shared memory, barriers) onto Chapters 0.4 and 1.2.
  5. Performance and scalability. Skim the numbers, but note the argument: the same program runs on GPUs with more or fewer SMs, because blocks are independent. That's why the grid exists.

While reading, keep a list of every number you find (SMs, SPs, threads per SM, registers, shared memory, clocks, bandwidth). You'll need them for the exercise.

Reproduce it

Use the course's tools on the paper's machine. The GeForce 8800 GTX has 16 SMs × 8 SPs = 128 SPs at about 1.35 GHz, up to 768 resident threads per SM, 8,192 32-bit registers per SM, and about 86.4 GB/s of memory bandwidth.

  • Resident threads: $16 \times 768 = 12{,}288$.
  • Registers per thread at full occupancy: $8192 / 768 \approx 10.7$. That's tiny! Kernels needing more registers ran with fewer threads. This trade-off (Chapter 0.3) has been with GPUs from the start.
  • Can it saturate its memory? At 86.4 GB/s and, say, 400 ns of latency, Little's law needs $86.4 \times 400 \approx 34.6$ KB in flight, about 8,640 four-byte loads. 12,288 resident threads, each with one load in flight, cover that. The design is balanced, as Part 0 said it should be.

The exercise turns these calculations into functions and asks you to run them on other configurations.

What happened next

This architecture launched general-purpose GPU computing. CUDA's model of grids, blocks, threads, shared memory and barriers has survived almost unchanged for nearly two decades. AMD's HIP, OpenCL, SYCL and Apple's Metal compute all follow the same shape.

The hardware has grown far more than the model. Later generations added caches (Fermi), much larger register files and shared memory, independent thread scheduling (Volta), tensor cores (Volta onwards) and asynchronous copy engines (Ampere and Hopper). But the SM, the warp, and latency hiding through massive multithreading are still the core of every NVIDIA GPU. Reading this paper is reading the design document for the whole field.
