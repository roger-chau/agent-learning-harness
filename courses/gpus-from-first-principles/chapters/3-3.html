The real problem

Count how many pixels have each brightness value: a 256-bin histogram. Every thread looks at a pixel and wants to add 1 to some bin, and which bin depends on the data. Thousands of threads updating a few hundred counters at once is a recipe for lost updates. If two threads both read 41 and both write 42, one increment vanishes.

The smallest idea

An atomic operation performs read-modify-write as one indivisible step. atomicAdd(bins, v, 1) adds 1 to bins[v] and returns the old value, and no other thread's update can slip in between. In the simulator, as in CUDA, there's a family: atomicAdd, atomicSub, atomicMax, atomicMin, atomicExch, atomicCAS (compare-and-swap), atomicOr and atomicAnd. Each works on global buffers and on shared() arrays.

Atomics are correct, but correctness isn't the problem; contention is. Atomics to the same address must happen one after another. If all 32 lanes of a warp hit the same bin, that one instruction becomes 32 serialised updates. The simulator reports this as atomicSerialization: the sum over atomic warp instructions of the worst same-address count.

Add one block: privatise, then merge

Global atomics travel all the way to L2. The standard fix is privatisation: each block keeps its own histogram in shared memory, does its atomics there (fast and on-chip), and at the end adds each non-zero bin into the global histogram once. With 64 blocks and 256 bins, that's at most 16,384 global atomics instead of one per element.

function hist(x, bins, n) {
  const h = shared("h", 256, "u32");
  h[threadIdx.x] = 0;                                  // blocks of 256: one bin each
  __syncthreads();
  for (let i = blockIdx.x * blockDim.x + threadIdx.x; i < n; i += blockDim.x * gridDim.x)
    atomicAdd(h, x[i], 1);
  __syncthreads();
  if (h[threadIdx.x] > 0) atomicAdd(bins, threadIdx.x, h[threadIdx.x]);
}

But skew still hurts. If the image is mostly black, most lanes of every warp hit the same shared counter, and privatisation doesn't help at all. In the simulator, a privatised histogram of a constant image is about 3.5× slower than one of uniform noise. Real images are skewed: sky, shadows, blank documents.

Two families of fixes:

  • Combine before the atomic. A thread that sees the same value repeatedly can count locally and do one atomic with the run's count. Or the lanes of a warp can agree on a value with __shfl_sync and __ballot_sync, so one lane adds the number of matching lanes (warp aggregation).
  • Spread the counters. Keep several copies of each hot counter (for example one per warp), so fewer lanes collide on each, and sum the copies at the end.

Each costs something on uniform data. Milestone B3 asks you to make one histogram that's good on every distribution.

The whole machine

Atomics are also how blocks coordinate:

  • Allocation. const slot = atomicAdd(count, 0, k) reserves k output slots, as in "append to a queue". It's fast, but the order of the output depends on timing.
  • Work distribution. A global counter handing out tile ids (B2's dynamic tile ids).
  • Arbitrary read-modify-write via compare-and-swap: read the old value, compute a new one, and atomicCAS it in only if nobody changed it meanwhile, retrying otherwise. That's how floating-point atomicMax, or atomics on custom types, are built.

Floats deserve a note: atomicAdd on floats makes the summation order depend on timing, so results can vary in the last bits between runs (Chapter 3.1's reproducibility point again).

Reality

  • Hardware help. Modern GPUs perform global atomics at L2 with high throughput, and newer generations add warp-level matching (__match_any_sync), which groups lanes with equal values in one instruction to make warp aggregation cheap.
  • Libraries. CUB's DeviceHistogram uses privatised shared-memory histograms. Histogramming is also the first step of radix sort (Chapter 3.5, milestone B4).
  • Contention is everywhere. A single global counter that every thread bumps is a classic accidental bottleneck in "simple" GPU code. Profilers report it as atomic throughput saturation.

Worked examples

Example 1: costing three histogram designs

Data. $2^{24}$ bytes, 60% zeros, 256 bins, the GW-1 with 128 blocks of 256 threads.

  • Global atomics: one per element, $2^{24}$ in all, each warp's atomic serialised about 19–20 ways on bin 0 (Problem 4). All of them go to L2.
  • Shared-memory privatisation: the same $2^{24}$ atomics, but in shared memory (tens of cycles instead of hundreds), still serialised ~19×; then $128 \times 256 = 32{,}768$ global atomics for the merge, negligible.
  • Privatisation + warp aggregation: per warp atomic, the ~19 lanes holding 0 become one update, and the ~13 others mostly hit distinct bins: about 14 shared-memory updates per warp instead of a 19-deep chain on one counter, and they no longer queue behind each other. Add run counting per thread (zeros arrive in long runs in real images) and most of those updates disappear too.

Lesson: the cost model is serialisation × atomics × latency of the memory they hit. Privatisation cuts the latency, aggregation cuts the serialisation, and run counting cuts the count. B3's "good on every distribution" needs at least two of them.

Example 2: building atomicMax for floats from CAS

function atomicMaxFloat(buf, i, v) {
  let old = buf[i];
  while (old < v) {
    const seen = atomicCAS(buf, i, old, v);   // write v only if buf[i] is still old
    if (seen === old) break;                  // we won
    old = seen;                               // someone changed it: retry against the new value
  }
}

Why it's correct: CAS writes only if nobody changed the value since we read it; otherwise it returns the current value and we re-check. Values only increase, so the loop terminates.

Why it's usually fast: the early exit. Once the stored maximum exceeds most candidates, most threads never attempt a CAS. Under heavy contention with increasing values it degrades towards the quadratic worst case (Problem 7).

The trick most libraries use instead: for non-negative floats, the IEEE bit pattern orders like an unsigned integer, so atomicMax on the bits as int is a correct float max in one native atomic. Negative floats need the inverted ordering (Chapter 3.5's transform).

Example 3: an append queue with warp aggregation

Task. Threads that find a match append its index to a global output list.

Per-thread atomics: each matching thread does slot = atomicAdd(count, 1). With 5% matches over $10^7$ threads: 500,000 serialised atomics on one address.

Aggregated: m = ballot(match); the lowest set lane does base = atomicAdd(count, popc(m)); the base is shuffled to all lanes; each matching lane writes at base + popc(m & lanesBelow). Atomics: one per warp that has any match: with 5% per lane, $1 - 0.95^{32} = 81\%$ of warps, about 253,000. Not a huge saving at 5%; at 50% matches it's 5,000,000 versus 312,500: 16×.

Order: output order depends on which warp's atomic arrives first: fine for a work queue, wrong if the consumer needs input order (then use a scan, Chapter 3.5).
