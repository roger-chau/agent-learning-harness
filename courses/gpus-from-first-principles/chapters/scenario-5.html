Scenario · The regression
The nightly benchmark says the smoothing filter got slower after PR #4711. The PR's author says the benchmark is noisy and nothing is wrong. Settle it, and fix it.
Context
A 5-tap smoothing filter (y[i] = 0.1·x[i−2] + 0.2·x[i−1] + 0.4·x[i] + 0.2·x[i+1] + 0.1·x[i+2], for 2 ≤ i < n−2) runs on every frame of a signal-processing pipeline. The PR description: "process 4 outputs per thread to cut launch overhead". Both versions are in the starter.
Part 1
The team needs a trustworthy A/B tool. Write compare(dev, runA, runB, reps): runA() and runB() each launch one version once on dev. Return { ratio, verdict }, where ratio is B's typical synchronised time over A's (within ±3%) and verdict is "slower", "faster" or "same" (B vs A; "same" means within 3%). The tests run it on pairs with known true times, through the simulator's noisy clock: warm-up effects, jitter and occasional 1.5–3× outliers.
Part 2
Find the root cause in the PR with the profiler metrics, and write runFixed(x, y, n) (returning an array of launch stats): correct, and no slower than the pre-PR version (within 5%) at n = 218. Stretch: ≤ 7,500 cycles. The pre-PR kernel wasn't at the roof either.

What a good answer looks like

A verdict with a number and an uncertainty, not "seems slower". A root cause stated as a mechanism and backed by metrics, before and after. A fix, with its own measurement. And, because the PR author had a point, an honest look at whether launch overhead was ever the problem for this kernel at this size.

Interleave A and B, warm up, use robust statistics. Then think about what else could make a nightly benchmark lie, such as other jobs on the machine or clocks, and how you'd guard against it.
