The real problem

The last chapter gave the rule: a warp's access costs one unit per distinct 32-byte sector it touches. Now turn it around. You decide which thread touches which address, through your indexing and your data layout. Get it right and every warp load costs 4 sectors; get it wrong and the same work costs 32. Same algorithm, same answers, 8× the memory traffic.

The smallest idea

Make consecutive lanes of a warp touch consecutive addresses. That's called a coalesced access. Since lanes are consecutive values of threadIdx.x, the rule becomes:

The ruleThe index that varies fastest in memory should be driven by threadIdx.x.

For a row-major 2D array (a[y * width + x]), x varies fastest in memory, so x should come from threadIdx.x. Swap them, so that each thread walks a column or threadIdx.x picks the row, and consecutive lanes are width × 4 bytes apart. Each lane then lands in its own sector.

Add one block: layouts

Indexing is half the story; the other half is how the data is laid out. Consider particles, each with a position and velocity:

// Array of structures (AoS): x, y, vx, vy, x, y, vx, vy, ...
p[4*i + 0] = x,  p[4*i + 1] = y,  p[4*i + 2] = vx,  p[4*i + 3] = vy

// Structure of arrays (SoA): four separate arrays
x[i], y[i], vx[i], vy[i]

In AoS, when a warp reads every particle's x, lane $\ell$ reads byte $16\ell$: a stride of 16 bytes. The warp spans 512 bytes, 16 sectors for 128 useful bytes, which is 25% efficiency. Reading y, vx and vy hits the same sectors again. A real cache would save some of that, but the per-instruction cost is still 4× the ideal. In SoA, all 32 lanes read 32 consecutive x values, 4 sectors, 100%.

AoS is natural for CPUs, where one thread processes one object and wants all its fields in one cache line. SoA is natural for GPUs, where 32 threads process 32 objects and each instruction wants one field of many objects. Converting AoS to SoA is one of the most common GPU porting steps.

Set the element size to 4 bytes and the stride to 4: that's the AoS particle read. Stride 1 is SoA.

Also check alignment and pitch. If each row of an image starts at an arbitrary byte offset (say, width 1000 floats = 4000 bytes, not a multiple of 128), every row's warps straddle an extra sector. Real code often pads rows to a multiple of 128 bytes. CUDA's cudaMallocPitch does exactly this and returns the padded row length, the pitch.

Reality

  • Some patterns can't be fixed with indexing alone. A transpose must read rows and write columns; a 3-byte-per-pixel RGB image puts each pixel's channels 3 bytes apart. The fix for both is cooperation: threads load a tile coalesced into fast on-chip shared memory, then each reads whatever it needs from there. That's 2.5, and it's how milestone A2 coalesces your imaging pipeline.
  • Vector loads help too. Real GPUs can load 8 or 16 bytes per thread in one instruction (float2, float4). That's fewer instructions for the same sectors; Part 4 uses it.
  • Measure it. Profilers report sectors per request and "uncoalesced global accesses". The simulator's coalescing field is the same idea.

Worked examples

Example 1: diagnosing an access from the code

Code. out[i] = in[i * C + c]: each thread i reads channel c of pixel i from an image with C = 4 interleaved float channels.

Step 1, find the lane stride. Consecutive lanes have consecutive i, so addresses are $4C = 16$ bytes apart.

Step 2, count. 32 lanes × 16 bytes = 512 bytes spanned, 16 sectors for 128 useful bytes: 25%.

Step 3, fix. Either change the layout to planar (four arrays: 100%), or have each thread read the whole pixel as one float4 (lane stride 16 bytes, each lane uses all 16: 100%) and process all channels. The second needs no layout change, which matters when the data format isn't yours to choose.

Example 2: a 2-D stencil and block shape

Setup. A 3 × 3 stencil over a 4096-wide float image. Each output pixel reads 3 rows × 3 columns.

32 × 8 blocks. Each warp is one row of 32 outputs. For each of the 3 input rows it reads 34 consecutive floats (32 plus a neighbour each side): 136 bytes, 5 or 6 sectors when not aligned. Mostly coalesced.

8 × 32 blocks. Each warp is 4 rows of 8 outputs. For each input row it reads 4 runs of 10 floats (40 bytes, 2–3 sectors each): about 10 sectors per input row, roughly double.

Reuse. Within a 32 × 8 block, each input row is read by up to 3 warps; the L1 cache or a shared-memory tile catches the repeats. The block's input footprint is $34 \times 10$ floats for $32 \times 8$ outputs: 1.33 reads per output, against 9 in the source. Wide blocks are better on both counts.

Example 3: converting AoS to SoA, and when not to

Setup. A particle system with 7 floats per particle (position, velocity, mass). Kernel A integrates positions (reads all 7, writes 6). Kernel B computes the total mass (reads 1).

AoS (28-byte structs). Kernel A: for each field, 32 lanes span 896 bytes: 28 sectors per instruction, 13 instructions: 364 sector requests per warp, but only 28 distinct sectors per warp overall, so with a good L1 DRAM traffic is near minimal. Kernel B: 28 sectors for 128 useful bytes: 14% efficiency, and caching can't help since the other fields are never used. Kernel B is 7× slower than necessary.

SoA. Every instruction in both kernels: 4 sectors, 100%.

Hybrid (AoSoA). Groups of 32 particles stored as 7 arrays of 32: each field access by a warp is contiguous (100%), and all of one particle's data stays within 896 bytes, which is friendly to CPU code and to copying a group at once. Libraries for particle and molecular dynamics use exactly this layout.
