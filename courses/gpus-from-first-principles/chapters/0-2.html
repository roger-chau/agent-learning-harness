The real problem

Arithmetic is cheap. A modern CPU core can start several floating-point operations every cycle, and with vector units dozens. At 4 GHz a cycle is a quarter of a nanosecond.

Fetching a number from main memory, by contrast, takes on the order of 80–100 ns. At 4 GHz that's 320–400 cycles: hundreds of cycles of doing nothing for one load. Over decades, processor speed grew much faster than DRAM latency improved. This widening gap is called the memory wall, and it's why "how fast is the ALU" is almost never the right question.

The smallest idea

What a load costs depends on where the data is. Close to the core, memory is small, fast and expensive. Far away, it's huge, slow and cheap. So machines build a hierarchy and try to keep the data you're about to use near the top.

Caches work because programs have locality. Temporal locality: data you used recently, you'll probably use again. Spatial locality: if you used address $a$, you'll probably use $a+4$ soon. That's why caches fetch whole lines (64 bytes on most CPUs), not single words.

Add one block: average memory access time

With a hierarchy, there's no single "latency". There's an expected latency, which depends on how often you hit each level. For one level of cache:

$$\text{AMAT} = \text{hit time} + \text{miss rate} \times \text{miss penalty}$$

The miss penalty is itself the AMAT of the next level down, so the formula nests. With an L1, an L2 and DRAM:

$$\text{AMAT} = t_{L1} + (1-h_{1})\big(t_{L2} + (1-h_{2})\, t_{\text{DRAM}}\big)$$

Here $h_2$ is the L2 hit rate among the accesses that missed L1.

A worked example

Take $t_{L1} = 4$, $h_1 = 0.90$, $t_{L2} = 14$, $h_2 = 0.60$, $t_{\text{DRAM}} = 300$ cycles.

$$\text{AMAT} = 4 + 0.10\,(14 + 0.40 \times 300) = 4 + 0.10 \times 134 = 17.4\ \text{cycles}$$

Notice where the time goes. The 4-cycle L1 hit is paid every time. The DRAM term is paid only $0.1 \times 0.4 = 4\%$ of the time, yet it contributes $0.04 \times 300 = 12$ of the 17.4 cycles. Rare misses dominate. Moving the L1 hit rate from 90% to 95% cuts AMAT to 10.7 cycles, almost a 40% improvement from five percentage points.

Set the work per load to 4 cycles and drag the L1 hit rate down to 70%. The core now spends most of each iteration waiting. Then drag it to 100% and watch the waiting almost vanish. That's the whole game a CPU plays: reduce the average latency of one thread.

The whole machine

CPUs attack the memory wall with three big mechanisms, all aimed at making one thread wait less:

  1. Caches reduce how often you go far away, by exploiting locality.
  2. Out-of-order execution keeps working on later, independent instructions while a load is outstanding, so some of the latency overlaps with useful work. It can only look ahead as far as its reorder buffer, a few hundred instructions, and 300 cycles of latency easily outruns that.
  3. Prefetching guesses which lines you'll need next and requests them early, turning a latency problem into a bandwidth problem. It works beautifully on regular access patterns and not at all on random ones.

All three spend a large share of a CPU core's transistors and power on predicting and hiding latency for a single stream of instructions. Keep that in mind; the GPU makes the opposite bet.

Reality

Caches only help when data is reused, or at least arrives in predictable order. Consider streaming once through a 1 GB array, as in vector addition. No cache can hold it, and every byte is used once. Every line comes from DRAM. The best you can do is keep enough requests in flight to run at full bandwidth, which is exactly the Little's law problem from the last chapter.

So there are two different regimes:

  • Latency-bound: you're waiting on individual accesses (pointer chasing, dependent loads). Lower latency helps; more bandwidth doesn't.
  • Bandwidth-bound: you have plenty of independent accesses (streaming, most array code). More concurrency helps until you hit the bandwidth ceiling.

Throughput workloads like graphics, simulation and machine learning live mostly in the second regime. For them, spending transistors on lowering one thread's latency is the wrong trade. The next chapter shows the alternative: don't make the wait shorter, fill it with other work.
