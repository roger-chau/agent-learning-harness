Real hardware

Everything here ran on a simulator built to be honest about first-order effects. The next step is real GPUs: rewrite the capstone in CUDA or Triton, profile it with Nsight Compute, and find what the simulator didn't model (instruction-level stalls, the real cache hierarchy, clocks). A cloud instance or a Jetson-class board is enough. The gaps you find are worth writing up: that's how engineers show they understand a machine.

Worked examples: interview answers

Example 1: "Walk me through a kernel you optimised."

Structure (2–3 minutes): the problem and its size; the first measurement and the bound you computed (roofline); each change, the evidence that motivated it, and the number it produced; where you stopped and why.

Model answer, in the shape of Lab 4 (the numbers here are illustrative; use your own measurements): "SGEMM at 2048³ on an RTX 2060 Super. cuBLAS reaches about 6.5 TFLOP/s. The naive kernel did 4 instructions per FMA, so it was capped at 25% of peak and measured 0.9 TFLOP/s. Shared-memory tiling cut global loads 32× but left 3 instructions per FMA: 1.6 TFLOP/s. Register tiling with 8 × 8 outputs per thread and float4 shared loads raised the FMA share to 94%; ptxas showed 128 registers, no spills, 25% occupancy, which was fine because each warp had 64 independent FMAs per step: 4.1 TFLOP/s, 63% of cuBLAS. The profile then showed the global-load latency at the tile boundaries; I'd add double buffering next." Every claim has a number and a reason.

Example 2: "Why is my kernel slow?" (debugging a profile live)

Given: DRAM 20%, L2 85%, issue 30%, many sectors per request on stores.

Answer: "L2 is the busiest unit, and stores touch many sectors per request: uncoalesced writes that L2 merges before DRAM, so DRAM looks idle. It's L2-bound on write traffic. I'd check the store indexing; if it's a transpose-like pattern, stage through shared memory so both sides coalesce. I'd expect L2 traffic to drop ~8× and the kernel to become DRAM- or latency-bound." The structure: name the unit, cite the counter, give the mechanism, propose a fix, predict its effect.

Example 3: a compiler-track question

Q: "When can you not reorder a load above a store?"

Answer: "When they may access the same address: a true memory dependence. The compiler needs proof they don't alias: different allocations, __restrict__, or index analysis showing the subscripts differ, for example via the GCD test on affine subscripts. Without proof it must keep the order. On a GPU there's a second layer: across threads, even independent addresses need fences if another thread observes the order, but that's the memory model, not the single-thread dependence." Interviewers look for the distinction between program-order dependences and cross-thread ordering.
