The real problem

So far, every launch has handed you exact numbers: the simulator's stats are what a perfect profiler would report. Real measurement is messier. You time a kernel and get 4 µs; you change one line and get 155 µs; you run it again and get 8.4 µs. None of these numbers is the kernel's speed. Most benchmark mistakes in GPU work aren't subtle, but they are common, and they make claims like "my change made it 30% faster" wrong more often than right.

From this Part on, the simulator also has a wall clock that behaves like a real one: gpu.now() (host time in µs) and gpu.synchronize().

The smallest idea: launches are asynchronous

A kernel launch returns as soon as the work is queued, not when it's done. The host pays a few microseconds to issue the launch, and the GPU runs it later, in order. So this measures only the launch overhead:

const t0 = gpu.now();
gpu.launch(k, cfg, x, y, n);
const t1 = gpu.now();          // ~4 µs, whatever the kernel does

To time the kernel, wait for it: gpu.synchronize() before reading the clock. (In CUDA: cudaDeviceSynchronize(), or better, CUDA events recorded on the stream. Copying results back to the host also synchronises, which hides this bug in a lot of code.)

Add one block: warm-up and noise

Even a synchronised measurement isn't one number:

  • The first run is special. The first launch of a kernel loads its code onto the device (here: +150 µs), and the GPU's clock ramps up over the first few launches. Always run a few warm-up iterations and throw them away.
  • Runs vary. Every run jitters a little, and now and then one is interrupted (another process, a clock change, an interrupt) and takes 2–3× longer.

So repeat, and summarise with a statistic that ignores outliers: the median (typical run) or the minimum (best case, closest to the hardware's capability). The mean is dragged by outliers and the first run; never report a mean without saying what was excluded.

To compare two versions, run them interleaved (A, B, A, B, ...) rather than all of A then all of B, so slow drifts affect both equally, and look at how far apart the distributions are, not just two numbers.

The whole machine: latency vs throughput

There are two honest answers to "how long does this kernel take?":

  • Latency: launch, synchronise, repeat. Each measurement includes the launch overhead. That's the right number when the kernel runs once, alone, with the host waiting.
  • Throughput: launch it many times back to back, synchronise once, divide. The launch overhead overlaps with the previous kernel's execution. That's the right number for a kernel inside a pipeline of many launches.

For a big kernel they agree. For a tiny one they don't: if the kernel runs for 1 µs and a launch costs 4 µs, back-to-back throughput is one kernel per 4 µs, and the GPU is idle 75% of the time. That kernel is launch-bound, and no amount of kernel tuning helps. Fusing kernels, batching work or CUDA Graphs (which pre-record a chain of launches) do.

Reality

  • Real profilers (Nsight Compute) lock clocks to a base frequency by default so numbers are reproducible. That makes them lower than what users see under boost clocks. Know which one you're quoting.
  • Caches carry over between runs on real hardware: a second run may find its data in L2. Benchmarks either flush the L2 between runs or say they don't. (The simulator starts each launch with a cold L2.)
  • Report: the statistic, the number of runs, warm-up, problem size, and the hardware. A number without these can't be checked.
