Paper project · A paged KV cache
Virtual memory for attention: block tables, reference counts and copy-on-write, then the GPU gather that reads through them.

Build, part 1: the cache

A pool of numBlocks physical blocks, each holding blockSize tokens (one number per token stands in for its K and V vectors). Functions on a cache object c:

FunctionDoes
createCache(numBlocks, blockSize)An empty cache
addSeq(c, id)A new, empty sequence
append(c, id, value)Add one token. Allocates a block when the last one is full, and copies on write if the last block is shared. Returns false and changes nothing if no block is free
fork(c, src, dst)A new sequence sharing all of src's blocks (reference counts up, no copying)
read(c, id)The sequence's values in order, through its block table
freeSeq(c, id)Drop the sequence; blocks whose count reaches 0 return to the pool
usedBlocks(c)Physical blocks currently in use

Build, part 2: the gather on the GPU

runGather(pool, table, out, nTokens, blockSize): a simulator kernel that copies a sequence's tokens into out in logical order, where token t lives at pool[table[⌊t / blockSize⌋] · blockSize + t mod blockSize]. It must be correct and keep coalescing ≥ 0.9: the lookup indirection shouldn't cost bandwidth if consecutive lanes read consecutive tokens. Return the stats.

Then think

The write-up asks you to compare your cache's capacity with contiguous allocation on a realistic mix of lengths, and to choose a block size: what do small and large blocks each cost?
