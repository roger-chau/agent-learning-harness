The real problem

Everything in this course used NVIDIA's model, because that's where most GPU software lives. But AMD GPUs run the largest supercomputers and serve large models, Intel and Apple ship GPUs in huge numbers, and phones and embedded devices have their own. Code that assumes one vendor's details breaks, sometimes loudly, often silently, on another. Compiler engineers in particular work across targets: half the job is the parts that differ.

The smallest idea: same model, different constants

The SIMT model you've learned is shared by all modern GPUs. The constants differ, and code that hard-codes them is the main source of bugs.

HIP is deliberately close to CUDA (and hipify translates mechanically), so the code compiles. The bug is a literal 32 hiding in the logic: threadIdx.x & 31 as the lane id, 32-bit masks, warps-per-block computed as blockDim.x / 32.

Add one block: writing portable kernels

  • Use the built-in warpSize (a compile-time constant in HIP for a given target), never 32.
  • Treat ballot results as wide enough for the wavefront, and count bits with an intrinsic (__popc, __popcll) of the matching width.
  • Prefer block-level primitives (from CUB, hipCUB, or your own Part 3 code parameterised by warp size) over hand-rolled warp tricks.
  • Don't rely on implicit warp-synchronous execution: Volta already broke that assumption on NVIDIA (independent thread scheduling), which is why the _sync intrinsics exist.

The simulator can build a device with 64-lane wavefronts: new GPUSim.Device({ warpSize: 64 }). Its __ballot_sync then returns a 64-bit BigInt, and __popc counts either.

The whole machine: performance portability

Correct isn't the same as fast. Tile sizes, occupancy, memory-system behaviour and matrix-instruction shapes differ, so a kernel tuned for one GPU is rarely best on another. The approaches, roughly from least to most portable:

  1. Separate hand-tuned kernels per vendor (most libraries' fastest paths);
  2. Templates with per-target parameters plus autotuning (Part 6's tile compiler);
  3. Tile-level languages and ML compilers (Triton, MLIR-based stacks) with backends per vendor;
  4. Portable standards (SYCL, OpenCL, Vulkan compute, Kokkos), trading peak speed for one codebase.

That spread, one model with many targets, is why GPU compiler engineering is a growing field.

Reality

  • Embedded and mobile GPUs (Mali, Adreno, PowerVR, the integrated GPUs in Jetson-class SoCs) often expose compute through OpenCL or Vulkan rather than CUDA, with smaller caches, shared DRAM and tight power budgets (next chapter).
  • Test on every target in CI. Portability bugs are usually silent wrong answers, not crashes.
  • Read each vendor's ISA documentation once (AMD publishes full ISA manuals); the differences teach you what the common model abstracts away.

Worked examples

Example 1: porting a block reduction to 64-wide wavefronts

CUDA original: warp-shuffle reduce with offsets 16..1; lane 0 of each warp writes s[threadIdx.x / 32]; warp 0 reduces blockDim.x / 32 partials.

Every 32 that must change: starting offset → warpSize / 2; threadIdx.x / 32 → / warpSize; the partial count → blockDim.x / warpSize; the full mask 0xffffffff → a 64-bit mask (HIP's shuffles take a 64-bit mask, or none); the lane test threadIdx.x & 31 → % warpSize. With 256 threads, CDNA has 4 partials, not 8, so the final step reads 4 values.

Test: block sizes 64, 128, 256 and 1,024, and n not a multiple of 64. Four sizes catch every one of the hidden constants above.

Example 2: same algorithm, different tuning

A tiled GEMM tuned on an NVIDIA GPU uses 128 × 128 tiles, 256 threads, 48 KB shared memory per block.

On a CDNA GPU with 64 KB of LDS per CU and 64-wide wavefronts: 256 threads is 4 wavefronts; the matrix instructions (MFMA) have different shapes (e.g. 32 × 32 × 8) and fragment layouts, so the warp tile must change; LDS bank structure differs, so the padding or swizzle changes too. The algorithm (block tile, warp tile, register tile, pipelined K loop) transfers unchanged; nearly every constant needs re-tuning. That's why portable libraries are templates with per-target parameter tables, and why compilers like Triton separate the algorithm from the layout.

Example 3: a portability checklist for code review

  1. grep for 32, 31, 0xffffffff, __popc (32-bit), >> 5.
  2. Find implicit warp-synchronous code: shared-memory exchanges between lanes without __syncwarp.
  3. Find hard-coded resource limits: shared memory sizes, registers per thread assumptions, occupancy targets.
  4. Find vendor intrinsics (mma, cp.async, __ldg) and check each has a fallback or a per-target path.
  5. Check the test matrix covers both widths, odd sizes and the largest block sizes.

Readings

  • Required: AMD, HIP Programming Guide: "Porting CUDA code to HIP" and the warp-size notes.
  • Required: AMD, "AMD Instinct MI300 / CDNA 3 Instruction Set Architecture" overview chapters (wavefronts, LDS, MFMA).
  • Optional: Khronos, SYCL 2020 Specification, section on sub-groups.
