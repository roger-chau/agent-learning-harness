The real problem

The previous chapters optimised what's already inside a basic block. The biggest wins usually come from changing the loops themselves: how much work one iteration does, which order the iterations run in, and which loops (or kernels) run together. These are the transformations behind most of Part 4's speedups, viewed now as something a compiler can do mechanically, and must prove safe.

The smallest idea: unrolling

Replicate the loop body u times and run 1/u of the iterations. Three separate benefits:

  1. The loop overhead (increment, compare, branch) is paid once per u bodies.
  2. The scheduler gets a block u times bigger to fill latencies with.
  3. With separate accumulators, the iterations' math becomes independent: instruction-level parallelism, Volkov's ILP from Part 2.

The third needs care: s0 + s1 + s2 + s3 sums in a different order than one running total, and floating-point addition isn't associative. Compilers won't reassociate a float reduction unless told it's allowed (fast-math flags), so for floats this one is often yours to do by hand. Costs of unrolling: more registers (each accumulator and loaded value), bigger code, and remainder handling when the trip count isn't a multiple of u. In CUDA: #pragma unroll.

TransformWhat it doesWhere you've seen it
Loop-invariant code motionMoves computations that don't change across iterations out of the loopBase addresses computed once

Each is legal only if it preserves every dependence. Compilers prove that with dependence analysis on array subscripts; when they can't (pointers that might alias, unknown strides), they don't transform. __restrict__ exists to tell them two pointers don't alias.

The whole machine: fusion

Three elementwise kernels in a row (scale, ReLU, square) each read and write the whole array. Fused into one, the intermediate values stay in registers: a third of the DRAM traffic for a memory-bound chain, and two fewer launches. That's why ML compilers spend so much effort on fusion. XLA, TorchInductor and Triton-based stacks fuse elementwise operations into each other and into the epilogue of a GEMM, and FlashAttention (Part 8) is a fusion that changes the algorithm to make it possible.

Fusion isn't free: a fused kernel holds more live values (registers), may need a different parallel decomposition than its parts, and can lose the reuse one of them had. When fusion makes things slower, register pressure is the first suspect.

Reality

  • nvcc unrolls small constant-trip loops automatically; check the SASS to see what it did.
  • Polyhedral compilers model loop nests mathematically and search transformations; tile-level languages like Triton (next) let the programmer state the tiling and leave the rest to the compiler.
  • The PP-triton project builds a tiny compiler that generates fused, tiled kernels and autotunes their parameters.

Worked examples

Example 1: deriving the tiled GEMM as a sequence of transformations

Start: for i, for j, for k: C[i][j] += A[i][k]·B[k][j].

  1. Tile i and j by 64 (strip-mine and interchange): for ii, for jj, for i in tile, for j in tile, for k. Legal: the only dependence is the reduction over k, carried by the innermost loop.
  2. Interchange k outward within the tile: for ii, jj, for k, for i, for j. Legal because + is treated as associative for the reduction (the compiler needs permission for floats; libraries take it).
  3. Tile k by 16 and stage A[ii][kk] and B[kk][jj] in shared memory: the loads hoist out of the i, j loops.
  4. Map ii, jj to blocks and the inner i, j to threads, then unroll each thread's sub-tile into registers.

Every step of Part 4 is one of the classic transformations. A compiler like Triton or a polyhedral tool performs them automatically once the dependences are known; the hard part is choosing tile sizes, which is a cost-model (or search) problem.

Example 2: fusing softmax into a matmul epilogue

Unfused: GEMM writes S (n × n), softmax reads S and writes P. Traffic: write S, read S, write P: $3 \times 4n^2$ bytes beyond the GEMM's inputs.

Fused epilogue: each GEMM block, holding a tile of S in registers, computes the tile's row maxima and exponentials before writing. But softmax needs a full row's max and sum, and a block holds only part of a row: the fusion is only legal across the whole row. Either one block owns entire rows (possible when n is small), or the kernel keeps running max and sum per row and rescales: the online softmax, which turns this into FlashAttention (Part 8). Fusion legality comes down to which data a block can see.

Example 3: proving an interchange illegal, then fixing it

Loop: for i in 1..n: for j in 0..n−2: a[i][j] = a[i−1][j+1] + a[i][j]. Distance vector (1, −1).

Interchange gives (−1, 1): illegal, as Problem 8 showed. Skew j by i: $j' = j + i$. Now the dependence from $(i-1, j+1)$ to $(i, j)$ has $j'$ distance $(j + i) - (j + 1 + i - 1) = 0$: vector (1, 0). Interchanging gives (0, 1): legal. After skewing, all iterations on the same wavefront (an anti-diagonal of the original loop) are independent and can run in parallel. This is the classic wavefront parallelisation of stencils and dynamic programming, and the reason GPU dynamic-programming kernels (sequence alignment, for instance) sweep anti-diagonals.
