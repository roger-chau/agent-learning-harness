The real problem

Two workhorse operations need everything in this Part at once. Compaction: from a million particles, keep the ones still alive, in their original order. Sorting: put a million keys in order. Both move every element to a position that depends on all the elements before it. With reduce, scan, histogram and atomics in hand, you can now build both.

The scan gives each kept element its output position, so the result is stable: kept elements keep their order. (The atomicAdd "reserve a slot" version from Chapter 3.3 is faster but unordered.) At GPU scale, the scan is your device-wide scan, or the three-phase version: per-block counts, a scan of the counts, then a per-block scatter using block-local scans.

Add one block: radix sort is compaction, many times

LSD radix sort sorts integer keys by looking at $d$ bits at a time, starting from the least significant digit. Each pass is a stable counting sort on one digit:

  1. histogram the digit: how many keys have digit 0, digit 1, … ($2^d$ bins);
  2. exclusive scan the counts: where each digit's keys start in the output;
  3. stable scatter: each key goes to its digit's start plus the number of earlier keys with the same digit.

Why does starting from the least significant digit work? After the pass on digit $k$, keys are sorted by digits $0 \ldots k$. The pass on digit $k+1$ is stable, so keys with equal digit $k+1$ keep their order from the previous passes. Stability is the whole trick: an unstable scatter breaks the sort.

On a GPU, each pass splits the keys into tiles (one per block). The histogram becomes a table of counts, counts[digit][tile]. Scanning that table in digit-major order gives every (digit, tile) pair its global starting offset. Within a tile, a key's rank among same-digit keys can come from warp ballots: __ballot_sync(…, digit === d) marks which lanes share digit d, and counting the set bits below your lane gives your rank inside the warp.

Choosing $d$. 32-bit keys need $32/d$ passes, and each pass reads and writes every key. Larger digits mean fewer passes but bigger histograms (256 bins for $d = 8$, 16 for $d = 4$) and more work per pass. Fast GPU sorts typically use $d = 8$: four passes.

The whole machine

Count the memory traffic of a straightforward radix sort pass: read keys for the histogram, read keys again for the scatter, write keys. That's about $3n$ per pass, times 4 passes for 32-bit keys with $d = 8$. A sort is memory-bound, so this traffic is the runtime. This Part's paper chapter, Onesweep, shows how to cut it:

  • compute all four digit histograms in one upfront pass over the keys;
  • then make each digit pass a single sweep that reads and writes the keys once, using decoupled look-back (B2's technique) to get each tile's global offsets without a separate scan phase.

Milestone B4 asks you to build a correct radix sort from your own primitives. How far you push it toward Onesweep is up to you; B5 measures it.

Reality

  • Libraries: CUB's DeviceRadixSort (which adopted Onesweep), Thrust's sort, and torch.sort all use radix sort for primitive key types.
  • Floats and signed integers radix-sort correctly after a bit-twiddling transform that makes their bit patterns order like unsigned integers (flip the sign bit for positives, all bits for negatives).
  • Key-value sorts move a payload along with each key, which doubles the traffic. Sorting indices or 32-bit handles instead of fat records is a classic optimisation.
  • Where sorting shows up in GPU work: binning particles into cells, ordering rays or work items by type to remove divergence (Chapter 1.4's fix), building BVHs, mixture-of-experts token routing, and database operators.
