The paper
A. Adinets, D. Merrill. "Onesweep: A Faster Least Significant Digit Radix Sort for GPUs." arXiv preprint, 2022.
Find it on Google Scholar / arXiv · Builds directly on the decoupled look-back paper you've just read.

The problem

Radix sort is memory-bound, so its speed is decided by how many times each key crosses DRAM. A classic GPU LSD radix sort runs each digit pass as reduce-then-scan: read the keys to build histograms, scan the histograms, then read the keys again to scatter them, and write them. That's about $3n$ key movements per pass. For 32-bit keys with 8-bit digits, it's $12n$ across the sort, even though a pass fundamentally only needs to read and write each key once.

The key idea

Make each digit pass a single sweep, and move histogramming out of the passes. Two parts:

  1. All histograms up front. One kernel reads the keys once and builds the global histogram for every digit position at the same time. Those global histograms give each digit's starting offset in each pass.
  2. One sweep per pass, with decoupled look-back. Each tile counts its keys per digit and needs, for each digit, how many keys of that digit come from earlier tiles. That's a scan across tiles, done exactly like B2: publish per-digit tile counts with an "aggregate" flag, look back through predecessors' aggregates until reaching inclusive prefixes, publish the prefix, then scatter. The keys are read once and written once per pass.

So each pass moves about $2n$ keys instead of $3n$, and the sort as a whole approaches the cost of reading and writing the data once per digit. The authors also discuss the practical details: tile sizes, keeping a tile's keys in shared memory between ranking and scattering to make writes more coalesced, and handling the look-back efficiently across 256 digits at once.

Reading guide

  1. Background: LSD radix sort and the reduce-then-scan design it improves on. Compare the data-movement count with Chapter 3.5.
  2. The upfront histogram. Read closely: why can all digit histograms be computed in one pass, and what does that save?
  3. The single-sweep pass with look-back. Read very closely. Map the per-digit status words to B2's X/A/P states, now with 256 digits per tile.
  4. Implementation and tuning. Skim for the choices that matter: tile size, digit width, and how scatters are made more coalesced.
  5. Results. Note what the comparison is against (the previous CUB sort) and on what hardware.

Reproduce it

The exercise asks you to model key traffic for both designs, and to write a small host-side reference LSD radix sort using counting-sort passes. Having a sequential reference you trust is a habit worth having before optimising a GPU version. Then run your B4 sort and compare its measured dramBytes with the two models.

What happened next

Onesweep became the radix sort in CUB, so it's what Thrust and many frameworks run when they sort primitive keys on NVIDIA GPUs. More broadly, it shows a pattern you'll see again in this course: remove passes over data by computing what you'll need up front, and replace multi-kernel phases with single-pass cooperation. Kernel fusion (Part 7) and FlashAttention (Part 8) are the same idea in other clothes.
