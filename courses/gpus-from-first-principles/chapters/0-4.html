The real problem

We now have three requirements for a machine that runs throughput workloads well:

  1. From Little's law (0.1): to use hundreds of GB/s across hundreds of nanoseconds of latency, it must keep hundreds of thousands of bytes in flight.
  2. From the memory wall (0.2): caches and clever single-thread tricks don't save streaming workloads, so the transistors are better spent elsewhere.
  3. From latency hiding (0.3): that concurrency comes from very many threads, each with its registers on-chip, switched for free.

Let's design that machine. The result will be a GPU.

The smallest idea

Spend the chip on many simple execution lanes and huge register files, not on making one thread fast. Strip out most of what makes a CPU core big: large out-of-order windows, aggressive branch prediction, deep speculation. Put the area into arithmetic units and the storage to hold thousands of threads.

One more saving makes this practical. Throughput workloads usually run the same code on different data: every pixel, every element, every row. So group threads into bundles of 32 that share a single instruction fetch and decode, each lane working on its own data. NVIDIA calls such a bundle a warp. One instruction issued to a warp does 32 lanes' worth of work, so the control logic is paid once per 32 threads. Part 1 is entirely about what that means for your code.

Add one block: the hierarchy of the machine

Reading the picture from the inside out:

  • Thread: your code, running on one lane with its own registers.
  • Warp: 32 threads that issue together, one instruction at a time.
  • Warp scheduler: each cycle it picks one ready warp from its pool and issues its next instruction. Recent NVIDIA SMs have four of them. This is the latency-hiding loop from the last chapter, built into hardware.
  • SM: holds up to dozens of warps resident at once (64 on many recent NVIDIA GPUs, i.e. 2,048 threads), along with their registers and a fast on-chip scratchpad called shared memory.
  • GPU: many SMs sharing an L2 cache and the off-chip DRAM, which CUDA calls global memory.

Count the concurrency. A GPU with 100 SMs and 2,048 resident threads per SM holds about 200,000 threads. Each one with a 4-byte load in flight gives 800 KB in flight. That's the same order of magnitude Little's law demanded. The design follows from the constraints.

The whole machine: grids, blocks and waves

How does work get onto this machine? You write a function called a kernel from the point of view of one thread, and launch it over a grid of blocks:

  • A block is a group of threads (up to 1,024) that always runs on a single SM. Its threads can cooperate through shared memory.
  • The grid is all the blocks of one launch. They're independent and can run in any order.
  • Each thread finds its piece of the work from built-in indices: blockIdx (which block am I in), blockDim (how big is a block), and threadIdx (which thread am I within the block).

The hardware hands blocks to SMs until every SM is full, then hands out more as blocks finish. With more blocks than fit at once, the grid runs in waves.

Try 40 blocks on 8 SMs with 2 resident per SM: 16 run at once, so three waves, and the last wave only fills half the machine. That idle half in the last wave is called the tail effect; Part 5 measures it. Now try 48 blocks: same number of waves, no waste.

Reality: your first kernel

Here's the classic first kernel, vector addition, written for this course's simulator. Every thread computes one element:

function add(a, b, c, n) {
  const i = blockIdx.x * blockDim.x + threadIdx.x;   // my global index
  if (i < n) c[i] = a[i] + b[i];                     // guard: the last block may overhang
}

The guard matters. Blocks have a fixed size, so for $n = 1000$ and blocks of 256 you launch $\lceil 1000/256 \rceil = 4$ blocks, 1,024 threads. The last 24 must do nothing, or they'd read and write past the end of the arrays.

Run it below. Besides the result, the simulator prints what the hardware did: warps launched, memory transactions, how efficiently each warp's accesses were combined (coalescing, Part 2), and whether any warp's threads took different paths at a branch (divergence, Part 1). Try changing the block size, or n, and see which numbers move.

Real GPUs are far bigger than the GW-1: a data-center part might have over a hundred SMs and several TB/s of bandwidth. The principles are the same, and the simulator's small numbers keep the arithmetic easy to follow. One caveat to carry forward: the simulator runs the threads of a warp one after another and lines up their memory accesses afterwards. For code without divergence that matches lockstep hardware exactly; Part 1 shows where the difference matters.

Worked examples

Example 1: mapping threads to a 2-D problem

Setup. Brighten a $W \times H = 1000 \times 600$ image stored row-major (img[y * W + x]), one thread per pixel, 32 × 8 blocks.

  1. Grid: $\lceil 1000/32 \rceil \times \lceil 600/8 \rceil = 32 \times 75$ blocks.
  2. Coordinates: x = blockIdx.x * 32 + threadIdx.x, y = blockIdx.y * 8 + threadIdx.y.
  3. Guard: if (x < W && y < H). Here $32 \times 32 = 1024 > 1000$, so the last column of blocks has 24 idle threads per row. 600 is a multiple of 8, so rows have none.
  4. Which threads form a warp? Within a block, threads are numbered $x$-fastest: threadIdx.x + 32 * threadIdx.y. So each warp is one row of the block: 32 consecutive pixels of one image row, which are consecutive addresses. That's the layout Part 2 calls coalesced.

The mistake to avoid. Swapping the roles, x = ...threadIdx.y and y = ...threadIdx.x, gives the same results but makes each warp walk down a column, 1000 floats apart per lane. It's correct and 8–16× slower. Correctness tests won't catch it; the simulator's coalescing number will.

Example 2: residency, waves and run time

Setup. GW-1 (16 SMs, 2,048 threads and 16 blocks per SM). A kernel has 4,000 blocks of 256 threads, using 40 registers per thread; each block takes about $T$ to run once resident, the same for all blocks.

  1. Thread limit: $2048/256 = 8$ blocks. Block limit: 16. Registers: $65536/(256 \times 40) = 6.4 \to 6$ blocks. Resident: 6 blocks per SM.
  2. Slots: $16 \times 6 = 96$. Waves: $\lceil 4000/96 \rceil = 42$ (41.7).
  3. Run time ≈ $42\,T$; the last wave runs $4000 - 41 \times 96 = 64$ blocks on 96 slots.

What if registers drop to 32? Then 8 blocks per SM fit, 128 slots, $\lceil 4000/128 \rceil = 32$ waves. If a block's own time $T$ stays the same, the kernel takes 24% less time (32 waves instead of 42). (It may not: with more blocks sharing an SM, each runs slower if the SM is saturated. Waves count residency, not throughput: use them for tail effects, and the utilisation model from 0.3 for throughput.)

Example 3: grid-stride loops and sizing a grid to the machine

Problem. Process $n = 50{,}000{,}000$ elements. One thread per element needs 195,313 blocks of 256: fine for the hardware, but per-thread setup is repeated 50 million times and the last wave is ragged.

Alternative. Launch exactly as many blocks as fit at once (GW-1 at 8 blocks/SM: 128 blocks, 32,768 threads) and loop with a stride of 32,768. Each thread does $\lceil n / 32768 \rceil = 1526$ iterations (some 1525). There's one wave, no tail, and setup happens 32,768 times.

Trade-off. Fixed grids depend on the machine's size; launching "enough" blocks is portable. A common compromise: size the grid to a small multiple of the SM count, e.g. 2–4 × SMs × resident blocks.

Example 4: from datasheet to design check, on a real card

Your RTX 2060 Super. 34 SMs; on Turing each SM holds at most 1,024 threads (32 warps); 448 GB/s. Assume about 450 ns loaded latency.

Requirement. $448 \times 450 = 201{,}600$ bytes in flight.

Supply. $34 \times 32$ warps $\times$ 128 bytes per warp load $= 139{,}264$ bytes with one load per warp. That's 69% of the requirement.

Conclusion. On this card a naive copy kernel can't reach peak even at full occupancy. Two loads per warp in flight (two elements per thread, or one 8-byte load per thread) clears the requirement. When you measure this on the card (the real-GPU track), you should see the naive copy plateau well below 448 GB/s, and the 2- or 4-element version get much closer. Predicting that before running it is the skill.
