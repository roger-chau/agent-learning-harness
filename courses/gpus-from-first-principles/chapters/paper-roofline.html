The paper
S. Williams, A. Waterman, D. Patterson. "Roofline: An Insightful Visual Performance Model for Multicore Architectures." Communications of the ACM, vol. 52, no. 4, 2009.
Find it on Google Scholar · Short and very readable: one sitting.

The problem

By the late 2000s, processors had become wildly diverse: multicore x86 chips, many-threaded designs, and the Cell processor with its explicitly managed local stores. Programmers and architects needed a way to answer "how fast should this kernel run on that machine, and what's stopping it?" without a cycle-accurate simulator. Detailed models were too complex to be insightful, and simple metrics like peak FLOP/s were misleading for memory-bound code.

The key idea

You've already used it in Chapter 2.1: bound performance by two numbers, peak compute and peak memory bandwidth, and place each kernel by its operational intensity. The paper's contributions beyond the basic roof are worth knowing precisely:

  • Operational intensity uses DRAM traffic, measured after the caches have filtered accesses, not the loads and stores in the source. That's why the same algorithm can sit at different places on the roofline depending on how well it uses the caches.
  • Ceilings. Below the roof, the paper draws additional horizontal lines (compute ceilings), each showing performance if some optimisation is missing: for example without instruction-level parallelism, or without SIMD. It also draws extra slanted lines (bandwidth ceilings), for example without proper memory affinity on multi-socket machines, or without software prefetching. A kernel sitting under a ceiling tells you which optimisation would lift it.
  • The ridge point as a machine property. A machine whose ridge sits far to the right is hard to use well: only high-intensity kernels reach its peak.

Reading guide

  1. The opening and the model's derivation. Read closely. Note the exact definition of operational intensity and why they chose DRAM traffic.
  2. The figures that build the roofline step by step. Read closely. Rebuild one figure on paper with the GW-1's numbers (1,536 GFLOP/s, 512 GB/s).
  3. Adding ceilings. Read closely. For each ceiling, write down which optimisation it represents, and decide whether it's a compute or a bandwidth ceiling.
  4. The case studies on four multicore platforms with several scientific kernels. Skim for the method: how they measured intensity, and how the plots explained the results. Note which kernels sat where, and why.
  5. The fallacies section. Read closely. These are the most common misreadings of the model, and they still come up in performance reviews today.

Reproduce it

The simulator gives you everything the paper needed: DRAM bytes (dramBytes) and time (timeUs). Add the FLOP count, which you know from the algorithm, and you can place any kernel on the GW-1's roofline:

$$I = \frac{\text{FLOPs}}{\text{dramBytes}} \qquad \text{achieved GFLOP/s} = \frac{\text{FLOPs}}{\text{time}} \qquad \text{efficiency} = \frac{\text{achieved}}{\min(1536,\ 512 \cdot I)}$$

In the exercise you'll write that measurement as a function and use it on two kernels: a memory-bound one and one that reuses data. You'll also add a ceiling, "without fused multiply-add", which halves peak compute, and see which kernels it affects.

What happened next

The roofline became the standard first-order performance model in HPC and then in GPU and ML work. Profilers draw it directly: NVIDIA Nsight Compute plots a kernel on a hierarchical roofline with separate roofs for L1, L2 and DRAM, and for FP32, FP64 and tensor-core math, and Intel Advisor does the same on CPUs. In ML, "is this layer compute-bound or memory-bound?" is answered with exactly this model. That reasoning underlies FlashAttention (Part 8) and much of LLM inference optimisation, where decoding is typically memory-bound.
