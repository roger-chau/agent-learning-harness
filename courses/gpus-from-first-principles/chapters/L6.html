Why this lab

A GPU compiler engineer's daily work is reading what nvcc produced and asking why. A performance engineer needs the same skill to tell "my algorithm is slow" apart from "the compiler did something I didn't expect". This lab gives you three effects you can see in the SASS and measure on the clock: instruction-level parallelism standing in for occupancy, an array that silently ends up in local memory, and fusion.

What to do

Open labs/L6-compiler/l6.cu. Before writing anything, run make regs and make sass-poly_naive and look at the code you were given.

  • A. ILP versus occupancy. poly_naive evaluates a degree-32 polynomial 16 times per element with Horner's rule. That is 512 dependent FMAs. The shared-memory request leaves room for only one 128-thread block per SM: 4 warps, one per scheduler. Predict the fraction of FP32 peak from the FMA latency and issue rate (Chapter 6.4). Then write poly_ilp, which evaluates 4 elements per thread with their FMAs interleaved. The result must be bit-identical, since each element sees the same FMAs in the same order.
  • B. Local memory. sort8_local is an insertion sort for a run-time length k. Its array is indexed with run-time values, so it lives in local memory: make regs shows a 32-byte stack frame, and make sass-sort8_local counts the LDL and STL instructions. Write sort8_regs for exactly 8 values, using only compile-time indices: a sorting network built from cmp_swap. The program checks with cudaFuncGetAttributes that it uses no local memory.
  • C. Fusion. Three elementwise kernels write two temporaries that nobody needs. Write fused, one pass with float4 accesses, and predict the speedup from the bytes moved. Do the same operations in the same order, so the result is bit-identical. This is what a fusion pass in a compiler like XLA, TorchInductor or Triton does.

Read the machine code

  • make sass-poly_ilp: count the FFMAs. Does the count match 4 × 32 × the inner loop's unrolling? Find where the four chains interleave.
  • make ptx, then find sort8_local's .local array and its ld.local and st.local. Is local memory "slow memory"? It's cached in L1, so the honest answer depends on the hit rate: check it with make ncu.
  • In sort8_regs's SASS, find the FMNMX instructions. How many should there be for your network?
  • Compare your fused kernel's SASS with the three originals: what did fusion remove besides memory traffic?

Going further

  • Sweep ILP from 1 to 8 in A. Where does it stop helping, and how do the registers per thread change? Then remove the shared-memory request: does ILP still matter at full occupancy? This is Volkov's paper (Part 2) measured on your own card.
  • Replace odd-even transposition (28 comparators) with Batcher's network (19 comparators). Is it faster, and if not, why not?
  • Add __launch_bounds__(256, 4) to Lab 4's register-tiled GEMM, which forces fewer than 64 registers per thread. Measure the spills and the time.
  • Write C's fused kernel in Triton (Python, on your card) and compare its PTX with yours.

Passing

All results bit-exact, and sort8_regs uses no local memory. poly_ilp reaches at least 70% of FP32 peak and is at least 1.6× faster than the naive version. sort8_regs reaches at least 60% of peak bandwidth and is at least 1.5× faster than the local-memory sort. The fused kernel reaches at least 70% of peak bandwidth and is at least 2.5× faster than three passes. The report quotes SASS for each claim.
