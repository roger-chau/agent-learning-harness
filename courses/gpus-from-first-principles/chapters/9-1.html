The real problem

Run the same training job twice on the same GPU and get different losses. Move it to a new GPU and a test fails in the fifth decimal place. Neither is necessarily a bug, and either can be. Floating-point addition isn't associative, parallel hardware adds things in different orders, and a performance engineer has to know when a difference is rounding and when it's wrong.

The smallest idea: order changes the answer

(a + b) + c and a + (b + c) round differently. In FP32, $10^8 + 1 - 10^8$ gives 0 one way and 1 the other. Any parallel sum (a tree in shared memory, warp shuffles, atomics from many blocks) picks an order, and:

  • a fixed tree gives the same bits every run (on the same hardware and launch shape);
  • atomics add in whatever order blocks happen to arrive, so the bits change from run to run;
  • changing the launch shape, the GPU, or the library version changes the tree, and the bits.

Measure differences in ULPs (units in the last place: how many representable numbers lie between two results), or as relative error against a higher-precision reference, never with === or a fixed absolute tolerance.

Add one block: making it reproducible, and more accurate

  • Deterministic reductions: write per-block partial results to an array, then reduce the array in a fixed order (a second kernel or a last-block pass). A little more work and traffic, bitwise identical for a given launch shape.
  • Compensated (Kahan) summation: carry the rounding error of each addition in a second variable and feed it back. Error stops growing with n.
  • Wider accumulators: FP32 accumulation for FP16 data (Part 4), FP64 for sensitive FP32 sums.

Frameworks expose "deterministic" modes that choose such algorithms, at some cost in speed. Know what you're buying: same bits run to run, not the exact answer.

The whole machine: where numerics bite on GPUs

  • FMA contraction (Chapter 6.1) and fast-math flags (approximate exp, flush denormals to zero) change results between compilers and settings.
  • Low precision (FP16, BF16, FP8) and their scaling (Part 7) move the error budget by orders of magnitude; tensor cores may accumulate internally in ways the documentation only loosely specifies.
  • Split-K, Stream-K and other decompositions (Part 5) change the summation order with the problem shape: the same GEMM can give different bits at different sizes.

Reality

  • Bitwise reproducibility across different GPUs is generally not promised by vendor libraries. Within one GPU and configuration, many operations can be made deterministic.
  • When a test fails after an optimisation, first compare against a high-precision reference: did the error grow, or just move?
  • Nondeterministic atomics are fine for many uses (histograms of integers are exact). The problem is floating-point atomics.

Worked examples

Example 1: is this difference a bug?

Report: "My GPU softmax differs from NumPy's by up to 3 × 10⁻⁷ in rows of 4,096."

Check the scale: outputs are around 1/4096 ≈ 2.4 × 10⁻⁴ for a flat row, so 3 × 10⁻⁷ absolute is about 10⁻³ relative. FP32 unit roundoff is 6 × 10⁻⁸; a sum of 4,096 exponentials has error up to ~4096 u in the worst case (2.4 × 10⁻⁴ relative) and typically ~√4096 u (4 × 10⁻⁶). 10⁻³ relative is far above both: this is a bug, or NumPy is computing in FP64 while the GPU uses an approximate exponential (__expf, a few ULPs) and an approximate reciprocal. Check those before trusting either side.

The method: convert the difference to relative error or ULPs, compare it with what the operation's error analysis allows, and only then decide.

Example 2: catastrophic cancellation in a GPU reduction

Task: compute $\sum x_i - \sum y_i$ where both sums are ≈ 10⁶ and their difference is ≈ 1, in FP32.

Each sum has a relative error of maybe 10⁻⁷ (good tree reduction): an absolute error of ≈ 0.1. The difference inherits both: ≈ 0.14 absolute on a result of 1, a 14% error, even though each sum was accurate to 7 digits.

Fix: reduce the differences $x_i - y_i$ directly (if they pair up), or accumulate in FP64, or use compensated summation. The general rule: subtracting nearly equal computed quantities amplifies their relative errors by the ratio of their size to the result's.

Example 3: making a reduction reproducible across grid sizes

Problem: a sum's last bits change when the grid size changes, because each block's share (and so the tree) depends on the grid.

Design: fix a chunk size C independent of the grid (say 4,096 elements). Chunk k always covers elements [kC, (k+1)C) and is reduced with a fixed tree. Blocks take chunks in any order, and write the chunk sums to partial[k]. A final pass sums partials with a fixed tree. The tree now depends only on n and C, so any grid size gives identical bits. The cost is a slightly larger partials array. This is the approach of "reproducible" BLAS reductions, and what Lab 9's "going further" asks for.
