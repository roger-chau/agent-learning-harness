The real problem

A warp issues one load instruction, and each of its 32 threads wants 4 bytes. From your code's point of view, 128 bytes were requested. But memory doesn't hand out 4-byte pieces. What it actually moves, and therefore what the load costs, depends on where those 32 addresses are. The same instruction can cost 4 units of memory traffic or 32.

The smallest idea

Memory moves data in fixed-size chunks, and you pay for every chunk you touch. On modern NVIDIA GPUs the unit is a 32-byte sector, aligned to a multiple of 32. Four sectors make a 128-byte cache line. When a warp's load reaches the memory system, the hardware works out which sectors the 32 addresses fall in, and fetches each one once.

$$\text{efficiency} = \frac{\text{bytes requested}}{32 \times \text{sectors touched}}$$

Why chunks at all? A DRAM chip is a grid of rows. Reading anything means activating a whole row into a row buffer, which is slow, then streaming bursts out of it, which is fast. Interfaces are built to deliver bursts of consecutive bytes at a time. Asking for 4 isolated bytes still costs a whole burst. Caches and memory controllers are organised around these fixed-size pieces, and the 32-byte sector is how that physical reality shows up for a GPU programmer.

Add one block: counting sectors

Take 4-byte floats and a warp where lane $\ell$ reads element $o + \ell \cdot s$ (offset $o$, stride $s$):

Element size matters too: 32 lanes reading consecutive 8-byte doubles span 256 bytes, 8 sectors, still 100%. Reading consecutive single bytes spans 32 bytes, 1 sector, also 100%, but only 32 bytes per instruction, which needs far more instructions for the same data.

Set the stride to 2, then 4, then 8, and watch the sectors multiply. Then go back to stride 1 and shift the offset by one: the warp now straddles one extra sector. Alignment matters, though less than stride.

The whole machine

Sectors are the currency of the memory system. In the GW-1 simulator:

  • transactions counts sectors requested from L2, summed over all warp memory instructions;
  • bytesMoved is transactions × 32, the traffic between the SMs and L2;
  • dramBytes is what actually came from or went to DRAM: sectors that missed in L2 (2.4);
  • coalescing is bytes requested ÷ bytes moved, the efficiency above averaged over the whole kernel.

A kernel with 12.5% efficiency moves 8× the data it needs. If it's memory-bound, and most simple kernels are, it runs up to 8× slower than it should. That's why the next chapter, on arranging accesses so warps touch as few sectors as possible, is the most important optimisation in GPU programming.

Reality

  • Older GPUs were stricter. Early CUDA GPUs required specific alignment and ordering to "coalesce" at all. Modern ones simply count distinct sectors, which is the model used here, so any permutation of addresses within the same sectors is equally fast.
  • Writes too. Stores are counted the same way. Partial-sector writes can be extra costly in real hardware because the memory may have to read, merge and write back.
  • Caches soften, but don't remove, the cost. A real GPU's L1 cache may catch the second warp that touches a sector the first warp already fetched. Counting sectors per instruction is still how profilers report it: NVIDIA's Nsight Compute shows "sectors per request", and 4 is ideal for 4-byte loads.
  • DRAM pages and channels. Below the sectors, addresses are spread across memory channels and banks. Pathological strides can pile every request onto one channel ("partition camping"). Modern GPUs hash addresses to make that rare.

Worked examples

Example 1: counting sectors for an arbitrary pattern

Pattern. 8-byte doubles, lane ℓ reads element $2\ell + (\ell \bmod 2)$ (a zigzag).

Method. Write down byte addresses, divide by 32, count distinct results. Element indices for lanes 0–7: 0, 3, 4, 7, 8, 11, 12, 15. Byte addresses: 0, 24, 32, 56, 64, 88, 96, 120. Sectors: 0, 0, 1, 1, 2, 2, 3, 3. So every pair of lanes shares a sector, and the 32 lanes span elements 0–63 (bytes 0–511): 16 sectors.

Efficiency: $32 \times 8 / (16 \times 32) = 50\%$. The pattern reads every other double, so half of every sector is wasted, regardless of the zigzag. Shortcut: for any pattern, efficiency = useful bytes / (32 × distinct sectors). Draw the sectors; don't trust intuition about "almost contiguous".

Example 2: what a cache line costs in DRAM terms

Setup. GDDR memory delivers data in bursts: say a 32-bit channel with burst length 16 gives $4 \times 16 = 64$ bytes per burst, or 32 bytes for a 16-bit channel at BL16. An activation (opening a row) costs on the order of 30–50 ns; a burst from an open row a few ns.

Consequence 1: the minimum useful granularity is one burst, which is why sectors are 32 bytes and not 4.

Consequence 2: a stream of consecutive sectors from one row amortises the activation over many bursts. Random sectors pay an activation each. That's why "random 32-byte reads" run at a fraction of the bandwidth of sequential reads even when each read is a full sector: the GPU's spec-sheet bandwidth assumes row-buffer locality. Lab 0's pointer chase shows the latency side of this.

Example 3: from sectors to a time prediction

Kernel. 16 M particles in AoS (16 bytes: x, y, vx, vy); the kernel updates x += vx and y += vy, one thread per particle, field by field.

Per warp: 4 loads (x, y, vx, vy) and 2 stores (x, y), each touching the same 16 sectors (512 bytes): 6 × 16 = 96 sector requests. Useful: 6 × 128 = 768 bytes. Efficiency 25%.

DRAM. If L1/L2 catch the repeats, DRAM sees 512 bytes in and 512 out per warp: 1 KB per 32 particles, the minimum. If they don't (a huge working set and poor ordering), it can see up to 3,072 bytes.

Prediction. At 512 GB/s: best case $16\text{M}/32 \times 1\,\text{KB} = 512$ MB, 1.0 ms; worst case 3.0 ms. SoA needs the same 1 KB per warp at 100% efficiency with no reliance on caching: reliably 1.0 ms. Predicting both bounds before measuring is what lets you interpret the measurement.
