The real problem

Chapter 0.3 said latency hiding needs many resident warps, and that resident warps are limited by on-chip resources. Now you've met all the resources a block uses: its threads, its registers and its shared memory. Each SM has a fixed budget of every one of them. Use a bit too much of one and a whole block no longer fits, so the SM runs fewer warps and hides less latency. Which resource runs out first, and by how much?

The smallest idea

Occupancy is the fraction of an SM's warp slots that are actually filled:

$$\text{occupancy} = \frac{\text{resident warps per SM}}{\text{maximum warps per SM}}$$

Blocks are placed whole, so resident warps = blocks per SM × warps per block, and blocks per SM is the smallest of four limits. On the GW-1:

LimitGW-1 budget per SMBlocks that fit
warp slots64 warps⌊64 / warps per block⌋
block slots16 blocks16
registers65,536 (allocated per warp in chunks of 256)⌊⌊65,536 / regs per warp⌋ / warps per block⌋
shared memory64 KB (allocated in chunks of 256 B)⌊65,536 / shared per block⌋

Registers per warp is the per-thread count times 32, rounded up to a multiple of 256.

Add one block: worked examples

256-thread blocks (8 warps), 32 registers, no shared memory. Warps: 64/8 = 8 blocks. Registers: 32 × 32 = 1,024 per warp, so 64 warps' worth, which is 8 blocks. Occupancy: 8 × 8 = 64 warps, 100%.

Same, with 64 registers. 2,048 per warp, so 32 warps, so 4 blocks. Occupancy 50%, limited by registers.

Same, with 80 registers. 2,560 per warp, so 25 warps, so ⌊25/8⌋ = 3 blocks. Note the rounding: the 25th warp can't be used because blocks come whole. 24 warps, 37.5%.

128-thread blocks with 20 KB of shared memory. ⌊64 / 20⌋ = 3 blocks, so 12 warps, 18.75%, limited by shared memory.

Find the cliffs. Push registers from 64 to 65 with 256-thread blocks: occupancy falls from 50% to 37.5%. Small changes in resource use can drop a whole block.

The whole machine: what occupancy buys

Occupancy matters because of Little's law. To run memory at full bandwidth, enough bytes must be in flight. In the simulator's model, a warp with one 128-byte request outstanding contributes 128 bytes, so the GPU needs

$$\text{warps} \ge \frac{\text{bandwidth} \times \text{latency}}{128\ \text{bytes} \times \text{requests in flight per warp}}$$

For the GW-1: 341 bytes per cycle × 400 cycles ÷ 128 bytes ≈ 1,067 warps, against a maximum of 16 SMs × 64 = 1,024. Even 100% occupancy only just saturates memory with one request per warp. At 50% occupancy, a simple copy kernel can reach about half of peak bandwidth.

The simulator applies this. A launch takes an optional registers count per thread (default 32, since JavaScript can't tell us the real number) and reports occupancy, occupancyLimiter, and limitedBy: "DRAM latency" when too few requests are in flight.

But more occupancy isn't always better. The term in the denominator, requests in flight per warp, is the other lever. A thread that issues 4 independent loads before using any of them puts 4 requests in flight. It can then run at a quarter of the occupancy with the same bandwidth, and use the freed registers to keep more data close. This Part's last paper chapter, on Volkov's work, is about exactly this trade.

Reality

  • Registers are decided by the compiler. You don't choose them directly; the compiler allocates as many as the code seems to need. You can cap them with __launch_bounds__(maxThreads, minBlocks) or -maxrregcount.
  • Spilling. If the cap is below what the code needs, values spill to local memory. Despite the name, that's per-thread space in DRAM, cached in L1/L2. A few spills are fine; heavy spilling turns register accesses into memory traffic. Part 6 reads the compiler's output to find them.
  • Real limits vary by generation. Typical recent NVIDIA SMs allow 2,048 threads (64 warps), 16–32 blocks, 65,536 registers (at most 255 per thread) and up to about 100–230 KB of shared memory. NVIDIA's occupancy calculator and Nsight Compute do this arithmetic for real GPUs; you now know what they compute.
  • Tail effects. Blocks per SM also decides how many blocks run per wave (Chapter 0.4), so occupancy changes can shift a grid from 2 waves to 3. Part 5 looks at this.
