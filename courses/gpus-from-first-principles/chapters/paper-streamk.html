The work
M. Osama, D. Merrill, C. Cecka, M. Garland, J. D. Owens. "Stream-K: Work-centric Parallel Decomposition for Dense Matrix-Matrix Multiplication on the GPU." PPoPP 2023.
Find it on Google Scholar · Short and clear. Merrill is also an author of the decoupled look-back paper from Part 3, and it shows.

The problem

GEMM libraries split C into output tiles and give each block one tile: the data-parallel decomposition. When the tile count isn't a multiple of the number of SMs, the last wave is partly empty (Chapter 5.4). Libraries fight this with many kernel variants per GPU (different tile shapes, split-K factors) and heuristics to pick one per problem size. That means big binaries, fragile heuristics, and performance that still falls off a cliff for unlucky shapes.

The key idea

Divide the work, not the output. A GEMM's total work is (number of tiles) × (k-iterations per tile) inner-loop iterations. Stream-K launches exactly as many persistent blocks as the GPU can run at once, and gives each one an equal, contiguous range of those iterations, in tile order. A block's range may start in the middle of one tile and end in the middle of another.

$$\text{iterations per block} = \left\lceil \frac{\text{tiles} \times \text{iters per tile}}{\text{blocks}} \right\rceil$$

Tiles covered by more than one block need a fix-up: each contributor produces a partial accumulator, and someone adds them up. In the paper, contributors write partials to a workspace and signal with flags; the block that owns the tile's final iterations waits for them and finishes it, the same consumer–producer pattern as decoupled look-back. Simpler variants use atomic adds into C, or a second, small kernel.

Since every block does the same number of iterations, there is no tail, whatever the problem shape. One kernel configuration covers shapes that used to need many.

Reading guide

  • The motivation figures: data-parallel efficiency against problem size is a sawtooth; Stream-K's is flat.
  • The basic Stream-K algorithm: the iteration-range arithmetic, and the fix-up protocol.
  • The hybrid schedules: pure Stream-K splits many tiles, and every split costs fix-up traffic and hurts cache locality. The paper's practical answer: run full waves data-parallel, and use Stream-K only for the remainder ("data-parallel + Stream-K").
  • The evaluation: thousands of problem shapes against cuBLAS, which picks from many kernels; Stream-K matches or beats it with one.

Reproduce it

Do the scheduling arithmetic: data-parallel time, Stream-K time, and how many tiles end up split (each costing a fix-up). Then the paper project builds Stream-K on your GEMM.

What happened next

Stream-K went into CUTLASS, NVIDIA's open-source GEMM library, as a standard tile scheduler. Work-centric decomposition has since spread to other kernels with uneven parallelism. For example, attention kernels for LLM decoding split long sequences across blocks with a final reduction ("split-KV" or "flash-decoding"), which you'll meet again in Part 8.
