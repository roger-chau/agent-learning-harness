The real problem

Your best SGEMM is limited by FP32 compute: the lanes are doing an FMA almost every cycle. There is no more to win from data movement. The only way past the FP32 roof is a unit that does more multiply-adds per instruction. Deep learning made that worthwhile, since neural networks are mostly GEMMs and tolerate lower precision. Since Volta (2017), every NVIDIA datacenter GPU has had tensor cores.

The smallest idea

A tensor core does a whole small matrix multiply as one warp instruction. In the simulator, one __mma_sync does $C_{16\times16} \mathrel{+}= A_{16\times16} \cdot B_{16\times16}$: 4,096 FMAs from one instruction, where the FP32 lanes would need 128 warp-level FMA instructions.

// sA: 16x16 tile of A, row-major, row stride lda.  sB: 16x16 tile of B, row stride ldb.
acc = __mma_sync(sA, aOffset, lda, sB, bOffset, ldb, acc);   // all 32 lanes, together

The 256 results are spread across the warp as a fragment: lane $l$ holds 8 accumulators, row $l \gg 1$, columns $(l \mathbin{\&} 1) \cdot 8$ to $+7$. Each lane passes in its own 8 and gets its 8 back. Real hardware uses messier layouts (mma.m16n8k16 spreads rows over lane groups), but the idea is the same: the warp collectively owns the tile, and no single thread owns the whole result.

On GW-1, tensor cores give 256 FMAs per SM per cycle against 32 for the FP32 lanes: 8× the roof. On an H100, dense FP16 tensor throughput is roughly 15× FP32.

Add one block: what the precision costs

The catch is the inputs: tensor cores read FP16 (or BF16, TF32, FP8). FP16 has a 10-bit mantissa, so rounding an input to FP16 changes it by up to $2^{-11}$ relative. That's fine for inputs, but deadly for an accumulator:

$$\text{in FP16: } 2048 + 1 = 2048$$

Above 2048 the spacing between FP16 numbers is 2, so adding 1 rounds back down. A long dot product accumulated in FP16 stops growing. That's why tensor cores accumulate in FP32: FP16 products, FP32 sums. This is mixed precision.

FormatExponent bitsMantissa bitsRelative roundingUsed for

A worst-case error budget for an FP16-input GEMM: each of the $n$ products has inputs off by up to $2^{-11}$ relative each, so

$$|C - C_{\text{exact}}| \lesssim n \cdot \max|A| \cdot \max|B| \cdot 2 \cdot 2^{-11}$$

In practice errors partly cancel, and you'll see far less. A test that checks against an FP32 reference with tolerance 1e-3 will fail, and should be replaced with a budget like this one.

The whole machine: memory is the limit again

Put tensor cores in a tiled kernel and the math gets 8× faster, while the loads stay as they were. A kernel that was compute-bound in FP32 is suddenly waiting on memory latency again. This is where Chapter 4.4 pays off: double buffering, and on real hardware cp.async and TMA pipelines. On Hopper, a warpgroup MMA (wgmma) takes its operands straight from shared memory, and the kernel's job becomes keeping that unit fed.

Modern GEMM performance work is mostly that: feeding a matrix unit that's faster than everything around it. It's also why Part 5 measures the memory system so carefully.

Reality

  • You rarely write mma by hand. CUTLASS, cuBLAS, Triton (Part 7) and compilers (Part 6 onwards) generate it. You still need to know its shape, its fragment layout and its precision, to read the generated code and to debug numerical problems.
  • Training in FP16 needs loss scaling (the Mixed Precision Training paper, Part 8) to keep small gradients from flushing to zero. BF16 avoids that with a wider exponent.
  • Peak tensor throughput is quoted for dense matrices; "2:4 structured sparsity" figures are double that and rarely achieved in practice.

Worked examples

Example 1: decomposing a GEMM into MMA instructions

Problem. A 64 × 64 output tile per block, 4 warps, K-step 32, with 16 × 16 × 16 MMAs.

Warp tiles. 4 warps as 2 × 2, each owning 32 × 32 of C: 2 × 2 accumulator fragments.

Per K-step, each warp loads A fragments for its 32 rows × 32 k (2 row-blocks × 2 k-blocks = 4 fragments) and B fragments for 32 k × 32 columns (4 fragments), then issues 2 × 2 × 2 = 8 MMAs: each (row-block, column-block) pair accumulates over the 2 k-blocks.

Reuse in registers: each A fragment is used by 2 MMAs (both column-blocks), each B fragment by 2: 8 fragment loads for 8 MMAs. A 64 × 64 warp tile (4 × 4 fragments) would need 16 loads for 32 MMAs: 2× the reuse. Same lesson as Chapter 4.3, one level up: the fragment is the new "register".

Example 2: choosing a precision with numbers

Task. A layer computes $Y = XW$ with $K = 4096$, inputs of magnitude around 1, and the downstream code needs relative accuracy of about $10^{-2}$ in Y.

FP16 inputs, FP32 accumulation: each input is off by at most $2^{-11}$ relative, so each product by about $10^{-3}$. Those errors have random signs, so they partly cancel in the sum: when Y isn't itself the result of heavy cancellation, its relative error stays around $10^{-3}$ or below. Well within $10^{-2}$.

FP8 E4M3 inputs: each input is off by up to $2^{-4} \approx 6\%$, each product by up to about 12%, typically a few percent. Even with partial cancellation, Y's relative error lands in the percent range: too much, unless values are scaled per block so they use FP8's precision well, and accumulation stays in higher precision. That's what FP8 training recipes and Hopper's FP8 GEMMs do.

Rule: estimate the error from the format's unit roundoff and the reduction length before choosing; then confirm with a test against an FP64 reference.

Example 3: exact tests for tensor-core kernels

Trick. Choose A and B with entries that are small multiples of a power of two (say $k/64$ with $|k| \le 64$). Then every input is exact in FP16 (10 mantissa bits hold 7-bit integers easily), every product is a multiple of $2^{-12}$ with magnitude ≤ 1, and with K = 2048 every partial sum is a multiple of $2^{-12}$ below 2,048: at most 23 significant bits, exact in FP32.

So the tensor-core result, cuBLAS's result and a CPU double-precision result must agree bit for bit, whatever the summation order. Any difference is a bug: a wrong fragment layout, a missed k-step, an off-by-one at an edge. This is how Lab 4 checks the WMMA kernel, and it's far more sensitive than any tolerance.
