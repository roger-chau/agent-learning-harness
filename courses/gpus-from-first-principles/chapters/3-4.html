The real problem

B2's look-back had one block write a value and then set a flag, while another block read the flag and then the value. That only works if the reader can never see the new flag together with the old value. On a machine with many SMs, caches, write buffers and a memory system that reorders requests for speed, nothing makes that order automatic. When exactly does one thread's write become visible to another thread, and what can you rely on?

The smallest idea

Without synchronisation, other threads may see your writes late, and in a different order from the one you made them in. A memory model is the contract that says which orderings are guaranteed. GPUs, like most modern processors, have relaxed models: ordinary loads and stores can be reordered as seen by other threads, and you add ordering explicitly where you need it.

The tools, from narrowest to widest scope:

ToolWhat it guarantees
__syncwarp()lanes of a warp synchronise, and their memory operations before it are visible to each other after it
__syncthreads()the same for all threads of a block: a barrier plus visibility of shared and global writes within the block
__threadfence()no waiting, but this thread's earlier writes become visible device-wide before its later ones
atomicsindivisible read-modify-write; with the right ordering (acquire/release) they also order surrounding accesses

Add one block: message passing

The pattern B2 used, publishing data and then a flag, is called message passing. It needs ordering on both sides:

// producer (block A)                 // consumer (block B)
value[tile] = total;                  while (status[tile] === 0) {}   // wait for the flag
__threadfence();   // value before flag      __threadfence(); // flag before value (acquire side)
status[tile] = 1;                     const v = value[tile];

Without the producer's fence, the flag's write could reach memory first, and the consumer would read a stale value. Without the consumer's ordering, it could read value early (from cache) and the flag later. In CUDA C++ you'd also make the flag accesses volatile or atomic, so the spin loop really re-reads memory instead of a value the compiler cached in a register.

A second classic: the last block done pattern, a single-pass reduction without look-back:

  1. each block writes its partial sum to partials[blockIdx.x];
  2. __threadfence();
  3. thread 0 does atomicAdd(counter, 0, 1); the block that gets back gridDim.x − 1 knows every other block has already published;
  4. that last block sums partials and writes the result.

The whole machine: what you can't do

There's no grid-wide barrier in an ordinary kernel. Suppose every block spins until all blocks reach some point. If the grid has more blocks than can be resident at once, the running blocks wait for blocks that can never start, because the waiting blocks occupy the SMs. That's a deadlock. Cross-block cooperation must therefore be:

  • one-directional and forward-progress-safe: wait only on blocks that have definitely started, which is why B2 uses dynamic tile ids; or
  • split across kernel launches, since a launch boundary is a full grid barrier; or
  • a cooperative launch, where the runtime guarantees all blocks are resident at once, so grid.sync() from cooperative groups is legal.

Reality

  • The simulator can't show you visibility races. It runs blocks one at a time, so writes are always visible in program order. It does randomise block order (blockOrder: "shuffle"), which catches the most common bug, assuming blocks run in index order. Visibility bugs only show up on real hardware, intermittently, which is exactly why you need to reason about them rather than test for them.
  • Scopes and orders. CUDA's C++ memory model (via cuda::atomic) lets you say exactly what you mean: scope (thread block, device, system) and order (relaxed, acquire, release, sequentially consistent). That's the modern replacement for volatile plus fences.
  • Warps aren't implicitly synchronous on Volta and later (Chapter 1.4). Code that exchanges data through shared memory within a warp needs __syncwarp().
