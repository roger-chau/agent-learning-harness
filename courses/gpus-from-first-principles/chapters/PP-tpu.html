Paper project · TPU
Build a weight-stationary systolic array, cycle by cycle, and find out what keeps it busy.

The machine

An array of $K \times N$ cells computes $Y = X \cdot W$ for an $M \times K$ matrix $X$ and a $K \times N$ matrix $W$. Cell $(i, j)$, in row $i$ and column $j$, holds weight $W_{ij}$. Each cycle, every cell:

  1. takes an activation from its left neighbour (row $i$'s left edge is fed from $X$) and passes it right next cycle;
  2. takes a partial sum from the cell above (row 0 receives 0), adds activation × weight, and passes the result down next cycle.

Row $i$ is fed $X_{mi}$ at cycle $m + i$: the skew lines activations up with the partial sums coming down. So the activation $X_{mi}$ and the partial sum for output $(m, j)$ both reach cell $(i, j)$ at cycle $m + i + j$. $Y_{mj}$ leaves the bottom of column $j$ at the end of cycle $m + (K - 1) + j$.

$$\text{cycles} = M + K + N - 2$$

Your busy trace should match the "cells busy now" readout cycle for cycle.

Build, part 1: the array

systolic(X, W, M, K, N) simulates it cycle by cycle, with registers for each cell's activation and partial sum, and returns { Y, cycles, busy }. Y is a flat M×N array, and busy[t] is the number of cells doing a useful MAC at cycle t. Model the registers explicitly: a formula for Y won't produce the right busy trace.

Build, part 2: a TPU-sized problem

Real matrices are bigger than the array. tpuMatmul(X, W, M, K, N, S, overlap) runs an $M \times K$ by $K \times N$ product on an $S \times S$ array ($K$ and $N$ multiples of $S$), one $S \times S$ weight tile at a time, accumulating partial results for each $K$ tile. Loading a weight tile takes $S$ cycles. With overlap false, each tile costs $S$ (load) $+ M + 2S - 2$ cycles. With overlap true, the next tile's weights shift in during the current tile's work (the TPU double-buffers its weights), so only the first load shows. Return { Y, cycles, utilisation }, where utilisation is useful MACs / (cycles × S²).

Then think

Your simulator is fine up to arrays of a few dozen cells a side. For the TPU's real size, use the cycle formula your tests have confirmed: work out utilisation for $S = 256$ with $M = 1$, then $M = 256$, then $M = 4096$. $M$ is the batch size, and that one number is the paper's latency-vs-throughput tension. The write-up asks you to set this against your GEMM kernels and tensor cores.
