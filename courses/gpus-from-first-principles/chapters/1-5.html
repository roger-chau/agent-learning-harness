The real problem

Divergent branches cost the sum of both paths. Even branches that don't diverge aren't free: they're extra instructions, and they split the code into pieces the compiler finds harder to schedule. For a short conditional like "if negative, use zero", a branch is a heavy tool for a light job.

Is there a way to make a decision without changing the flow of control at all?

The smallest idea

Predication: compute both answers, then pick one per lane. Instead of "if p, run A, else run B", every lane runs A and B, and a select instruction keeps A's result where the predicate p is true and B's where it's false. There's no branch, so there's nothing to diverge.

Compare this with the divergent version in Chapter 1.4. Same logic, and here every issued instruction runs on all 32 lanes, so SIMD efficiency is 100%. The price is that every lane executes both sides. Hardware supports this directly: GPU instructions can carry a predicate register that turns them off per lane, and there are select instructions (SEL, FSEL in NVIDIA's machine code) that pick between two registers.

Add one block: when predication wins

Compare the costs of an if/else with paths of $a$ and $b$ instructions, plus a few instructions of overhead for the branch itself:

StrategyCost when the warp divergesCost when it doesn't
branch$a + b$ + overhead$a$ or $b$ + overhead
predicate$a + b$ + 1 select$a + b$ + 1 select

So predication wins when both sides are short, and when divergence is likely. Branching wins when the sides are long and the warp usually agrees. Compilers make this choice automatically for small bodies (if-conversion), usually turning a ternary or a tiny if into a select.

Branch-free idioms

Many conditionals are really arithmetic in disguise:

Instead ofWrite
if (v < 0) v = 0;v = Math.max(v, 0)
if (i < 0) i = 0; if (i > n-1) i = n-1;i = Math.min(Math.max(i, 0), n - 1) (clamp)
if (p) s += v;s += p ? v : 0
if (v < 0) v = -v;v = Math.abs(v)

The clamp deserves special attention. Image filters read neighbours, and at the image border the neighbours don't exist. The branchy fix ("if this is a border pixel, do something else") makes every warp along the edge diverge. The branch-free fix clamps the coordinate: reading pixel $\text{clamp}(x-1, 0, W-1)$ simply re-reads the edge pixel at the border. That's "clamp-to-edge" border handling, and milestone A1 depends on it.

The whole machine

In our simulator, if, while and for are branches and are checked for divergence. Ternaries and Math.min/Math.max are treated as predicated selects. That's a fair model of what a GPU compiler does with short expressions. Real compilers decide for themselves, though: a ternary whose sides call long functions will usually become a branch, and a tiny if will usually become a select. The only way to know for sure is to read the generated machine code, which Part 6 teaches you to do.

Reality

  • Predication isn't free. Both sides always execute, so predicating a long or expensive branch can be slower than diverging, especially when most warps would have agreed anyway.
  • Side effects. Predicated memory operations are safe on GPUs: a load that's turned off doesn't fault. But computing both sides means doing both sides' arithmetic, and that matters when one side is rare and expensive.
  • Uniform branches are cheap. If a condition depends only on uniform values (kernel arguments, blockIdx), every lane agrees, and the branch costs just a couple of instructions. Don't contort such code to avoid it.
  • Rule of thumb. Short and data-dependent: predicate. Long but warp-uniform: branch. Long and data-dependent: restructure the data so warps agree (1.4).

Worked examples

Example 1: if-conversion, step by step

Source: if (v > t) { y = v - t; } else { y = 0; } (a soft threshold).

Branchy machine code (schematic): compare, branch if false, subtract, jump, move zero, join: about 5 instructions, two of them control flow, and a divergent warp runs both sides.

Predicated machine code:

SETP.GT p, v, t      // p = v > t
FADD    d, v, -t     // compute the then-value for every lane
SEL     y, d, 0, p   // y = p ? d : 0

Three instructions, no control flow, 100% SIMD efficiency. Better still, this particular one is y = max(v - t, 0): two instructions (FADD, FMNMX). Recognising that a conditional is really arithmetic (max, min, abs, clamp, multiply by a 0/1 predicate) is the most useful branch-free skill.

Example 2: deciding by cost model

Setup. A particle update: if the particle is outside a boundary (probability $q$ per lane, independently), reflect it (30 instructions); otherwise nothing. Branch overhead 2 instructions; predication runs the 30 instructions on every lane plus 1 select.

Branch: $2 + 30 \cdot P(\text{any lane outside}) = 2 + 30\,(1 - (1-q)^{32})$.

Predicate: 31.

Compare. The branch is cheaper whenever $30\,(1 - (1-q)^{32}) < 29$, i.e. $(1-q)^{32} > 1/30$, i.e. $q < 1 - (1/30)^{1/32} = 10.1\%$. For a few percent of particles out of bounds, branch; for most of them out, predicate. And if particles are sorted spatially, so that out-of-bounds particles cluster in a few warps, the branch wins by far: the probability term becomes the fraction of warps touching the boundary.

Example 3: border handling for a 3 × 3 filter, three ways

Branch per pixel: if (border) slowPath(); else fastPath();. Warps along the left and right image edges diverge (Problem 3: about 6% of warps for 32-wide rows), and the slow path must be written and tested separately.

Clamp per read: every neighbour coordinate becomes min(max(x+dx, 0), W-1): 2 extra instructions per coordinate, 9 reads × 2 coordinates = 36 extra instructions per pixel, for every pixel, but zero divergence and one code path.

Pad the input: copy the image into a buffer one pixel larger on each side, with replicated edges, once. Then the filter reads without any checks. Costs one extra pass over memory, saves every per-read clamp.

Which wins depends on the arithmetic per pixel. For a 3 × 3 blur (9 multiply-adds), 36 clamp instructions per pixel more than quadruple the instruction count, and padding is better if the image is reused. For a heavy filter, clamping is noise. Real libraries use all three; milestone A1 uses clamping because it's correct and simple.
