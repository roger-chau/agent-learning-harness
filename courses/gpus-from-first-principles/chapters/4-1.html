The real problem

Matrix multiplication, $C = A \times B$, is the kernel modern computing runs on. Every layer of a neural network, every attention head, most of scientific computing reduces to it. GPU vendors quote peak FLOP/s, and GEMM is the one workload that can actually reach that peak. A naive GEMM reaches only a small fraction of it, so the gap between naive and tuned is where performance engineers earn their keep. This Part closes that gap step by step, through Project C.

The smallest idea

For $A$ of size $M \times K$ and $B$ of size $K \times N$, each output is a dot product:

$$C_{ij} = \sum_{k=0}^{K-1} A_{ik} B_{kj}$$

That's $M \cdot N \cdot K$ multiply-adds, or $2MNK$ FLOPs. Each multiply-add is one fused multiply-add instruction (FMA: $a \cdot b + c$ with a single rounding). From this Part on, kernels write it explicitly as fma(a, b, c), which lets the simulator count compute:

function naive(A, B, C, n) {
  const col = blockIdx.x * blockDim.x + threadIdx.x, row = blockIdx.y * blockDim.y + threadIdx.y;
  if (row < n && col < n) {
    let s = 0;
    for (let k = 0; k < n; k++) s = fma(A[row * n + k], B[k * n + col], s);
    C[row * n + col] = s;
  }
}

Launches now also report fmaInstructions, flops, achievedGflops and percentOfPeakFp32. The GW-1's FP32 peak is 1,536 GFLOP/s: each SM issues one warp-wide FMA per cycle.

Add one block: GEMM's intensity is high, but naive code wastes it

For square $n \times n$ matrices, GEMM does $2n^3$ FLOPs on $3n^2$ numbers. The minimum DRAM traffic is reading $A$ and $B$ once and writing $C$ once, $12n^2$ bytes, so the best-case intensity is

$$I_{\max} = \frac{2n^3}{12 n^2} = \frac{n}{6}\ \text{FLOP/byte}$$

For $n = 256$ that's about 43, far right of the GW-1's ridge at 3. GEMM can be compute-bound. But the naive kernel doesn't reuse anything on purpose: every FMA issues two loads, so it moves 8 bytes per 2 FLOPs, an intensity of 0.25. Whether those loads hit in cache is luck.

Count instructions too. Per FMA the naive kernel issues two loads, the FMA itself and a loop branch: four instructions, one of them useful math. Even if every load hit in cache, it could reach at most about 25% of peak. Fast GEMM is about raising the fraction of issued instructions that are FMAs, and that means reusing data.

The whole machine

Every byte of $A$ and $B$ is used $n$ times across the whole computation: row $i$ of $A$ by every column of $B$. The game is to load each value into fast storage once and use it many times. The memory hierarchy offers three levels:

LevelReuse techniqueChapter
shared memory (per block)tiles of A and B shared by all threads in a block4.2
registers (per thread)each thread computes several outputs, reusing loaded values4.3

Then 4.5 swaps the FMA units for tensor cores, which multiply whole small matrices in one instruction.

Reality

  • About the simulator in this Part. Simulating a 4096×4096 GEMM in JavaScript would take hours, so the milestones use 128×128 and 256×256 matrices. Two consequences. First, small matrices make filling the GPU hard: 64×64 tiles on a 256×256 matrix give only 16 blocks for 16 SMs, which is real (small GEMMs are hard to make fast) and is part of the lesson. Second, the simulator runs warps one after another, which makes cache reuse look better than on hardware, where warps interleave. So in this Part, trust the instruction-mix numbers (FMAs as a share of issued instructions, loads per FMA) more than the cache hit rates.
  • Libraries. cuBLAS and CUTLASS reach 80–95% of peak on large GEMMs. You'll build the same ladder they climb.

Worked examples

Example 1: the full cost model of naive GEMM

Setup. n = 1024 on the GW-1, naive kernel, 16 × 16 blocks, thread (i, j) computes $C_{ij}$.

Instructions: per FMA, 2 loads + FMA + branch: $4 \times 2^{30} \approx 4.3 \times 10^9$ thread instructions, or $1.3 \times 10^8$ warp instructions. At 16 SMs × 1 warp instruction per cycle (one scheduler's worth in this model) and 1.5 GHz: 5.6 ms. That's the issue-bound floor.

Memory: a warp of 16 × 2 threads reads, per k, one A element per row (2 distinct, broadcast within each half-warp) and 16 consecutive B elements (64 bytes, 2 sectors). Sectors per warp per k: about 4, for 2 FMAs per thread. Across the kernel: $2^{30}/32 \times 4 \times 32 \approx 4.3$ GB of L1/L2 traffic. Most of it hits in cache (A's row is reused by every block in a block-row), so DRAM traffic is far less, but L2 bandwidth (1,024 GB/s) would take 4.2 ms for it.

Prediction: about 5–6 ms, roughly 400 GFLOP/s, 25% of peak, dominated by instruction issue with L2 not far behind. Every later chapter attacks one of these numbers.

Example 2: intensity of real GEMM shapes

Transformer layer (batch × sequence = 4096 tokens, hidden 4096, FP16): the QKV projection is $M = 4096$, $K = 4096$, $N = 3 \times 4096$. $I_{\max} = 2MNK / (2(MK + KN + MN)) \approx 1{,}640$ FLOP/byte (FP16 is 2 bytes): hugely compute-bound.

The same layer during generation, one token at a time: $M = 1$. Now $I_{\max} \approx 2NK/(2KN) = 1$ FLOP/byte: memory-bound by a factor of hundreds on a tensor-core GPU. Batching 64 requests gives $M = 64$ and $I \approx 64$: still below an H100's tensor ridge (about 300 for FP16). This one calculation explains why LLM serving is a memory-bandwidth business and why batching (Part 7) matters so much.

Example 3: checking a GEMM result properly

Problem. Your FP32 GEMM and a CPU reference differ by up to $3 \times 10^{-5}$ on n = 1024 with entries in [−1, 1]. Bug or rounding?

Budget. Each output sums 1,024 products. A sequential sum's error bound is about $n \cdot u \cdot \sum |a_k b_k|$ with $u = 2^{-24} \approx 6 \times 10^{-8}$; with $\sum|a_k b_k| \approx 256$ (average $|ab| = 1/4$), that's $1024 \times 6 \times 10^{-8} \times 256 \approx 0.016$ worst case, and the typical error is about $\sqrt{n}$ times one rounding of a partial sum of size ~10: $32 \times 6 \times 10^{-8} \times 10 \approx 2 \times 10^{-5}$. Your $3 \times 10^{-5}$ is ordinary rounding.

Better test: choose inputs that make every product and partial sum exact (small integers, or multiples of $2^{-6}$ as in Lab 4). Then any mismatch at all is a bug, and the test can demand bit equality.
