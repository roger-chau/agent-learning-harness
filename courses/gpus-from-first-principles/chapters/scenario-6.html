Scenario · Occupancy or ILP, on a small GPU
A fused normalisation kernel runs 4× slower than expected on an embedded GPU. The team suspects the compiler. You have its output and the profiler.
Context
A sensor pipeline normalises each 8-value group a lane owns: subtract the group's mean, divide by its standard deviation (y = (x − mean) · rsqrt(var + 1e-5), var = mean of squared deviations). Warp-row r holds 256 values at X[r·256 + 32·j + lane], j = 0..7; there are $rows warp-rows. Warps loop over rows: row = %warp, %warp + %nwarps, ….
The hardware
An embedded GPU's SM, modelled in GWX with a 16,384-register file (a quarter of the GW-1's). How many warps fit depends on how many registers your code names.
Goal
Rewrite the kernel (NORM) and pick a warp count (WARPS): same results, ≤ 12,000 cycles for 128 rows (the compiler's output, at the most warps that fit, takes about 32,000). Stretch: ≤ 8,500.

Two levers, pulling against each other

Occupancy: fewer registers per thread means more warps to hide the 400-cycle global loads. ILP: issuing all eight loads before using any of them hides latency within a warp, but each in-flight load needs its own register. The compiler's output gets neither right. Find out which one it gets wrong first, using the stall counts and the register count, before you change anything.

The write-up asks for the measurements behind your choice, what a production compiler would have done here, and what you'd tell the team about the hardware.
