A device-wide inclusive scan in a single pass: one launch, reading the input once and writing the output once. Read the decoupled look-back paper chapter right after this one, or before if you prefer the theory first.

Build: scanInclusive

Write scanInclusive(x, y, n): y[i] = x[0] + … + x[i] over all n floats, using exactly one kernel launch. Return that launch's stats. The design:

  1. Dynamic tile ids. Each block takes a tile number from a global counter with atomicAdd, not from blockIdx. Blocks then process tiles in the order they actually start, so a block only ever waits for tiles that have already started.
  2. Scan the tile in shared memory and registers (your 3.2 block scan).
  3. Publish the tile's aggregate: write its total and a status flag "aggregate available" (A) for this tile into global arrays.
  4. Look back: one thread walks backwards over predecessor tiles, adding their aggregates, until it finds a tile with status "inclusive prefix available" (P), adds that prefix, and stops. If it meets a tile with no status yet (X), it waits (spins) and checks again.
  5. Publish the inclusive prefix (P) for this tile, then add the exclusive prefix to every element and write the output.

Use __threadfence() between writing a value and setting the flag that announces it. On real GPUs that ordering is essential (Chapter 3.4).

The simulator will test your assumptions

The checks launch with blockOrder: "shuffle", so blocks run in a random order, as they can on real hardware. If your tile id comes from blockIdx, a block can end up waiting for a tile that hasn't started. The simulator then hits its execution limit ("is there an infinite loop?"). That isn't a simulator bug; on a GPU it would be a hang. Your launch must pass blockOrder and seed through from the opts argument:

function scanInclusive(x, y, n, opts = {}) {
  ...
  return gpu.launch(kernel, { grid, block: 256, ...opts }, ...);
}

How it's checked

  • Correct on several sizes and several shuffled block orders.
  • Exactly one launch, with DRAM traffic ≤ 1.25 × the bytes of input plus output. That's single-pass: no re-reading the input, and the status words are small overhead.
