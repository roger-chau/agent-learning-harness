The real problem

Add up a million numbers. On one CPU core it's a loop: each addition waits for the previous one, a chain a million operations long. On a GPU, a million threads each holding one number is easy, but the answer is one number, and something has to combine them. How do thousands of threads cooperate to produce a single result, without spending all their time waiting on each other?

Reduction (sum, max, min, count, dot product, norm) is the simplest "many to one" pattern, and it shows up everywhere: softmax denominators, loss functions, statistics, the first step of every histogram and scan. Writing a fast one teaches almost every technique in this Part.

The smallest idea

Addition is associative, so the chain can become a tree. Pair up the numbers and add each pair in parallel, then pair up the results, and so on. $n$ numbers need $\log_2 n$ rounds instead of $n - 1$ sequential steps, and the total number of additions is still $n - 1$. Nothing is wasted.

Within a block, the tree lives in shared memory. Each round, thread $t$ adds element $t + s$ into element $t$, with a __syncthreads() between rounds so every thread sees the previous round's results.

A warning about floatsFloating-point addition is not exactly associative: $(a + b) + c$ can differ from $a + (b + c)$ in the last bits. A tree sums in a different order from a loop, so the results differ slightly. That's expected, and the tests allow for it. Part 9 comes back to reproducibility.

Add one block: which threads do the work

There are two natural ways to lay out the tree, and they perform very differently.

Interleaved addressing (stride 1, 2, 4, …): thread $t$ works if $t \bmod 2s = 0$. The active threads are scattered, so every warp diverges in every round, and the shared-memory accesses at stride $2s$ cause bank conflicts.

Sequential addressing (stride $n/2$, $n/4$, …, the first animation): threads $0 \ldots s-1$ work. The active threads are contiguous, so whole warps are either fully active or fully idle. No divergence until $s < 32$, and lanes read consecutive words with no conflicts. Same math, a much better fit for the hardware.

The last 32. Once $s \le 32$, only one warp is working. There's no need for shared memory or block-wide barriers any more: the warp can pass values between lanes directly with shuffles.

// sum the 32 values held by the lanes of a warp
for (let d = 16; d > 0; d >>= 1) v += __shfl_down_sync(0xffffffff, v, d);
// lane 0 now holds the warp's total

__shfl_down_sync(mask, v, d) returns the value of v held by the lane d places higher. It costs one instruction, involves no memory, and needs no barrier, because lanes of a warp meet at the shuffle. (mask names the participating lanes; 0xffffffff means all 32.)

The whole machine: a fast reduction

A memory-bound reduction should run at DRAM bandwidth: read each number once, do one add. Three things get it there:

  1. Many elements per thread. Launch roughly enough threads to fill the GPU (Chapter 2.6), not one per element. Each thread first sums its share with a grid-stride loop (Chapter 1.2), which is fully coalesced. This also shrinks the tree part to a tiny fraction of the work.
  2. Warp, then block. Each warp reduces with shuffles. Each warp's lane 0 writes its result to shared memory, one barrier, and then the first warp reduces those values with shuffles again.
  3. Combine the blocks. Either write one partial per block and launch a tiny second kernel, or have each block atomicAdd its partial into the result (Chapter 3.3). With a few hundred blocks, both cost almost nothing.

The data never leaves registers except for one shared-memory round per block and one global write per block. DRAM traffic is essentially $4n$ bytes, the minimum.

Reality

  • Libraries do this for you (CUB's DeviceReduce, Thrust, torch.sum). Write your own when you need to fuse the reduction into other work: computing a softmax's maximum and sum in the same pass as loading the data, for example (Part 7).
  • Determinism. With atomics, the order blocks finish changes the summation order, so float results can differ run to run in the last bits. When reproducibility matters, use the two-pass version with a fixed tree.
  • Newer hardware helps. Recent NVIDIA GPUs add warp-level reduce instructions for integers, and Hopper's thread-block clusters let blocks combine results through distributed shared memory. The tree is the same idea underneath.

Worked examples

Example 1: Harris's reduction ladder, quantified

Mark Harris's classic sequence of reduction kernels is the best single lesson in GPU optimisation. For a block of 256 and $n = 2^{24}$ floats, here is what each step removes.

  1. Interleaved addressing with modulo. 47 warp-rounds per block (Problem 2), divergent, and % is slow. Each element is read by its own thread, so there are $2^{24}/256 = 65{,}536$ blocks.
  2. Interleaved, strided index (thread t handles element $2st$): no divergence in early rounds, but stride-2s shared accesses: bank conflicts.
  3. Sequential addressing: 12 warp-rounds, no conflicts.
  4. First add during load: each thread loads two elements and adds them before the tree. Half the blocks, and the tree's first round is gone.
  5. Unroll the last warp: the last 5 rounds need no barrier (today: shuffles).
  6. Many elements per thread (grid-stride): a few hundred blocks; the tree's cost becomes negligible (Problem 5: about 0.05% of the additions).

The point: steps 1–5 shave instruction overhead; step 6 changes the algorithm's shape so that the overhead stops mattering. Harris reported about 30× from first to last on 2007 hardware, reaching near-peak bandwidth. Always ask "what fraction of the work is the part I'm optimising?"

Example 2: a warp reduction, traced

Values in lanes 0–7 (an 8-lane warp for readability): 3, 1, 4, 1, 5, 9, 2, 6. Sum 31.

shfl_down, offset 4: lane ℓ adds lane ℓ + 4: lanes 0–3 become 8, 10, 6, 7. Offset 2: lanes 0–1 become 14, 17. Offset 1: lane 0 becomes 31. ✓

shfl_xor, mask 4, 2, 1: each lane pairs with ℓ ⊕ mask and both add. After mask 4 every lane ℓ holds $v_\ell + v_{\ell \oplus 4}$; after mask 2, the sum of its group of 4; after mask 1, all 8: every lane holds 31.

Cost: 3 shuffles + 3 adds either way ($\log_2$ of the width). The xor form costs nothing extra and leaves the result everywhere.

Example 3: reductions that aren't sums

Argmax. Reduce pairs (value, index) with the operator "keep the larger value; on ties, the smaller index". It's associative (and commutative), so every tree works, and the tie rule makes the result deterministic.

Mean and variance in one pass. Reduce triples (count, mean, M2) with Chan's combination rule: for parts A and B, $n = n_A + n_B$, $\delta = \bar x_B - \bar x_A$, $\bar x = \bar x_A + \delta n_B/n$, $M_2 = M_{2,A} + M_{2,B} + \delta^2 n_A n_B/n$. This is associative, so a GPU tree reduction computes a numerically stable variance in one read of the data. The naive $E[x^2] - E[x]^2$ formula is one pass too, but cancels catastrophically when the mean is large compared with the spread (Lab 7, Chapter 9.1).

Rule: anything you can phrase as an associative operator on a small state is a reduction, and gets the same fast tree.
