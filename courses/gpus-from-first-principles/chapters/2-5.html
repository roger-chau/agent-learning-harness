The real problem

Two problems have been waiting for a tool. A transpose must read rows and write columns, so one side is always uncoalesced. And reuse through caches depends on luck: what the replacement policy keeps, and what other warps push out. Both need a place where a block's threads can put data on purpose, read it back in any order, and share it with each other.

The smallest idea

Shared memory is a small, fast, on-chip scratchpad that all threads of a block can read and write. It lives in the same storage as L1 on each SM, has latency of a few tens of cycles instead of hundreds, and is managed entirely by your code. In the simulator you declare it inside the kernel:

const tile = shared("tile", 32 * 32);   // one per block; every thread gets the same array

Because threads write data that other threads will read, they need a barrier: __syncthreads() waits until every thread of the block has reached it, so all writes before it are visible to all reads after it. The pattern is always the same:

  1. Load: threads cooperatively copy a tile from global memory into shared memory, coalesced.
  2. __syncthreads()
  3. Compute: threads read the tile in whatever order the algorithm needs.
  4. If the tile is about to be overwritten, __syncthreads() again.

For a transpose: load a 32×32 tile by rows (coalesced), sync, then write it out by rows of the output, reading the tile by columns. Both global accesses are now coalesced; the awkward access pattern happens in shared memory, where it's cheap. Almost cheap, anyway, as the next block shows.

Add one block: banks

Shared memory serves a whole warp per cycle by splitting into 32 banks. Successive 4-byte words go to successive banks: word $w$ lives in bank $w \bmod 32$. Each bank delivers one word per cycle, so:

  • 32 lanes touching 32 different banks: 1 pass.
  • Several lanes reading the same word: it's broadcast, still 1 pass.
  • $k$ lanes touching different words in the same bank: a $k$-way bank conflict, $k$ passes.

Now read a column of a 32×32 float tile. Lane $\ell$ reads word $32\ell + c$, and $32\ell \bmod 32 = 0$, so every lane hits the same bank: a 32-way conflict, 32 passes for one instruction. The transpose above walks into exactly this.

The classic fix is one word of padding: declare the tile as 32×33 and index it as tile[row * 33 + col]. Now lane $\ell$ reads word $33\ell + c$, which lands in bank $(\ell + c) \bmod 32$: all different. One wasted column buys a 32× speedup on that access.

Try the presets: a row is conflict-free, a column is 32-way, a padded column is conflict-free, and a broadcast costs nothing extra. Then try strides 2, 4, 8, 16: the conflict degree is the largest power of two dividing the stride, up to 32. Any odd stride is conflict-free.

The whole machine

Here is the conflict-free tiled transpose. Blocks are 32×8, so each thread handles 4 elements of the 32×32 tile:

function transpose(a, b, n) {
  const T = 32;
  const tile = shared("tile", T * (T + 1));                   // padded
  const x = blockIdx.x * T + threadIdx.x;
  for (let j = 0; j < T; j += blockDim.y)                       // coalesced reads of rows
    tile[(threadIdx.y + j) * (T + 1) + threadIdx.x] = a[(blockIdx.y * T + threadIdx.y + j) * n + x];
  __syncthreads();
  const ox = blockIdx.y * T + threadIdx.x;
  for (let j = 0; j < T; j += blockDim.y)                       // coalesced writes of rows
    b[(blockIdx.x * T + threadIdx.y + j) * n + ox] = tile[threadIdx.x * (T + 1) + threadIdx.y + j];
}

In the simulator, shared accesses are reported as sharedLoads, sharedStores and bankConflicts. Each extra pass costs an instruction issue slot, so a 32-way conflict can make a kernel issue-bound. You'll measure exactly that in milestone A3.

Barrier rules. Every thread of the block must reach the same __syncthreads(). A barrier inside a branch that only some threads take can deadlock; the simulator detects that and tells you. And __syncthreads() must sit directly in the kernel function, not inside a helper.

Reality

  • Size and carve-out. Real SMs have on the order of 100–230 KB of combined L1/shared storage, with a configurable split. Blocks get 48 KB of shared memory by default and can opt into more. The GW-1 allows 48 KB per block and 64 KB per SM. Shared memory per block is also an occupancy limiter (next chapter).
  • Swizzling. Instead of padding, high-performance libraries often XOR the column index with the row (col ^ row) so that a tile's rows and columns both hit distinct banks without wasting space. CUTLASS and Triton do this automatically.
  • Wider accesses. With 8- or 16-byte accesses per lane, the hardware splits the warp into phases. The rule becomes "conflicts within each phase", but the idea is the same.
  • Async copies. Ampere and later can copy global memory straight into shared memory without passing through registers (cp.async, and Hopper's TMA). That overlaps the load phase with compute. Part 4 uses it.
