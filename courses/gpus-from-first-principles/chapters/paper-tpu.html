The work
N. P. Jouppi et al. "In-Datacenter Performance Analysis of a Tensor Processing Unit." ISCA 2017.
Find it on Google Scholar · About 12 pages, very readable, and written by architects for architects. It's also the case study at the end of H&P Chapter 7.

The problem

Around 2013, Google projected that if users ran voice search for a few minutes a day, serving the neural networks on CPUs would mean doubling its datacenters. Inference has to meet a tight latency limit (the paper's applications had 99th-percentile deadlines around 7 ms), and at that scale the cost that matters is performance per watt and per dollar, not peak speed. GPUs of the day were built for throughput at large batch sizes, which fights a latency limit. Google built a custom chip in about 15 months.

The key idea

Spend the silicon on one enormous matrix unit, and make it a systolic array so it needs almost no data movement. The TPU's Matrix Multiply Unit is a 256 × 256 grid of 8-bit multiply-accumulate cells: 65,536 MACs at 700 MHz, 92 tera-operations per second.

A systolic array pumps data rhythmically through a grid of identical cells, like blood through a heart. In the TPU's weight-stationary design:

  • each cell holds one weight $w_{ij}$, loaded once;
  • activations enter from the left, skewed by one cycle per row, and move one cell right each cycle;
  • partial sums move one cell down each cycle, each cell adding its $x \cdot w$;
  • finished dot products leave the bottom edge.

Step through it. Each colour is one row of $X$. Count the cycles in which the array is only partly full: that fill-and-drain cost is why batch size matters so much.

Every value read from memory is used 256 times as it crosses the array, and cells talk only to neighbours: no register files, no caches, no crossbars. That's the whole trick, and it's GEMM data reuse (Chapter 4.2) made physical.

$$\text{Peak} = 256 \times 256 \times 2 \times 0.7\,\text{GHz} \approx 92\ \text{TOPS}$$

Reading guide

  • The architecture section. The block diagram: Unified Buffer (24 MiB of activations), Weight FIFO fed from 8 GiB of DDR3 at 34 GB/s, the Matrix Unit, 4 MiB of accumulators. The TPU is a coprocessor on PCIe: the host sends it CISC-style instructions.
  • The roofline figures. The most important figures. Operational intensity here is MACs per byte of weights read, and the TPU's ridge point is around 1,350. Four of the six production workloads (the MLPs and LSTMs) sit far left of it: memory-bound, limited by the 34 GB/s DDR3, not by the 92 TOPS.
  • The latency vs. batch size table. Larger batches raise intensity, but the latency deadline caps the batch. This tension is why the CPU and GPU did badly on the latency-limited workloads.
  • The section on alternative TPU designs, which asks what would have helped. The answer is memory bandwidth: with GDDR5, the TPU would have been about 3× faster on average.
  • "Fallacies and pitfalls". Short, opinionated, quotable in interviews.

Reproduce it

Do the paper's roofline arithmetic. For a fully connected layer with 8-bit weights and batch size $B$, each weight byte read from DRAM is used in $B$ MACs, so its intensity is $B$ MACs per weight byte. That gives the batch size where a layer stops being memory-bound. The paper project after this chapter builds the array itself, cycle by cycle.

What happened next

The paper's verdict, that memory bandwidth was the limit, shaped what followed. TPU v2 (2017) added HBM, bfloat16 (a format Google introduced) and training support; later generations scaled to pods of thousands of chips with custom interconnects. GPUs answered the same year: Volta's tensor cores (Chapter 4.5) are small matrix units inside each SM. Today every serious AI accelerator, GPU or not, is built around matrix units and fights the same battle this paper describes: keeping them fed.
