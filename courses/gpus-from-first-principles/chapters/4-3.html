The real problem

The tiled kernel still issues two shared-memory loads for every FMA. Shared memory is fast, but each load is still an instruction, and instructions are the bottleneck: one FMA in three issued is a ceiling of about 33% of peak. To go further, the operands must come from registers, the only storage an FMA can read for free.

The smallest idea

Have each thread compute a small block of outputs, an outer product, from values held in registers. If a thread owns a $4 \times 4$ patch of $C$, then for each $k$ it loads 4 values of $A$ (a column slice) and 4 values of $B$ (a row slice) and does all $4 \times 4 = 16$ FMAs between them:

$$C_{ij} \mathrel{+}= a_i \cdot b_j \quad \text{for } i, j \in \{0..3\}: \quad 8 \text{ loads} \to 16 \text{ FMAs}$$

In general, an $r \times c$ thread tile costs $r + c$ loads per $r \cdot c$ FMAs. Loads per FMA fall from 2 (one output per thread) to $(r+c)/(rc)$: 0.5 for 4×4, 0.25 for 8×8.

const acc = new Array(16).fill(0);              // 16 accumulators in registers
for (let k = 0; k < 16; k++) {
  const a = ldg4(sA, k * BM + tr);              // 4 values of A's column k
  const b = ldg4(sB, k * BM + tc);              // 4 values of B's row k
  for (let i = 0; i < 4; i++)
    for (let j = 0; j < 4; j++) acc[i * 4 + j] = fma(a[i], b[j], acc[i * 4 + j]);
}

ldg4 reads 4 consecutive values in one instruction (a 16-byte vector load, Chapter 4.4). For it to work, A's tile is stored transposed in shared memory, so a thread's 4 values of column $k$ sit next to each other.

Try it: grow the thread tile and watch shared loads fall and registers rise. Then grow the block tile until the 256×256 problem no longer has enough blocks for 16 SMs.

Bigger thread tiles cut instructions but cost registers: 64 accumulators, plus the loaded values, plus addresses, is easily 100+ registers per thread. That means fewer resident warps (Chapter 2.6), and Volkov's point (Part 2's paper) applies: that's fine, as long as each warp has plenty of independent work. A thread with 64 independent FMAs per $k$ step has ILP to spare.

They also cost parallelism: bigger block tiles mean fewer blocks. On a 256×256 matrix, 64×64 tiles give 16 blocks, exactly one per GW-1 SM. On anything smaller, part of the GPU idles. Real libraries pick tile shapes per problem size for this reason.

The whole machine: the GEMM hierarchy

A high-performance GEMM is three nested tilings:

  1. Block tile (e.g. 64×64 of C): loaded through shared memory, reused by all threads of the block.
  2. Warp tile: the slice of the block tile one warp computes. In real kernels it's arranged so the warp's shared-memory reads are conflict-free or broadcast.
  3. Thread tile (e.g. 4×4 or 8×8): held in registers, the outer product.

CUTLASS's documentation draws exactly this hierarchy. Each level exists to raise reuse at the level above it.

Reality

  • Real kernels run 128 or 256 threads per block with block tiles like 128×128 and thread tiles of 8×8. Our 256×256 test matrices are too small for that, so the milestone uses smaller tiles.
  • Register pressure is decided by the compiler. Spills (Chapter 2.6) can silently ruin a register-tiled kernel, and Part 6 shows how to spot them in the generated code.
  • In JavaScript, acc is an array. On a GPU, a fully unrolled kernel keeps those 16 or 64 values in individual registers; that only works because the loops over i and j have constant trip counts.

Worked examples

Example 1: mapping threads to a 64 × 64 block tile

Choice. A 64 × 64 block tile with 4 × 4 thread tiles needs $4096/16 = 256$ threads. Arrange them as a 16 × 16 grid: thread (ty, tx) owns rows $4ty..4ty+3$ and columns $4tx..4tx+3$.

Per k: the thread reads sA_T[k][4ty..4ty+3] (A transposed: 4 contiguous floats, one float4) and sB[k][4tx..4tx+3] (one float4), then 16 FMAs.

Warp view. A warp is threads 0–31: ty ∈ {0, 1}, tx = 0..15. Its A reads hit 2 distinct float4s (broadcast to 16 lanes each); its B reads hit 16 consecutive float4s = 64 words = 2 phases of 32 banks, conflict-free. Both cheap.

Alternative "strided" mapping (thread owns rows ty, ty + 16, ty + 32, ty + 48): the same reuse, no float4 reads unless the layout is permuted. CUTLASS-style kernels choose mappings so each thread's values are contiguous for vector loads and each warp's reads are broadcasts or conflict-free: that's the warp tile.

Example 2: arithmetic intensity at every level

Kernel: block tile 128 × 128, BK = 8, 256 threads with 8 × 8 thread tiles.

  • DRAM → shared: per k-step, $(128 + 128) \times 8 = 2{,}048$ floats (8 KB) for $128 \times 128 \times 8 = 131{,}072$ FMAs: 64 FMAs per float, 32 FLOP/byte.
  • Shared → registers: per thread per k, 16 floats for 64 FMAs: 4 FMAs per float loaded.
  • Registers → FMA units: every FMA reads 3 registers; free.

Each level has an intensity, and each must exceed the ratio of compute to that level's bandwidth. Shared memory on the GW-1 delivers 32 words per cycle per SM against 32 FMAs per cycle: needs ≥ 1 FMA per word. At 4, there's margin, which is why this kernel can approach peak.

Example 3: diagnosing a register-tiled kernel that's slower than expected

Symptom. An 8 × 8 thread-tiled kernel reaches 40% of peak, not the 80% the instruction count predicts.

Check 1, spills: -Xptxas -v reports "0 bytes spill stores": fine. (If not, the accumulators live in local memory and every FMA does a memory access.)

Check 2, the accumulator array: if the code indexes acc[i][j] with loop variables the compiler can't fully unroll (a runtime tile size), the array can't live in registers at all (Lab 6's local-memory lesson): look for LDL/STL in the SASS.

Check 3, bank conflicts on the A reads if A isn't stored transposed: each thread's 8 values are a column, stride BK... conflict counters in the profiler.

Check 4, waves: a 512 × 512 problem with 128 × 128 tiles is only 16 blocks; with 2 per SM on a 34-SM card, the GPU is a quarter full. Choose the tile for the problem.

Each check is a different number in the profiler; knowing which number to read first is the skill.
