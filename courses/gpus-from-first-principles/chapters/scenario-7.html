Scenario · Serving an LLM
A team serves a 7B-parameter model on one GPU. They batch requests in fixed groups and the GPU sits half-idle. Write the scheduler that decides, step by step, which requests run.
The model of the system
Generation proceeds in decode steps. In each step, every active request produces one token. A step costs stepBaseUs (reading 7 GB of weights at 1 TB/s: 7,000 µs) plus usPerKvToken (0.5 µs) per token held in the active requests' KV caches. So batching is nearly free until the KV cache grows: Scenario 4 from the other side.
Memory
The KV cache is paged: blocks = 512 blocks of blockSize = 16 tokens. A request holding prompt + generated tokens uses ⌈that / 16⌉ blocks. Every step, the active requests' blocks must fit (after the step's new token).
Rules
All requests are waiting at time 0, each with a known prompt length and output length. Once a request starts, it runs in every step until it has produced all its tokens: no preemption.
Goal
schedule(requests, cfg) returns the list of steps, each an array of request ids. It must be valid and finish at least 1.8× faster than the team's current static batching (in the starter) on hidden workloads. Stretch: 2.3×.

Where the time goes

Static batching takes groups of requests that fit if each one reserved the maximum length, and runs each group until its longest request finishes. Short requests finish early and leave their slot idle while the long ones run. That's padding, and worst-case reservation on top. The vLLM paper (earlier in this Part) attacks both: continuous batching admits a new request the moment there's room, and paging means "room" is measured in blocks actually used.

The hard part is admission without preemption: admit too eagerly and the cache overflows later as everyone's context grows. The starter's evaluate tells you exactly where a schedule breaks.
