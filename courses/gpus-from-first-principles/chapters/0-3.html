The real problem

Take a simple processing loop: load a value, do a few cycles of arithmetic on it, load the next. With a cache miss to DRAM costing hundreds of cycles, the execution unit sits idle for most of every iteration. Caches and out-of-order execution shrink that idle time for one thread, at great cost in transistors and power, and for streaming data they barely help at all.

The idle unit is the waste. Is there another way to fill it?

The smallest idea

When one thread is waiting, run a different one. If the machine holds many threads, each with its own independent work, then whenever one stalls on memory, another is usually ready to issue an instruction. The latency of each individual load doesn't change at all. It's simply hidden behind other threads' work.

For this to pay off, switching must be essentially free. If changing threads meant saving and restoring registers through memory, as an operating-system context switch does, the switch would cost more than the wait. So the hardware keeps every resident thread's registers on-chip at the same time, and choosing which thread issues next is just a multiplexer decision made each cycle.

CPUs do a mild version of this: simultaneous multithreading (Intel calls it Hyper-Threading) keeps two threads per core. A GPU does it at enormous scale, with dozens of groups of threads resident on each core.

Add one block: how many threads?

Model it precisely. One execution unit issues one instruction per cycle. Each thread repeatedly does $C$ cycles of computation, then issues a load and waits $L$ cycles for it. A thread therefore needs the unit for $C$ cycles out of every $C + L$.

Assume a greedy scheduler: it keeps issuing from the same thread until that thread stalls on its load, then switches to the next ready one. Real warp schedulers use policies in this spirit, such as "greedy-then-oldest". With $N$ threads, the demand on the unit per period is $N \cdot C$ cycles out of $C+L$. The unit can't be more than fully busy, so

$$\text{utilization} = \min\!\left(1,\ \frac{N\cdot C}{C+L}\right) \qquad N_{\text{saturate}} = \left\lceil \frac{C+L}{C} \right\rceil$$

Worked example: $C = 2$ cycles of compute per load and $L = 16$ cycles of latency. One thread keeps the unit $2/18 \approx 11\%$ busy. Four threads: $8/18 \approx 44\%$. You need $\lceil 18/2 \rceil = 9$ threads to saturate it.

Now use realistic GPU numbers. Memory latency is about 400 cycles, and a streaming kernel might do only about 4 cycles of work per load. That gives $\lceil 404/4 \rceil = 101$ threads' worth of work in flight per execution unit. That's the scale of concurrency we're designing for.

Press play with 4 threads, then drag the thread count up until the bottom "unit" row is solid. Then raise the memory latency and watch gaps reappear: more latency needs more threads. Raise compute per load instead and fewer threads suffice: more work per load needs fewer threads.

The whole machine

This is Little's law again, seen from the execution unit. To keep a resource busy you need enough independent work in flight to cover its latency: $N \cdot C \geq C + L$ is "concurrency × work per item ≥ latency × throughput" with a throughput of one instruction per cycle.

There are two ways to get that concurrency, and GPU performance engineers use both:

  • Thread-level parallelism (TLP): more threads, each with one thing in flight. That's what the animation shows.
  • Instruction-level parallelism (ILP): each thread issues several independent loads before it needs any of them, so one thread has several things in flight. Four independent loads per thread can stand in for four times as many threads.

Hold on to that second option; it becomes important in Part 2 when threads get expensive, and again in Part 6 when the compiler schedules instructions for you.

The key ideaA GPU doesn't make memory faster. It holds so many threads that some always have work ready, so the execution units stay busy while each individual thread waits.

Reality

Threads aren't free. Every resident thread's registers must stay on-chip, and the register file has a fixed size. On many recent NVIDIA GPUs each SM (streaming multiprocessor, the GPU's equivalent of a core) has 65,536 32-bit registers and can host at most 2,048 threads.

  • If each thread needs 32 registers: $65{,}536 / 32 = 2{,}048$ threads fit, the maximum.
  • If each thread needs 64 registers: only $1{,}024$ fit, half the latency-hiding capacity.
  • If each thread needs 128 registers: only $512$ fit.

So there is a trade-off at the heart of GPU tuning. Using more registers per thread can make each thread faster, through more ILP and more data kept close, but it leaves fewer threads to hide latency. The fraction of the maximum threads that are actually resident is called occupancy, and Part 2 builds an occupancy calculator from first principles. Part 6 shows that the compiler's register allocator is quietly deciding this trade-off for you.
