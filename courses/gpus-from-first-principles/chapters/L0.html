Why this lab

Part 0 made predictions from first principles: memory latency is hundreds of nanoseconds, so you need a lot of work in flight to use the bandwidth; on your RTX 2060 Super, one load per warp shouldn't be enough. Now you test them on real silicon. Everything that follows in the real-GPU track uses the setup you do here, the shared harness (labs/common/gw.h), and the habit this lab is really about: write the prediction down before you run the experiment.

Setup (once)

  1. Operating system. Native Linux is simplest. On Windows, use WSL2 with Ubuntu: CUDA works inside WSL2 with the normal Windows NVIDIA driver (don't install a Linux driver inside WSL).
  2. Driver and toolkit. A recent NVIDIA driver, and the CUDA Toolkit 12.x from NVIDIA's site (on WSL2, pick the "WSL-Ubuntu" installer). Check: nvidia-smi shows your card; nvcc --version prints 12.x.
  3. Profilers. Nsight Compute (ncu) and Nsight Systems (nsys) come with the toolkit. Reading hardware counters needs permission: on Linux, run ncu with sudo or allow it for all users through the driver option NVreg_RestrictProfilingToAdminUsers=0; on Windows/WSL2, enable "Allow access to the GPU performance counters to all users" in the NVIDIA Control Panel's developer settings.
  4. Groundwork. Run groundwork on the same machine, so make submit can reach it.

What to do

Open labs/L0-hello/l0.cu. Implement the kernels marked TODO:

  • A. add: vector addition with a bounds check (n isn't a multiple of the block size).
  • B. Three copy kernels: one element per thread; copyK<K>, which issues all K loads before any store, with each warp's accesses contiguous; and copy_vec4, one 16-byte float4 per thread. The harness checks each one copies exactly, then times it and compares with cudaMemcpy.
  • C. chase: one thread follows a chain of indices, timing itself with clock64(). The harness builds random cyclic chains in arrays from 16 KB to 256 MB, so you see the latency of L1, L2 and DRAM as plateaus.

Before running, write down (in the write-up box): your predicted percentage of peak bandwidth for copy1, copy4 and copy_vec4, using Chapter 0.4's Example 4; and your guess at the DRAM latency in nanoseconds. Then make run.

What you should see, and why

  • The copies should improve from 1 to 2 to 4 elements per thread and level off near the hardware's practical ceiling, often 80–90% of the theoretical peak. If copy1 is already near that, your card's latency or occupancy differs from the chapter's assumptions: use your measured latency to explain it in the write-up.
  • The latency curve should step up as the array outgrows each cache: L1 (tens of cycles), L2 (a few hundred cycles), then DRAM. At the largest sizes TLB misses add to the DRAM number: the Volta microbenchmark paper (Part 5) separates them.
  • Part D multiplies your measured DRAM latency by the peak bandwidth: the bytes in flight your card needs. Compare it with what one load per resident warp supplies.

Then try: change the block size in the launches (128, 512), and K to 8. Profile copy1 with make ncu and find "DRAM Throughput" and "Achieved Occupancy" in the report.

Passing

All correctness checks pass, and your best copy kernel reaches at least 75% of theoretical peak bandwidth. The lab report asks you to compare every prediction with the measurement, and to explain each miss. That habit is what employers mean by "performance intuition".
