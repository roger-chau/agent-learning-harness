The real problem

A 5-tap blur reads every pixel five times: once for itself and once as a neighbour of four others. If each of those reads went to DRAM, the blur would move five times the data it needs. Yet blurs on real GPUs run close to "read once, write once" speed. Something between the SMs and DRAM is catching the repeats.

The smallest idea

A cache keeps recently used sectors close, so repeated accesses skip DRAM. It works when the same data is reused soon enough, before other data pushes it out. "Soon enough" has a precise meaning: if the amount of distinct data touched between two uses of a sector (its reuse distance) is smaller than the cache, the second use hits.

GPUs have two levels of hardware cache for global memory:

  • L1, per SM, combined with shared memory in the same on-chip storage (hundreds of KB per SM on recent GPUs, split between the two).
  • L2, shared by all SMs, in front of DRAM. Every DRAM access passes through it. Large GPUs have tens of megabytes.

The GW-1 simulator models a 256 KB L2: an LRU (least recently used) cache of 32-byte sectors. A sector that hits costs L2 bandwidth (twice DRAM's) but no DRAM traffic. l2HitRate and dramBytes report what happened.

Add one block: GPU caches are small per thread

Here's the number that makes GPU caching different from CPU caching. Divide the cache by the threads sharing it:

$$\frac{\text{256 KB of L1 per SM}}{2048 \text{ resident threads}} = 128 \text{ bytes per thread}$$

A CPU core might have 32–48 KB of L1 for one or two threads. A GPU thread gets about a cache line's worth. A GPU cache can't hold each thread's private working set. It helps when neighbouring threads share data (the blur's neighbours, a stencil's halo, a matrix row many threads read), and when reuse happens within a short window.

Worked example: a 5-tap horizontal blur over a 512×512 float image. Warps process rows left to right, so the neighbours a warp reads were loaded by the same or the previous warp a moment ago. The reuse distance is tiny, and almost every repeat read hits. DRAM sees about 4 bytes read and 4 written per pixel, even though the code issues five reads.

Now a bad case: a matrix walked by columns, where each warp's sectors aren't touched again until the whole column (thousands of sectors later) has been visited. If that exceeds the cache, every reuse misses.

The whole machine

How to use caches deliberately:

  • Shrink reuse distance. Process data in an order where reuse comes soon: tiles instead of whole rows or columns. Block shape decides which threads run together, and so what's "recently used".
  • Keep working sets under capacity. If a kernel's hot data fits in L2, repeated passes over it are nearly free; if it's 2× too big, an LRU cache can hit almost never on a cyclic sweep. That cliff is worth knowing about.
  • Don't depend on luck. When reuse is predictable, it's usually better to manage it yourself in shared memory: you choose what's kept and for how long, with no evictions. That's the next chapter.

Reality

  • Real L1 behaviour varies by generation. Whether global loads are cached in L1 by default, the line and sector sizes, and the L1/shared-memory split have all changed across NVIDIA architectures. The read-only data path (const __restrict__ pointers, or __ldg) tells the compiler a load can use the texture/read-only caching path.
  • Write policy. Writes typically go to L2 (not L1) and are merged there. The simulator counts a written sector that misses as one sector of DRAM traffic.
  • L2 controls. Ampere and later GPUs let you set aside part of L2 for "persisting" accesses, keeping a chosen buffer resident across kernels.
  • Replacement isn't perfect LRU. Real caches are set-associative with approximate replacement. The simulator's fully associative LRU is a clean model to reason with, not a cycle-exact copy.

Worked examples

Example 1: predicting a hit rate from reuse distance

Setup. A vertical 5-tap blur (each output reads its pixel and 2 above, 2 below) on a 4096 × 4096 float image, with warps assigned row by row, left to right, top to bottom. L2 is 256 KB.

Reuse distance. Pixel (x, y) is read by outputs in rows $y-2$ to $y+2$. Between the first and last of those reads, the kernel processes 4 full rows of outputs. Each row of outputs touches 5 input rows' worth of sectors in its window, but the distinct new data per output row is one input row: 16 KB. So the reuse distance is about $4 \times 16 = 64$ KB, well under 256 KB.

Prediction: every repeat hits; DRAM sees each input pixel once. Now make the image 32,768 wide: one row is 128 KB, the reuse distance is about 512 KB, and repeats start missing. The same kernel's DRAM traffic jumps up to 5×.

Fix: process the image in vertical strips (say 1,024 columns wide) so that the rows of a strip are short. Same code, different traversal order, and the reuse distance shrinks by the strip ratio.

Example 2: LRU on a cyclic sweep, step by step

Setup. A 3-line LRU cache, access sequence A B C D A B C D…

Trace. A, B, C miss (cold). D misses and evicts A, the least recently used. Then A misses and evicts B; B misses and evicts C; and so on: every access misses. With a 4-line cache, the second round hits everything.

Why it matters. One line short of the working set gives 0% hits, not 75%. Random replacement would keep some lines across rounds and do better here. GPU L2 replacement isn't pure LRU, but the cliff still shows up: a kernel's hit rate can collapse when the problem size grows past cache size, and the response is to tile (Example 1) or to use shared memory.

Example 3: how much does a cache save a stencil?

Setup. A 7-point 3-D stencil (centre and 6 neighbours) on a $512^3$ float grid, one output per thread, warps along x.

No cache: 7 reads + 1 write = 32 bytes per point. Perfect cache: 4 + 4 = 8. Ratio 4×.

What a real cache catches. The x-neighbours are in the same or adjacent sectors as the centre: caught by L1 immediately. The y-neighbours are one row (2 KB) away: caught if a block covers several rows. The z-neighbours are one plane (1 MB) away: with a 256 KB L2 and a plane-by-plane traversal, they miss. So DRAM traffic is about 4 (centre and x) + 4 (z−1) + 4 (z+1) + 4 (write) = 16 bytes: 2× the ideal.

Fix: 2.5D blocking: each block marches along z through its x–y tile, keeping three planes of the tile in shared memory or registers. Then z-reuse is managed on chip, and DRAM traffic falls to the 8-byte minimum. This is how production stencil codes work.
