The real problem

Each thread of a filter keeps some elements and drops others. Where should element 5,000 go in the output? It depends on how many elements before it were kept, which depends on every earlier thread's decision. Allocating output space, splitting work into buckets, building sparse structures, radix sorting: they all need, for every position, the total of everything before it. That looks inherently sequential. It isn't.

The smallest idea

A scan (prefix sum) turns $x_0, x_1, x_2, \ldots$ into running totals:

x31704
inclusive$y_i = x_0 + \cdots + x_i$34111115
exclusive$y_i = x_0 + \cdots + x_{i-1}$0341111

The exclusive scan of "how many items does each thread keep?" is exactly "where does each thread start writing?". Like reduction, scan only needs associativity, so it can be computed as a tree. The question is which tree.

Add one block: two classic trees

Hillis–Steele: in round $k$, every element adds the one $2^k$ places to its left. That's $\log_2 n$ rounds, every thread busy every round, and $n \log_2 n$ additions in total. Simple and short, but it does more work than needed, so it's best for small $n$ such as the 32 lanes of a warp.

Blelloch: an up-sweep (a reduction tree that keeps its partial sums), then a down-sweep that pushes prefixes back down. That's $2 \log_2 n$ rounds but only about $2n$ additions: work-efficient. It's better for large block-level scans when the extra rounds are affordable.

A warp scan with shuffles is Hillis–Steele in registers:

// inclusive scan across the 32 lanes of a warp
const lane = threadIdx.x % 32;
for (let d = 1; d < 32; d *= 2) {
  const y = __shfl_up_sync(0xffffffff, v, d);
  if (lane >= d) v += y;
}

A block scan composes it: scan within each warp, write each warp's total to shared memory, scan those totals (with one warp), then add each warp's exclusive offset back. That's two barriers in total.

The whole machine: scanning across blocks

Blocks can't see each other's shared memory or wait for each other with a barrier. So how do you scan a million elements spread over hundreds of blocks? Classic answers take several kernel launches:

  1. Reduce, then scan. Kernel 1: each block reduces its tile to one total. Kernel 2: scan the tile totals (small). Kernel 3: each block scans its tile again, starting from its tile's offset. DRAM traffic: read $n$, read $n$ again, write $n$, so $3n$.
  2. Scan, then propagate. Each block scans its tile and writes it plus its total; scan the totals; add offsets in a final pass. Traffic: about $4n$.

Both are correct, but a scan is memory-bound, so $3n$ means it runs at most at a third of copy speed. The ideal is $2n$: read once, write once. Getting there needs blocks to pass prefixes to their successors during a single pass. This Part's paper chapter, on decoupled look-back, shows how, and milestone B2 builds it.

Reality

  • Libraries: CUB's DeviceScan uses the single-pass design. Thrust and PyTorch's cumsum build on similar machinery.
  • Scans of other operators (max, logical OR, even matrix products) work the same way, provided the operator is associative. "Segmented" scans restart at segment boundaries and are the core of many sparse algorithms.
  • Floats again: different trees round differently, so a GPU cumsum can differ from a sequential one in the last bits.

Worked examples

Example 1: Blelloch's scan, traced on 8 elements

Input: [3, 1, 7, 0, 4, 1, 6, 3].

Up-sweep (reduction, keeping partials in place). Stride 1: positions 1, 3, 5, 7 add their left neighbour: [3, 4, 7, 7, 4, 5, 6, 9]. Stride 2: positions 3, 7 add the value 2 to the left: [3, 4, 7, 11, 4, 5, 6, 14]. Stride 4: position 7 adds position 3: [3, 4, 7, 11, 4, 5, 6, 25].

Down-sweep. Set the last element to 0 (the identity): [3, 4, 7, 11, 4, 5, 6, 0]. Stride 4: for the pair (3, 7): left takes the right's value, right takes left + right: position 3 ← 0, position 7 ← 11 + 0 = 11: [3, 4, 7, 0, 4, 5, 6, 11]. Stride 2: pairs (1, 3) and (5, 7): [3, 0, 7, 4, 4, 11, 6, 16]. Stride 1: pairs (0,1), (2,3), (4,5), (6,7): [0, 3, 4, 11, 11, 15, 16, 22].

Check: exclusive scan of the input is [0, 3, 4, 11, 11, 15, 16, 22]. ✓ Additions: 7 up, 7 down: $2(n-1)$.

Example 2: stream compaction of a sparse vector

Task. Convert a dense vector of $n$ floats with about 10% non-zeros to (index, value) pairs.

Plan. Each thread handles 8 consecutive elements: counts its non-zeros (in registers); block-scan the counts; the block's total is published, and blocks get their offsets (three-phase or look-back); each thread writes its non-zeros at its offset, in order.

Traffic. Three-phase: read $n$ (count), read $n$ again (write phase), write $0.1n$ pairs (8 bytes each): $4n + 4n + 0.8n = 8.8n$ bytes. Single pass: $4n + 0.8n = 4.8n$. For $n = 2^{26}$: 590 MB versus 322 MB, 1.15 ms versus 0.63 ms on the GW-1.

Note the per-thread chunk of 8 means each thread's loads are 32 bytes apart: load them as two float4s per thread (still sector-efficient), or stage through shared memory.

Example 3: why scan needs associativity, and what that excludes

Associative: +, max, min, AND, OR, matrix product, the segmented operator, the "affine map composition" $(a_1, b_1) \circ (a_2, b_2) = (a_1 a_2, a_2 b_1 + b_2)$.

That last one parallelises a recurrence. $y_i = a_i y_{i-1} + b_i$ (an IIR filter, a linear RNN, a state-space model) looks sequential. But each step is the affine map $y \mapsto a_i y + b_i$, and composition of affine maps is associative. Scan the pairs $(a_i, b_i)$ with that operator, apply to $y_0$, and every $y_i$ comes out in $O(\log n)$ span. This is exactly how linear-recurrence models such as Mamba are trained on GPUs.

Not associative: subtraction, division, floating-point addition (approximately associative: different trees give slightly different results), "keep the most recent non-NaN"... unless rephrased with extra state.
