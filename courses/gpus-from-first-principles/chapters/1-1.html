The real problem

Part 0 ended with a design decision: to pay for instruction fetch and decode only once per many threads, the GPU groups threads into bundles of 32 that execute the same instruction at the same time. Hardware like that is fast and cheap. The question is how anyone is supposed to program it.

There have been two answers, and the difference between them is the difference between a CPU's vector unit and a GPU. The first puts the width in front of the programmer. The second hides it.

The smallest idea

SIMD (single instruction, multiple data) makes the width explicit. A vector register holds, say, 16 floats, and one instruction adds two such registers lane by lane. Your loop becomes "for every chunk of 16 elements: load a vector, compute, store a vector". You, or an auto-vectoriser, write code about vectors. CPU extensions like SSE, AVX and AVX-512 work this way.

SIMT (single instruction, multiple threads) hides the width. You write ordinary scalar code for one thread: load my element, compute, store my element. The hardware runs 32 such threads in lockstep, one per lane. Each lane is a whole thread with its own registers and its own index. The vector still exists, but you never name it.

Step through it. Every line is one warp instruction, and all 32 lanes execute it together, each on its own data. That's the whole execution model when there are no branches.

Add one block: what the hardware takes over

Three things make SIMD code tedious. SIMT moves each of them into hardware.

  1. Tails. With 16-wide vectors and $n = 1000$, you get $\lfloor 1000/16 \rfloor = 62$ full vectors and a tail of $1000 - 992 = 8$ elements that needs special handling: a scalar loop or a masked vector instruction. In SIMT you launch $\lceil 1000/32 \rceil = 32$ warps, and the last warp has $1000 - 31 \times 32 = 8$ threads that pass the if (i < n) guard. The tail is just threads that do nothing.
  2. Addresses. SIMD loads want contiguous, aligned chunks; anything else needs explicit gather and scatter instructions. In SIMT every thread computes its own address, and any pattern is legal. The hardware combines the 32 addresses of a warp into as few memory transactions as it can. Whether that's 1 or 32 transactions is a performance question, not a correctness one; Part 2 is about it.
  3. Conditionals. SIMD code handles if with mask registers and blend instructions that you (or the compiler) write. In SIMT each thread just writes if, and the hardware tracks which lanes are active. Chapter 1.4 shows exactly what that costs.
The key ideaSIMT is SIMD where the hardware manages the vector: per-lane addresses, tails and masks. You write scalar code; the costs of the vector don't go away, they just stop being visible in the source.

The whole machine

SIMT didn't appear from nowhere. Vector supercomputers such as the Cray-1 already ran long vectors through pipelined units, with a vector-length register to handle tails and "strip-mining" to cut long loops into register-sized pieces. Hennessy & Patterson describe a GPU as a multithreaded SIMD processor, and that phrase is precise:

  • SIMD: a warp is a SIMD instruction stream 32 lanes wide.
  • Multithreaded: the SM holds many warps and switches among them every cycle to hide latency, which is Chapter 0.3 at warp granularity.
  • Plus per-lane addressing and hardware masking, which is what lets each lane pretend to be an independent thread.

The illusion has limits, and most of this course is about them. Lanes of a warp that want different instructions must take turns (1.4). Lanes that want scattered addresses cost extra transactions (Part 2). The programming model is scalar; the performance model is still a vector.

One more reality: CPUs and GPUs are converging at the edges. AVX-512 added per-lane masks, which pushes SIMD toward SIMT's convenience. Intel's ISPC compiler offers a SIMT-style "program one lane" model on top of CPU SIMD. And GPUs added warp-level instructions such as shuffles and votes that deliberately expose the vector again, because sometimes the programmer can use it better than the illusion can. Worked examples

Example 1: the same loop, written both ways

Task. $y_i = a x_i + y_i$ (SAXPY) for $n = 1000$.

SIMD (16-wide). The programmer writes about vectors: a loop of $\lfloor 1000/16 \rfloor = 62$ iterations, each loading 16 floats from x and 16 from y, one vector FMA, one vector store; then a tail of 8 elements, either a scalar loop or one masked vector iteration. Three pieces of code: the main loop, the tail and the setup that computes where the tail begins.

SIMT. The programmer writes about one element: i = blockIdx.x * blockDim.x + threadIdx.x; if (i < n) y[i] = a * x[i] + y[i];. Launch $\lceil 1000/256 \rceil = 4$ blocks of 256 threads (32 warps). One piece of code.

What the hardware does in each case is nearly identical: 32-lane (or 16-lane) loads, an FMA, a store, with lanes past the end switched off. The difference is who writes the bookkeeping. That's the sense in which a warp is a SIMD instruction stream that the hardware assembles from threads.

Example 2: lane efficiency of a launch, exactly

Setup. Kernel launches of size $n = 33$, $n = 100$ and $n = 10^6$, block size 128.

Method. Warps launched: $w = \lceil n/32 \rceil$ (blocks are multiples of 32, and warps entirely past $n$ still exist inside the last block, so count lanes per block: $\lceil n/128 \rceil \times 128$).

  • $n = 33$: one block, 128 lanes, efficiency $33/128 = 25.8\%$. Three of the four warps are almost or completely empty.
  • $n = 100$: one block, $100/128 = 78.1\%$.
  • $n = 10^6$: $7813$ blocks, $10^6/1{,}000{,}064 = 99.99\%$.

Interpretation. Tails cost a bounded amount per launch: at most one block's worth of lanes. They matter for small launches and for code that launches once per small piece of work (one launch per row of a small matrix, say), which is a common performance bug: batch the pieces into one launch.

Example 3: the cost of hiding the vector

Setup. Each thread reads x[perm[i]] for a random permutation perm.

In SIMD you'd have to write a gather instruction, and you'd see the cost in the source. In SIMT it's an ordinary load, and it compiles and runs correctly. But a warp's 32 addresses are now scattered across 32 different 32-byte sectors, where a contiguous load would touch 4. The warp's load moves 8× the bytes it uses.

Lesson. SIMT changes what's expressible without changing what's cheap. The performance model of every kernel in this course is still the vector: which lanes are active (Chapters 1.3–1.5) and which addresses they touch together (Part 2).
