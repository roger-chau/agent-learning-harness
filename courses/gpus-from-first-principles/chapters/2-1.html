The real problem

You've written a kernel and it runs in 2 ms. Is that good? Without a reference point you can't tell whether there's 10× left on the table or nothing at all. And if there is room, you don't know which way to push: fewer instructions, or fewer bytes.

The GPU has two ceilings: how fast it can compute and how fast it can move data. Every kernel hits one of them first. To know which, you need one number about the kernel.

The smallest idea

Arithmetic intensity is the work a kernel does per byte it moves to or from DRAM:

$$I = \frac{\text{floating-point operations}}{\text{bytes of DRAM traffic}} \quad \left[\tfrac{\text{FLOP}}{\text{byte}}\right]$$

Vector addition c[i] = a[i] + b[i] on floats does 1 FLOP per element and moves 12 bytes (two 4-byte reads, one 4-byte write): $I = 1/12 \approx 0.083$. A tiled matrix multiply reuses each loaded number dozens of times and can reach $I$ of 10 or more.

Intensity is a property of the algorithm and its data movement, not of the hardware. That's what makes it useful: it lets you place any kernel on any machine.

Add one block: the roofline

A kernel can't go faster than peak compute, and it can't process data faster than memory delivers it. With bandwidth $B$ (bytes/s) and intensity $I$, memory feeds at most $I \cdot B$ FLOP/s. So

$$\text{attainable FLOP/s} = \min\big(\text{peak FLOP/s},\ I \times B\big)$$

On a log-log plot of attainable performance against $I$, that's a slanted line (memory-bound) meeting a flat line (compute-bound): a roofline. The corner is the ridge point, $I^* = \text{peak} / B$. Kernels to its left are memory-bound; to its right, compute-bound.

For the GW-1: peak compute is 16 SMs × 32 lanes × 2 FLOP per fused multiply-add × 1.5 GHz = 1,536 GFLOP/s, and bandwidth is 512 GB/s. The ridge is at $1536/512 = 3$ FLOP/byte. Vector addition, at $I = 1/12$, can reach at most $512/12 \approx 43$ GFLOP/s: under 3% of peak compute, however well it's written. Its only meaningful goal is to run at full bandwidth.

Drag your kernel's intensity across the ridge. Then raise the bandwidth: every memory-bound kernel speeds up, and the ridge moves left. Raise peak compute instead and memory-bound kernels gain nothing. Most GPU generations add compute faster than bandwidth, so the ridge keeps moving right, and more kernels become memory-bound.

The whole machine

The roofline tells you which resource to measure yourself against and which optimisations can help:

If the kernel is…measure againstwhat helps
memory-bound (left of the ridge)% of peak bandwidthmoving fewer bytes: coalescing (2.3), reuse via caches and shared memory (2.4–2.5), fusion of kernels, smaller data types
compute-bound (right of the ridge)% of peak FLOP/sfewer or cheaper instructions, keeping all lanes busy (no divergence), tensor cores (Part 4)

The intensity in the formula counts DRAM traffic, which is what actually happens, not what the source code seems to read. A blur reads each pixel 5 times in the source, but if the neighbours come from cache, DRAM sees each pixel about once. So the same code can have very different intensity depending on how well it uses the memory hierarchy. Much of performance engineering is moving a kernel rightwards on the roofline by cutting DRAM traffic.

The GW-1 simulator reports dramBytes, so from now on you can compute any kernel's real intensity.

Reality

  • There are more roofs. Real GPUs have a ceiling for each level of the hierarchy (L2 bandwidth, shared-memory bandwidth) and for each kind of math (FP32, FP16, tensor cores). Tensor-core peak is often 10–20× the FP32 peak, which pushes the ridge far to the right.
  • Peaks aren't reachable. Practical ceilings are typically 80–90% of spec-sheet bandwidth and somewhat less than peak FLOP/s. The roofline is an upper bound, not a prediction.
  • Latency can keep you under both roofs. A kernel with too little parallelism is limited by neither bandwidth nor compute but by latency, as in Part 0. Then it sits below the roofline, and the fix is more concurrency, not fewer bytes. This Part's Volkov paper chapter is about exactly this.
