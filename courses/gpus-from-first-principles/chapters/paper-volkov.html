The work
V. Volkov. "Understanding Latency Hiding on GPUs." PhD thesis, University of California, Berkeley, 2016 (EECS technical report).
Also see his earlier talk, "Better Performance at Lower Occupancy" (NVIDIA GPU Technology Conference, 2010), which made the idea famous.
Find the thesis on Google Scholar · It's long: the reading guide picks the chapters that matter here.

The problem

For years, GPU programming advice said: maximise occupancy. More resident warps means more latency hiding, so use few registers, small blocks, little shared memory. But that advice is often wrong, and following it can make kernels slower. Using fewer registers can mean recomputing values, spilling, or giving up the data reuse that registers provide. Volkov asked a precise question: how much parallelism does a GPU actually need to hide latency, and does it have to come from warps?

The key idea

Latency hiding needs enough independent operations in flight, and they can come from instruction-level parallelism within each thread as well as from more threads. It's Little's law, applied carefully:

$$\text{operations in flight needed} = \text{latency} \times \text{throughput}$$
$$\text{in flight} = \text{resident warps} \times \text{independent operations per warp (ILP)}$$

So a target can be met with many warps and ILP 1, or a quarter as many warps and ILP 4. The second option leaves each thread more registers, which can hold data the kernel reuses, turning memory traffic into register traffic. That's why some of the fastest kernels, like dense matrix multiply, run at low occupancy: each thread computes many outputs, holds many values in registers, and keeps many independent loads and FMAs in flight.

The thesis also shows that "how much occupancy you need" isn't one number. It differs for arithmetic latency (short) and memory latency (long), and for memory it depends on bytes in flight, not just instruction counts. The simple occupancy rules of thumb ignored both.

Reproduce it

A note on the simulator. JavaScript can't tell the simulator how many of a warp's loads are independent, so a launch declares it with the ilp option (default 1), just as it declares registers. The time model then uses Little's law: bytes in flight = resident warps × bytes per request × ilp.

The experiment: a copy kernel where each thread moves 4 elements, with all 4 loads issued before any store. That's genuinely 4 independent requests per thread. Then:

  • launch it with registers: 128, which drops occupancy to 25%, and ilp: 1. Bandwidth collapses, because too little is in flight;
  • launch the same thing with ilp: 4. Bandwidth comes back to near peak, at a quarter of the occupancy.

Before running it, predict both numbers from the formula. That's the point of the model.

What happened next

"Lower occupancy, more work per thread" became standard practice in high-performance kernels. CUTLASS GEMMs, FlashAttention and most hand-tuned kernels deliberately use many registers per thread and run at modest occupancy, relying on ILP and software pipelining (Part 4) to keep enough operations in flight. Profilers changed their message too: Nsight Compute reports occupancy, but its guidance focuses on why warps are stalled rather than on raising occupancy for its own sake (Part 5).
