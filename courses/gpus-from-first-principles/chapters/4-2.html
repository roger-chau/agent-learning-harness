The real problem

In the naive kernel, the 16 threads that compute one row of a 16×16 output tile all read the same row of $A$, and the 16 threads in a column all read the same column of $B$. Each value is fetched from the memory system again and again by neighbouring threads. If a block loaded those values once into shared memory, every thread could reuse them.

The smallest idea

Split the $k$ loop into tiles. A block computing a $T \times T$ tile of $C$ walks along $k$ in steps of $T$. At each step it loads a $T \times T$ tile of $A$ and one of $B$ into shared memory, coalesced, one element per thread. After a barrier, every thread does $T$ FMAs from shared memory, then another barrier, and on to the next step.

for (let k0 = 0; k0 < n; k0 += T) {
  sA[ty * T + tx] = A[row * n + k0 + tx];        // one element each
  sB[ty * T + tx] = B[(k0 + ty) * n + col];
  __syncthreads();
  for (let k = 0; k < 16; k++) s = fma(sA[ty * T + k], sB[k * T + tx], s);
  __syncthreads();                                // before overwriting the tiles
}

Each element loaded from global memory is now used $T$ times, so global traffic per FMA drops by a factor of $T$. With $T = 16$, global loads go from 2 per FMA to $2/16 = 0.125$.

Add one block: what tiling buys, and what it doesn't

Count instructions per FMA in the inner loop: two shared loads (sA[…] is the same for the whole row of threads, so it's a broadcast; sB[…] is conflict-free), one FMA. The global loads are amortised away. That's three instructions per FMA, so the ceiling rises from 25% to about 33% of peak.

That's an improvement, but notice what tiling didn't change: every FMA still needs two operands brought from somewhere. Shared memory is fast, but each shared load is still an instruction issue. To break past a third of peak, operands must come from registers, which is the next chapter.

Choosing $T$. Bigger tiles mean more reuse but more shared memory per block ($2T^2 \times 4$ bytes) and fewer blocks. $T = 16$ uses 2 KB; $T = 32$ uses 8 KB with 1,024-thread blocks. On a small matrix, big tiles also mean too few blocks to fill the SMs.

A note on loop bounds. The inner loop above is written with a literal bound (k < 16). Like a real compiler, the simulator fully unrolls short loops with literal bounds (≤ 64 iterations), so they cost no branch instructions. Write k < T instead and you pay a branch per iteration, just as on a GPU when the compiler can't see the trip count.

The whole machine

Tiling applies at every level. Blocks tile $C$; shared memory tiles $A$ and $B$ along $k$; and, in real libraries, the order in which blocks are launched is arranged so that blocks running at the same time share $A$ rows and $B$ columns in L2 (block "swizzling" or rasterisation). Every level has the same structure: bring a tile close, use it many times, move on. Milestone C1 asks you to build the shared-memory level and measure how much global traffic per FMA it removes.

Reality

  • Real kernels use rectangular tiles (e.g. 128×128 blocks with $K$-steps of 32) and load tiles with vector instructions.
  • Bank conflicts matter when loading $A$ transposed into shared memory: padding or swizzling (Chapter 2.5) applies.
  • Ampere and later GPUs can copy tiles straight into shared memory asynchronously (cp.async, and TMA on Hopper), which Chapter 4.4 discusses.
