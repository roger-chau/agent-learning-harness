The real problem

Here is a puzzle that every performance engineer meets early. You have a machine whose memory can deliver hundreds of gigabytes per second. You write the simplest possible program: walk through an array and add up its numbers, one load after another. You measure it, and it moves data at a small fraction of that headline number.

Nothing is broken. The program is fast in one sense and slow in another, and the word "fast" was hiding two different quantities. Until we separate them, nothing else in this course will make sense, because a GPU is a machine built entirely around the gap between them.

The smallest idea

Any system that does work on a stream of requests (a memory, a network, a checkout queue) has two independent numbers:

  • Latency: how long one request takes, from the moment you ask to the moment you get the answer. Measured in time: nanoseconds, cycles.
  • Throughput (for memory, bandwidth): how many requests, or bytes, the system completes per unit of time once it's busy. Measured in work per time: requests per nanosecond, GB/s.

Picture a pipe. Its length is the latency: how long a drop of water takes to travel through. Its width is the throughput: how much water comes out of the far end each second. A long, wide pipe has high latency and high throughput. Those aren't in conflict; they're different axes.

Concretely, take the simulated GPU we'll use throughout this course, the GW-1. Its memory has a latency of about 400 cycles at 1.5 GHz, which is roughly 270 ns, and a bandwidth of 512 GB/s. Both numbers are true at the same time. A single request takes 270 ns no matter how wide the pipe is.

Add one block: Little's law

If a request takes 270 ns, how can the memory deliver 512 GB/s? Only by working on many requests at once. How many? Count the dots in the pipe.

Suppose requests enter at a steady rate of $\lambda$ per nanosecond, and each one spends $W$ nanoseconds inside. Then in steady state the number inside, $L$, is

$$L = \lambda \times W$$in flight = throughput × latency

This is Little's law. It needs almost no assumptions: only that the system is in a steady state, so that on average as many requests leave as enter. Here's why it holds. Watch the pipe for a long time $T$. About $\lambda T$ requests pass through, and each one contributes $W$ nanoseconds of being "inside". So the total request-time accumulated is $\lambda T W$. Divide by $T$ to get the average number inside at any moment: $\lambda W$.

A worked example with real numbers

For memory it's convenient to count bytes instead of requests. Throughput in GB/s times latency in ns gives bytes, because $10^9$ bytes per second times $10^{-9}$ seconds is just bytes:

$$512\ \tfrac{\text{GB}}{\text{s}} \times 270\ \text{ns} = 512 \times 270\ \text{bytes} \approx 138{,}000\ \text{bytes}$$

To keep the GW-1's memory fully busy, about 138 KB must be in flight at every moment. If each request is a 4-byte float, that's about 34,500 loads in flight. Fewer than that and the pipe has gaps. The bandwidth is still there, but you aren't using it.

Play with the sliders. Double the latency and twice as many requests must be in flight to keep the same throughput. Halve the request size and you need twice as many requests for the same bytes. The pipe is the same; only how full you keep it changes.

The whole machine

Now the puzzle from the start resolves itself. Our array-summing loop issues one load, waits for it, adds, and issues the next. It keeps one request in flight. By Little's law its throughput is

$$\lambda = \frac{L}{W} = \frac{4\ \text{bytes}}{270\ \text{ns}} \approx 0.015\ \text{GB/s}$$

That's about 15 MB/s on a machine rated for 512 GB/s: one thirty-four-thousandth of the pipe. The memory isn't slow; the program asks for too little at a time.

So the amount of concurrency a machine can sustain decides what fraction of its bandwidth you can use. That's a property of the hardware design as much as of your code. A CPU core tracks only a limited number of outstanding cache misses, roughly 10 to 16 on recent x86 cores, each fetching a 64-byte line. With around 100 ns of DRAM latency:

$$\frac{12 \times 64\ \text{bytes}}{100\ \text{ns}} \approx 7.7\ \text{GB/s per core}$$

That's why one CPU core can't saturate a modern memory system, however clever its caches. Hardware prefetchers help by issuing requests early, but the in-flight limit still caps them.

The key ideaTo use bandwidth you need concurrency. The amount you need is fixed by Little's law: bytes in flight = bandwidth × latency.

Reality

Three things complicate the clean picture, and you'll meet all of them again.

  • Latency isn't constant. As you push a memory system toward its peak bandwidth, requests queue up and latency rises, sometimes a lot. Little's law still holds for the averages, but the $W$ you plug in is the latency under load, not the idle-machine number on a spec sheet.
  • Peak is rarely reachable. Real kernels typically top out somewhere around 80–90% of the rated memory bandwidth. The rest goes to refresh, bank conflicts inside DRAM, and protocol overhead. Part 2 measures this.
  • Real GPUs need a lot more. A data-center GPU with roughly 3 TB/s of HBM bandwidth and on the order of 500–700 ns of loaded latency needs megabytes in flight, on the order of half a million 4-byte loads at once.

That last number is the whole reason the GPU looks the way it does. No design based on a few clever cores tracking a dozen misses each will ever have half a million loads outstanding. You need a machine built from the ground up to keep an enormous number of requests in flight. The next three chapters build it.
