The real problem

Profilers tell you that a kernel is issue-bound or waiting on memory. The generated code tells you why: which instructions are there, how many per loop iteration, and what the compiler did or didn't do with your source. Reading PTX and SASS fluently is the most common day-to-day skill in GPU performance work, and the entry ticket for compiler work.

The smallest idea: PTX, line by line

Learn to read one kernel completely, then the rest is vocabulary. Here is PTX of the kind nvcc -ptx produces for if (i < n) y[i] = a * x[i] + y[i];:

.visible .entry saxpy(.param .u32 n, .param .f32 a, .param .u64 x, .param .u64 y)
{
    .reg .pred %p<2>;  .reg .f32 %f<5>;  .reg .b32 %r<6>;  .reg .b64 %rd<8>;
    ld.param.u32   %r2, [n];
    ld.param.f32   %f1, [a];
    ld.param.u64   %rd1, [x];
    ld.param.u64   %rd2, [y];
    mov.u32        %r3, %ctaid.x;           // blockIdx.x
    mov.u32        %r4, %ntid.x;            // blockDim.x
    mov.u32        %r5, %tid.x;             // threadIdx.x
    mad.lo.s32     %r1, %r3, %r4, %r5;      // i
    setp.ge.s32    %p1, %r1, %r2;           // i >= n ?
    @%p1 bra       $L__BB0_2;
    cvta.to.global.u64 %rd3, %rd1;
    mul.wide.s32   %rd4, %r1, 4;            // byte offset, 64-bit
    add.s64        %rd5, %rd3, %rd4;
    ld.global.f32  %f2, [%rd5];
    cvta.to.global.u64 %rd6, %rd2;
    add.s64        %rd7, %rd6, %rd4;
    ld.global.f32  %f3, [%rd7];
    fma.rn.f32     %f4, %f1, %f2, %f3;      // a * x[i] + y[i], round to nearest
    st.global.f32  [%rd7], %f4;
$L__BB0_2:
    ret;
}

Things to notice: typed virtual registers declared in bulk; parameters loaded from a parameter space; special registers for the thread's coordinates; the if became a predicated branch around the body; addresses are 64-bit byte addresses computed explicitly; the multiply and add were contracted into one fma.

Add one block: SASS, what actually runs

The same kernel in SASS looks something like this (illustrative, in the style of recent architectures; exact output varies by compiler version and GPU):

S2R          R4, SR_CTAID.X
S2R          R3, SR_TID.X
IMAD         R4, R4, c[0x0][0x0], R3          // blockIdx * blockDim + tid
ISETP.GE.AND P0, PT, R4, c[0x0][0x160], PT    // i >= n
@P0 EXIT
MOV          R5, 0x4
IMAD.WIDE    R2, R4, R5, c[0x0][0x168]        // &x[i]
IMAD.WIDE    R4, R4, R5, c[0x0][0x170]        // &y[i]
LDG.E        R2, [R2.64]
LDG.E        R7, [R4.64]
FFMA         R7, R2, c[0x0][0x164], R7        // a read straight from the constant bank
STG.E        [R4.64], R7
EXIT

Differences from PTX are where the hardware shows through: real registers (R0–R254, predicates P0–P6), kernel parameters read directly from a constant bank (c[0x0][...]) as instruction operands, address arithmetic folded into IMAD.WIDE, the branch replaced by a predicated EXIT. Each instruction also carries control bits (stall cycles, yield hints, dependency barriers) that the compiler sets, which is how the hardware knows when a result is ready without a full scoreboard check.

The whole machine: what to look for

For a hot loop, count per iteration:

  • Useful math (FFMA, HMMA) against everything else: this is the FMA share from Part 4, read straight off the code.
  • Loads: their width (LDS.128 vs LDS), their space, and whether they were hoisted out of the loop.
  • Overhead: index arithmetic, compare, branch. Unrolling divides it by the unroll factor.
  • Local memory (LDL/STL): register spills. Usually a disaster in a hot loop.
  • Conversions and 64-bit math you didn't expect: an int index promoted to 64 bits, a double constant forcing FP64.

Reality

  • Learn PTX's grammar from NVIDIA's PTX ISA manual. SASS has only an instruction list, and is learned by reading lots of it (Compiler Explorer is ideal).
  • Line up SASS with source using Nsight Compute's source page, which also shows where the stalls happen, per instruction.
  • When a result surprises you, change one thing in the source and diff the generated code. It's the compiler-side twin of Part 5's one-change-at-a-time rule.

Worked examples

Example 1: auditing a register-tiled GEMM's inner loop

What you expect per k for an 8 × 8 tile: 4 × LDS.128 and 64 × FFMA, no branch inside an unrolled k-block, nothing else.

What you find (a real-world-style dump): 4 × LDS.128, 64 × FFMA, plus 8 × IMAD and 2 × IADD3 per k. Those are shared-memory addresses being recomputed each step because the tile offset was written sA[(k * BM) + ty * 8] with k a runtime loop variable and the loop not unrolled.

Fix: #pragma unroll on the k-loop within the tile (BK = 8 is constant), so every address becomes base + immediate offset, encoded in the LDS instruction itself. FMA share goes from 64/78 = 82% to 64/68 = 94%. That's a 15% speedup found by counting lines.

Example 2: spotting an accidental FP64 path

Symptom: an FP32 kernel is 10× slower on a GeForce card than on an A100.

SASS grep: cuobjdump -sass | grep -E "DMUL|DADD|DFMA|F2F" finds F2F.F64.F32 and DFMA inside the loop. Source: expf(x) * 2.0 + 1.0: double literals.

Why the GPUs differ: A100 runs FP64 at half the FP32 rate; GeForce cards at 1/32 or 1/64. The same bug costs 2% on one and 10× on the other. Fix with 2.0f and 1.0f, and add -Wdouble-promotion style checks (or grep SASS in CI).

Example 3: was the load vectorised?

Source: float4 v = reinterpret_cast<const float4*>(x)[i];

Expected SASS: one LDG.E.128. If you see four LDG.E, the compiler couldn't prove alignment (for example, x came from pointer arithmetic with an odd offset, or the type punning went through a struct without alignment). If you see LDG.E.128.CONSTANT (or .NC), the read-only path is in use, thanks to const __restrict__. The SASS mnemonic encodes width and caching path, so one line answers both questions.

Readings

  • Required: NVIDIA, CUDA Binary Utilities (cuobjdump, nvdisasm) and its instruction set reference tables for your architecture.
  • Required: NVIDIA, Parallel Thread Execution ISA, chapter 9 (instruction set): read the entries for ld, st, fma, setp, bra, mma.
  • Optional: Z. Jia et al., "Dissecting the NVIDIA Volta GPU Architecture via Microbenchmarking" (2018), section on instruction encoding and control codes.
  • Optional: Compiler Explorer (godbolt.org) supports CUDA: compare PTX and SASS for small kernels interactively.
