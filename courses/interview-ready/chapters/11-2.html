The signal

Every design uses the same dozen building blocks. Know each one's job, its scaling limit and its failure mode well enough to justify choosing it in one sentence.

The core idea: replicate for reads and availability, partition for writes and size

BlockJobKey trade-offs
Load balancer (L4/L7)spread requests over stateless servers; health checksL7 can route by path and terminate TLS; sticky sessions hurt balance

Relational DBtransactions, joins, constraintsvertical limits on writes; read replicas lag

Replication: leader-follower (simple; followers lag, so reads may be stale) or leaderless quorums (R + W > N gives read-your-writes-like guarantees). Partitioning (sharding): by key hash (even spread, no range scans) or by key range (range scans, risk of hot ranges). Consistent hashing places nodes and keys on a ring, so adding a node moves only ~1/N of the keys; virtual nodes even out the load.

CAP, practically: during a network partition you choose between consistency (refuse some requests) and availability (serve possibly stale data). Outside partitions the real trade-off is latency vs consistency (PACELC).

The invariant and template: caching patterns

# Cache-aside (lazy loading): the default
def get(key):
    v = cache.get(key)
    if v is None:
        v = db.read(key)
        cache.set(key, v, ttl=jittered(300))    # jitter TTLs to avoid synchronised expiry
    return v
def update(key, v):
    db.write(key, v)
    cache.delete(key)                          # delete, don't set: avoids racing stale writes

Write-through (write the cache and the DB together: fresher, slower writes); write-back (write the cache, flush later: fast, risks loss). Cache stampede: when a hot key expires, thousands of requests hit the DB at once. Mitigate with request coalescing (one loader per key), early probabilistic refresh, or serving stale content while revalidating.

A thinking trace: the hot partition

  1. Setup: a social app shards posts by user_id hash. One celebrity's account gets 10⁵ reads/s; their shard's p99 latency spikes and the shard falls over.
  2. Diagnose: hash partitioning balances keys, not load. A single hot key concentrates load on one shard however many shards exist.
  3. Read-side fixes: cache the hot key (and replicate the cache entry across several cache nodes), push it to a CDN, and serve from read replicas.
  4. Write-side fixes: split the hot key (a key suffix 0..k-1 spreads its writes over k shards; reads gather all k), or batch counter updates in memory and flush periodically.
  5. Detect: per-key request metrics and top-k heavy-hitter tracking (count-min sketch), so the system can promote hot keys automatically.

The habit: after any partitioning choice, ask "what's the most skewed realistic workload?". Uniformity assumptions fail at the worst moment.

Traps and variations

  • Exactly-once delivery doesn't exist end to end; use at-least-once delivery plus idempotent consumers (dedupe by message id).
  • Distributed transactions (two-phase commit) are slow and fragile. Prefer sagas with compensating actions, or design so updates stay within one partition.
  • Secondary indexes on sharded data are either local (scatter-gather reads) or global (writes touch several shards).
  • Time: clocks drift, so don't order events across machines by wall-clock time. Use logical clocks or a single sequencer.
  • Backpressure: queues hide overload until they're full. Bound them, and shed load early.
