The signal

A set of items, each with a weight (cost, size, count of zeros…) and maybe a value, a capacity or target, and a question about subsets: can we hit the target exactly? What's the maximum value within the capacity? How many ways are there? Partition into equal halves, target sum with ±, coin change, ones and zeroes, and the "last stone weight" variants are all knapsacks in disguise. Recognising the disguise is the skill.

The capacity has to be small (a table over it, roughly 10⁴–10⁶ entries). With huge targets and tiny n (≤ 40), use meet-in-the-middle instead.

The core idea: items outside, capacity inside

State: dp[c] = the best (or the count, or feasibility) using the items processed so far with capacity c. Process items one at a time. For each, every capacity either uses it or doesn't:

dp_new[c] = combine(dp_old[c], dp_old[c − w] + v)

With a single array the direction of the inner loop encodes the item rule:

  • Downward (c from high to low): dp[c − w] is still the old value, so each item is used at most once. That's 0/1 knapsack.
  • Upward: dp[c − w] may already include this item, so items are reusable. That's the unbounded knapsack.

And when counting, the order of the loops decides what you count. Items outside counts combinations (each multiset once). Capacity outside counts sequences (order matters).

The invariant and template

# 0/1: each item at most once (DOWNWARD)
dp = [base] + [init] * C
for w, v in items:
    for c in range(C, w - 1, -1):
        dp[c] = best(dp[c], dp[c - w] + v)

# Unbounded: reuse allowed (UPWARD)
for w, v in items:
    for c in range(w, C + 1):
        dp[c] = best(dp[c], dp[c - w] + v)

# Feasibility as a bitset (Python int or std::bitset)
reach = 1
for w in weights: reach |= reach << w     # 0/1 subset sums in O(n · C / 64)

Invariant (0/1, after processing item k): dp[c] = the best over subsets of the first k items with total weight ≤ c (or exactly c, depending on the base: "≤" starts every entry at 0, "exactly" starts at −∞ except dp[0]).

A thinking trace: target sum

  1. Brute force: 2ⁿ sign assignments. With n = 20 that's 10⁶, which actually passes. Say so, and then improve, because the follow-up will raise n.
  2. Memoised search: state (index, running sum) with sums in [−S, S] gives O(n · S). That's fine, but the state looks awkward.
  3. Algebra: let P be the sum of the + numbers and N the sum of the − numbers. Then P − N = target and P + N = S, so P = (S + target) / 2.
  4. Reduction: the answer is the number of subsets with sum P, a 0/1 knapsack count with a downward inner loop. If S + target is odd or |target| > S, the answer is 0.
  5. Test: zeros ([0, 0, 1] and target 1 gives 4, since each 0 can be ±), target 0, and a negative target.

The move: do algebra on the objective before choosing a state. Signs, differences ("minimise |A − B|" means "get a subset as close to S/2 as possible") and complements all reduce to standard knapsacks.

Traps and variations

  • Loop direction (0/1 versus unbounded) and loop order (combinations versus permutations) are the two classic bugs. State them before you code.
  • "Exactly c" versus "at most c": the base cases differ. Get them wrong and an infeasible state looks feasible.
  • Last stone weight II: minimise |A − B| over a two-way split. That's subset sums closest to S/2.
  • Bounded knapsack (item i at most kᵢ times): binary splitting into 1, 2, 4, … copies reduces it to 0/1.
  • Combination sum IV (count ordered sequences): capacity outside, items inside.
  • Pseudo-polynomial: O(n · C) is polynomial in the value of C, not its number of bits. Knapsack is NP-hard, so if C is 10⁹ the table is impossible. Mention this; quant and systems interviewers like hearing it.
