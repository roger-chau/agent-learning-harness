The signal

"What does std::move do?", "why is my vector of strings slow to grow?", "lvalue vs rvalue", "implement perfect forwarding", "when is a copy elided?". Move semantics questions test whether you understand value categories and the cost model behind them, which is exactly what latency-sensitive roles care about.

The core idea: a move is a copy that may steal from a source nobody will look at again

Every expression has a type and a value category. Roughly: an lvalue has an identity you can refer to again (a named variable, *p, a[i]); a prvalue is a pure temporary (f() returning by value, x + 1); an xvalue is an object about to expire (std::move(x)). Rvalue references (T&&) bind to rvalues, so overloading on T&& lets a function know it may plunder its argument.

  • std::move doesn't move anything. It's a cast to T&&, a promise that you won't rely on the object's value afterwards. The move constructor does the stealing.
  • A moved-from object is in a "valid but unspecified" state: you may assign to it or destroy it, but not read its value.
  • Named rvalue references are lvalues. Inside void f(string&& s), s is an lvalue; pass it on with std::move(s).
  • Copy elision: since C++17, returning a prvalue (return T(...);) constructs directly in the caller, so there's no copy or move at all. Named return value optimisation (return local;) is permitted but not guaranteed, with an implicit move as a fallback. Don't write return std::move(local);: it disables NRVO.

The invariant and template

// Perfect forwarding: preserve the caller's value category through a wrapper
template <class... Args>
auto make_widget(Args&&... args) {                 // forwarding references (deduced T&&)
    return Widget(std::forward<Args>(args)...);   // lvalues stay lvalues, rvalues stay rvalues
}

// Sink parameters: take by value, then move (one copy for lvalues, zero for rvalues)
class Person {
    std::string name_;
public:
    explicit Person(std::string name) : name_(std::move(name)) {}
};

Why noexcept on moves matters: when std::vector grows, it must keep the strong exception guarantee. It moves the old elements only if the move constructor is noexcept (via std::move_if_noexcept); otherwise it copies them. A missing noexcept can turn every reallocation of a vector<BigThing> into deep copies.

const T&read-only, no copy needed

A thinking trace: why is this vector growth slow?

struct Order { std::string id; std::vector<double> fills;
               Order(const Order&) = default;
               Order(Order&& o) : id(std::move(o.id)), fills(std::move(o.fills)) {} };
std::vector<Order> book; for (...) book.push_back(make_order());
  1. Observe: profiling shows time in string and vector copy constructors during push_back.
  2. Which push_back overload? make_order() is a prvalue, so push_back(T&&) is chosen and the new element is move-constructed. That part is fine.
  3. Reallocation: when capacity runs out, existing elements are transferred. The user-declared move constructor isn't noexcept, so move_if_noexcept picks the copy constructor to preserve the strong guarantee. Each growth deep-copies every order.
  4. Fix: mark the move constructor noexcept (it only moves members that can't throw), or better, delete both user-declared constructors (rule of zero), and the implicit ones are noexcept automatically. Also book.reserve(n) if n is known.
  5. Verify: static_assert(std::is_nothrow_move_constructible_v<Order>);

The habit: when a C++ program does surprising work, trace which overload and which special member function each line actually invokes.

Traps and variations

  • Moving from a const object silently copies (std::move of a const T gives const T&&, which binds only to the copy constructor).
  • Use after move: reading a moved-from string is legal but unspecified. Clang-tidy's bugprone-use-after-move catches it.
  • emplace_back vs push_back: emplace constructs in place from constructor arguments. With an existing object they're equivalent. Emplace can call explicit constructors, so v.emplace_back(10) on a vector<vector<int>> makes 10 zeros, not {10}.
  • Self-move assignment must leave the object valid (std types guarantee only that).
  • Small string optimisation: short strings (around 15 chars in libstdc++) live inside the object, so moving them is a copy of bytes. Moving isn't always cheaper.
  • Forwarding references vs rvalue references: T&& is forwarding only when T is deduced in that very call. std::vector<T>&& is not a forwarding reference.
