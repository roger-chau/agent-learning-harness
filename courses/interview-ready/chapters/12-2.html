The signal

"Design an LLM serving system for 10,000 requests per minute with a 500 ms time-to-first-token SLO", "how would you schedule requests on GPUs?", "how do you autoscale?". It's system design (Part 11) where the bottleneck is GPU memory and the scheduler is the product.

The core idea: the scheduler is a bin-packer for KV memory

Static batching waits for a batch, runs it to completion, and wastes slots as short sequences finish early. Continuous (in-flight) batching admits new requests into the running batch at every decode step and evicts finished ones, keeping the GPU full. The constraint at each step is that the total KV memory of the running sequences must fit.

  • Paged KV cache: allocate KV in fixed-size blocks (like OS pages, Part 10), so there's no fragmentation from unknown output lengths, and blocks can be shared (prefix caching for common system prompts).
  • SLOs: TTFT (prefill latency plus queueing) and TPOT (decode step time). Large batches raise throughput but stretch TPOT; long prefills stall everyone's decode.
  • Chunked prefill splits long prompts into chunks interleaved with decode steps, bounding the decode stall. Disaggregated serving runs prefill and decode on different GPU pools, since they have different bottlenecks, and ships the KV cache between them.
  • Routing: send requests sharing a prefix to the same replica (cache hits), balance by queue depth and free KV memory, and keep separate pools per model and adapter.

The invariant and template: serving architecture

clients ─▶ API gateway (auth, rate limit, request size limits)
        ─▶ router (model, prefix affinity, load: queue depth + free KV blocks)
        ─▶ replica: scheduler loop every step:
              1. retire finished sequences, free their KV blocks
              2. admit waiting requests while KV blocks remain (priority / fairness)
              3. run one fused step: chunked prefill for new + one decode token for running
        ─▶ stream tokens back (SSE / gRPC streaming)
autoscaler: target = f(queue depth, TTFT p95, KV utilisation); scale replicas, not batch size

Invariant: Σ KV blocks of running sequences ≤ pool size, with headroom reserved so running sequences can grow. If exhausted, pre-empt (swap the KV to CPU memory or recompute it later) rather than OOM.

A thinking trace: meeting a TTFT SLO under load

  1. Load: 10,000 requests/min ≈ 170/s; prompts average 1,000 tokens, outputs 300; model 70B in BF16 over 8×H100 with tensor parallelism.
  2. Prefill demand: 170 × 1,000 × 2 × 70 × 10⁹ ≈ 2.4 × 10¹⁶ FLOP/s. One 8-GPU replica at ~40% MFU gives 8 × 0.4 × 989 × 10¹² ≈ 3.2 × 10¹⁵ FLOP/s, so about 7.5 replicas just for prefill.
  3. Decode demand: 170 × 300 = 51,000 tokens/s. Per replica, the weights are 140 GB, read at 8 × 3.35 TB/s ≈ 27 TB/s, so a step takes ~5 ms plus KV reads, ~10 ms in practice at a large batch. With a batch of 128 that's ~12,800 tokens/s per replica, so about 4 replicas.
  4. Interference: on shared replicas, long prefills stall decode steps and blow the TPOT. Use chunked prefill, or disaggregate, e.g. 8 prefill replicas and 4–5 decode replicas sized separately.
  5. Queueing: keep utilisation ≤ ~70% (queueing delay grows sharply near saturation), so ~12 prefill-side and ~6 decode-side replicas with autoscaling on TTFT p95.
  6. Cheaper levers first: prefix caching for shared system prompts (prefill work saved), FP8 (≈2× on both phases), a smaller model for easy requests (routing by difficulty).

The habit: size prefill by FLOPs and decode by bytes, separately, then add queueing headroom.

Traps and variations

  • Unknown output lengths make KV demand unpredictable: reserve headroom, or pre-empt.
  • Head-of-line blocking: one 100k-token prompt can stall a replica, so cap prompt sizes per tier or route long prompts to a dedicated pool.
  • Fairness: per-tenant token budgets; priority classes for interactive vs batch traffic.
  • Cold starts: loading 140 GB of weights takes minutes, so keep warm pools and load from local NVMe or peer GPUs.
  • Metrics: TTFT and TPOT percentiles, tokens/s per GPU, KV utilisation, pre-emption rate, prefix-cache hit rate.
