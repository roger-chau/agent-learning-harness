The signal

Reach for a hash map or set when the brute force searches: "is there an earlier element that…", "have I seen…", "how many times does…", "group the items that share…". The search is usually the inner loop of an O(n²) solution, and a hash table turns it into an O(1) expected lookup. You trade O(n) memory for a factor of n in time.

The core idea

Remember what you've seen, keyed by what you'll search for later. The skill is choosing the key:

  • The value itself: duplicates, membership.
  • The complement: two-sum stores x and looks up target − x.
  • A canonical form: anagrams share sorted letters (or letter counts); "same shape" problems share a normalised representation.
  • A running quantity: prefix sums keyed by value, to find earlier prefixes that differ by k (next chapter).

And the value stored: an index (to return positions), a count (frequencies), a list (groups), or the earliest/latest position (window problems).

The invariant and template

seen = {}                       # invariant: seen holds every element before i, keyed for lookup
for i, x in enumerate(nums):
    if key_we_need(x) in seen:  # query BEFORE inserting x, so x can't match itself
        ...answer...
    seen[key(x)] = i            # restore the invariant for i + 1

"Query before insert" is the line people get wrong: for two-sum with [3, 3] and target 6, inserting first would let 3 pair with itself only if you then check indices; querying first handles it naturally. When the problem needs all elements in the map first (e.g. longest consecutive sequence), build it in a separate pass.

A thinking trace: longest consecutive sequence

Problem: length of the longest run of consecutive integers in an unsorted array, in O(n).

  1. Examples: [100, 4, 200, 1, 3, 2] → 4. By hand, I'd look for 1, then 2, 3, 4… my brain is doing membership tests.
  2. Brute force: for each x, count x + 1, x + 2, … with a linear search each time: O(n³); with a set, O(n²) (each run walked from each of its elements).
  3. Bottleneck: a run of length L is walked L times, once from each member. The repeated work is walking from the middle of runs.
  4. Transformation: only start walking from the first element of a run, recognisable because x − 1 isn't in the set.
  5. Argument: every element is walked over at most once in total (as part of exactly one run's walk), plus one start check each: O(n) amortised. Invariant for the walk: y is in the set and so is every value from x to y.
  6. Tests: empty (0), duplicates [1, 2, 0, 1] (3), negatives, one long shuffled run.

The transferable move: if work is repeated, find a canonical place to do it once.

Traps and variations

  • Mutable keys: Python lists can't be keys; use tuples. In C++, unordered_map needs a hash for pairs (or encode the pair into one 64-bit integer).
  • Worst-case hashing: adversarial inputs can force collisions (a known issue on competitive judges); mention it, and sorting as the deterministic alternative.
  • Counting versus storing: if you only need frequencies, an array of 26 or 256 counters beats a hash map: smaller and cache-friendly.
  • Variations: two-sum on a sorted array (two pointers, O(1) space), k-sum (sort + recursion to two-sum), subarray problems (prefix sums + map).
