What you're actually being scored on

A coding interview isn't an exam with a hidden answer key. It's a 45-minute sample of how you'd work as a colleague: can you take a vague problem, make it precise, find a good solution, explain why it's right, and produce working code, while someone watches? Interviewers fill in a rubric afterwards, and at most large companies it has four or five rows, scored separately:

  • Problem solving: did you find an efficient approach, and how much help did you need?
  • Coding: is the code correct, clean and idiomatic in your language?
  • Communication: could the interviewer follow your reasoning the whole time?
  • Verification: did you test your code yourself, with chosen cases, and find your own bugs?
  • Complexity: could you state and justify time and space?

The consequence: a correct optimal solution written in silence can score worse than a slightly slower one explained clearly and tested carefully. Every row is trainable, and this course trains them separately.

The 45-minute script

Strong candidates follow roughly the same timeline, and saying where you are in it ("let me start with a brute force, then optimise") is itself good communication:

  1. 0–5 min, clarify. Restate the problem in your own words. Ask about input sizes, value ranges, duplicates, empty input, whether the input is sorted, and what to return when there's no answer.
  2. 5–8 min, examples. Work one small example by hand, plus one edge case. This catches misunderstandings while they're cheap.
  3. 8–12 min, brute force. State the obvious solution and its complexity, even if it's bad. It proves you understand the problem and gives you something to improve.
  4. 12–20 min, optimise. Find what the brute force wastes and remove it (Chapter 0.3's method). Agree the approach with the interviewer before coding.
  5. 20–35 min, code. Write clean code, narrating the non-obvious lines.
  6. 35–42 min, test. Trace your code on your example and an edge case, out loud, line by line. Fix bugs calmly.
  7. 42–45 min, wrap up. Complexity, trade-offs, and what you'd do with more time.

Different kinds of loop

  • Big tech (Google, Meta, Amazon, NVIDIA's software teams): 2–4 coding rounds of the kind above, one or two system design rounds for experienced candidates, and a behavioural round.
  • Online assessments (OAs): 2–4 problems in 60–90 minutes, graded by hidden tests, before any human sees you. Speed and correctness on edge cases dominate. This platform's Submit button works the same way.
  • GPU, performance and compiler teams add domain rounds: "optimise this kernel", "what does this code compile to", "design a memory allocator". Your GPU course is the preparation for those.
  • Quant trading and HFT firms add mental maths tests, probability and betting games, and (for developers) low-latency C++. Track C covers these.

How to practise

Volume matters, but only with the right feedback loop. For every problem in this course:

  1. Spend up to 20 minutes (30 for hard) before using a hint. Struggle is where the learning happens; reading solutions early teaches recognition, not generation.
  2. Say your approach out loud (or write it as comments) before coding: the interview tests that skill.
  3. After solving, read the worked solution anyway. Compare the reasoning, not just the code: what clue should have led you there faster?
  4. Write one line in your notes: "signal → technique". After a few dozen problems, these lines are the pattern library you'll draw on under pressure.

Reality

Interviews are noisy: a strong candidate fails some rounds through bad luck or a bad match with the interviewer. Plan for that statistically: apply widely, treat each loop as practice, and keep a log of what each round asked. The goal of preparation is to make your worst round good enough, which is why this course drills fundamentals until they're automatic rather than chasing ever-harder puzzles.
