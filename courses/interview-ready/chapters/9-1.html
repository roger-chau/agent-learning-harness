The signal

C++ rounds at trading firms, compiler teams and GPU/driver teams start from one question: who owns this object, and when does it die? Expect "what's wrong with this class?", "implement a smart pointer", "why does this crash only in release builds?", and "explain the rule of five". The skill is reading code and tracking every object's lifetime and owner without running it.

The core idea: every resource has exactly one owner, and the owner's destructor releases it

RAII (resource acquisition is initialisation) ties a resource (memory, file, lock, socket, GPU buffer) to an object's lifetime: acquire in the constructor, release in the destructor. Because destructors run on every exit path, including exceptions, early returns and break, cleanup can't be forgotten.

Storage durations decide when destructors run:

  • Automatic (locals): destroyed at the end of their scope, in reverse order of construction.
  • Dynamic (new): destroyed when something calls delete, which should always be an owning object (unique_ptr, vector), never you by hand.
  • Static: at program exit, in reverse order of initialisation. Order across translation units is unspecified (the "static initialisation order fiasco").
  • Temporaries: at the end of the full expression, unless bound to a const& or && local, which extends the lifetime.

The rule of zero / three / five: if your class only holds members that manage themselves (vector, string, unique_ptr), write none of the special members (rule of zero). If you must write a destructor to release something, you almost certainly need the copy constructor and copy assignment too (rule of three), and for efficiency the move constructor and move assignment (rule of five).

The invariant and template: a minimal unique_ptr

template <class T>
class UniquePtr {
    T* p_ = nullptr;                                   // invariant: p_ is null or owned by exactly this object
public:
    UniquePtr() = default;
    explicit UniquePtr(T* p) noexcept : p_(p) {}
    ~UniquePtr() { delete p_; }
    UniquePtr(const UniquePtr&) = delete;              // unique ownership: no copies
    UniquePtr& operator=(const UniquePtr&) = delete;
    UniquePtr(UniquePtr&& o) noexcept : p_(o.p_) { o.p_ = nullptr; }   // steal, leave source empty
    UniquePtr& operator=(UniquePtr&& o) noexcept {
        if (this != &o) { delete p_; p_ = o.p_; o.p_ = nullptr; }
        return *this;
    }
    T* get() const noexcept { return p_; }
    T& operator*() const { return *p_; }
    T* operator->() const noexcept { return p_; }
    T* release() noexcept { T* q = p_; p_ = nullptr; return q; }
    void reset(T* q = nullptr) noexcept { T* old = p_; p_ = q; delete old; }   // assign first: safe if delete re-enters
};

Interviewers look for: copying is deleted, the moved-from object is left null, self-move assignment is handled, moves are noexcept, and the constructor is explicit. The extension questions are custom deleters, arrays (T[] uses delete[]), and why make_unique is preferred (exception safety in multi-argument calls before C++17, and no naked new).

shared_ptr adds a control block holding atomic strong and weak counts. Copies increment the strong count (an atomic RMW, so not free); the last strong owner destroys the object, and the last weak owner frees the block. make_shared puts the object and the block in one allocation. weak_ptr breaks reference cycles.

A thinking trace: "what's wrong with this class?"

class Buffer {
    char* data; size_t n;
public:
    Buffer(size_t n) : data(new char[n]), n(n) {}
    ~Buffer() { delete data; }
};
void f() { Buffer a(10); Buffer b = a; }
  1. Who owns data? Buffer does: it allocates and frees it. So it's a resource-owning class, and the rule of three applies.
  2. Bug 1: delete on memory from new[] is undefined behaviour. It must be delete[].
  3. Bug 2: Buffer b = a uses the implicit copy constructor, which copies the pointer. Two owners means a double delete at the end of f(), and UB.
  4. Bug 3 (design): the constructor isn't explicit, so Buffer b = 10; compiles. And there's no move support, so returning a Buffer by value copies (or would, if copying worked).
  5. Fix, best answer: rule of zero. Use std::vector<char> data; or std::unique_ptr<char[]>; the compiler-generated members are then correct (vector deep-copies; unique_ptr makes the class move-only).
  6. Fix, if asked to keep the raw pointer: write a deep copy constructor, copy assignment via copy-and-swap (strong exception safety, self-assignment safe), noexcept move operations, and delete[].

The habit: for each member, ask "who frees this?", then check every special member function against that answer. Most C++ code-review questions are this check.

Traps and variations

  • Dangling references: returning a reference or pointer to a local; holding a string_view or span to a temporary; a lambda capturing a local by reference that outlives the scope.
  • Iterator and reference invalidation: push_back may reallocate a vector, invalidating every pointer, reference and iterator into it. Holding auto& x = v[0]; across a push_back is a classic bug.
  • Exceptions in destructors terminate if thrown during stack unwinding; destructors are implicitly noexcept.
  • Virtual destructor: deleting a derived object through a base pointer without a virtual destructor is UB.
  • Slicing: copying a Derived into a Base by value drops the derived part. Pass polymorphic objects by reference or pointer.
  • shared_ptr cycles leak (parent ↔ child). Make the back-pointer a weak_ptr.
  • Constructing two shared_ptrs from one raw pointer gives two control blocks and a double delete. Use make_shared or enable_shared_from_this.
