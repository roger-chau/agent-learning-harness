The signal

"Why does this work in debug but not in release?", "is this code correct?", "what's the complexity of this container operation?", "which container would you use?". Undefined behaviour (UB) questions are a favourite at compiler teams (optimisers exploit UB) and HFT firms (UB shows up as a rare production crash).

The core idea: the optimiser assumes UB never happens

UB isn't "the program crashes". It's "the standard places no requirements", and compilers optimise on the assumption that valid programs never execute UB. So a UB bug can make the compiler delete your checks, reorder your code, or turn a finite loop infinite.

UBWhat the optimiser may do
signed overflow (INT_MAX + 1)assume x + 1 > x; delete overflow checks written as if (x + 1 < x)
null dereferencedelete a later null check (\"it was dereferenced, so it's non-null\")
out-of-bounds accessassume indices are in range; vectorise or unroll past your intent
data race on non-atomicshoist loads out of loops (a spin-wait on a plain bool never ends)
strict aliasing violationassume an int* and a float* don't alias; reorder loads and stores
use after free / lifetime endanything
shift by ≥ width or a negative amountanything (x86 masks the count, other ISAs don't)
uninitialised readstreat the value as whatever is convenient

Tools: -fsanitize=address,undefined (ASan + UBSan) in tests; -fsanitize=thread for races; -Wall -Wextra; and std::bit_cast or memcpy for type punning.

Big-O hides constants that matter here: a linear scan of a 1,000-element vector often beats a std::map lookup, because the vector is contiguous and prefetched while each map node is a cache miss. Flat hash maps (open addressing: absl, boost::unordered_flat_map) are typically 2–3× faster than std::unordered_map.

A thinking trace: "this check never fires in release"

bool add_overflows(int a, int b) {
    int s = a + b;
    return (b > 0 && s < a) || (b < 0 && s > a);
}
  1. Symptom: add_overflows(INT_MAX, 1) returns true at -O0, but Clang at -O2 returns false. (GCC 13 at -O2 happened to keep the check when we tried it, which is the point: UB results differ between compilers, versions and surrounding code.)
  2. Find the UB: when the sum overflows, a + b is signed overflow, which is UB. So the compiler may assume a + b never overflows, which makes s < a with b > 0 impossible. Both branches fold to false.
  3. Fix: check before the operation (b > 0 ? a > INT_MAX - b : a < INT_MIN - b), or use __builtin_add_overflow(a, b, &s), or do the arithmetic in a wider or unsigned type where wrap-around is defined.
  4. Prevent: UBSan (-fsanitize=signed-integer-overflow) flags it in tests immediately.

The habit: when behaviour differs between optimisation levels, assume UB first, then find the operation whose precondition can be violated.

Traps and variations

  • Erasing while iterating: use it = v.erase(it), or erase-remove (std::erase_if in C++20).
  • map[key] inserts a default value when the key is missing. Use find or contains for lookups, especially on a const map (where [] doesn't compile).
  • vector<bool> is a bit-packed proxy, not a container of bools: no bool&, and not thread-safe per element.
  • Struct padding: order members from largest to smallest to shrink objects; sizeof includes padding; alignas(64) prevents false sharing (Part 10).
  • Unsigned underflow: for (size_t i = v.size() - 1; i >= 0; --i) never ends, and v.size() - 1 underflows when empty.
  • Strict aliasing: reading a float's bits through an int* is UB. Use std::bit_cast<uint32_t>(f).
  • Integer promotion: uint8_t a = 200, b = 100; auto c = a + b; gives an int 300, not a wrapped 44.
