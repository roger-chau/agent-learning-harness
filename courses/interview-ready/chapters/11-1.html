The signal

"Design X" with 45–60 minutes and a whiteboard. Interviewers grade the process more than the final diagram: do you pin down requirements, quantify the load, choose components for stated reasons, find the bottleneck, and discuss trade-offs and failure modes? For performance-engineering roles, expect the estimation and bottleneck parts to be weighted heavily.

The core idea: a fixed five-step method

  1. Requirements (5 min): functional (what operations), non-functional (latency target, availability, consistency, durability), scale (users, requests/s, data size, read:write ratio). Write them down; ask which matter most.
  2. Estimate (5 min): QPS (average and peak), storage growth per year, bandwidth, memory for the hot set. These numbers drive every later choice.
  3. API and data model (5–10 min): the endpoints and the core tables or records. Access patterns decide the database.
  4. High-level design (10–15 min): clients → load balancer → stateless services → cache → database / queue / object store. Walk one request end to end.
  5. Deep dive and bottlenecks (15–20 min): the hardest part (the hot key, the fan-out, the consistency requirement), scaling each tier, failure handling, monitoring. Offer two options and pick one with a reason.

Numbers to know: a day has ~86,400 s ≈ 10⁵ s, so 1M requests/day ≈ 12/s on average (peaks are often 2–10×). A modern server handles ~10⁴–10⁵ simple requests/s; a single SQL primary ~10⁴ writes/s; a Redis node ~10⁵ ops/s; datacentre round trip ~0.5 ms; reading 1 MB sequentially from memory ~50 µs, from SSD ~1 ms, over 1 Gbps ~10 ms.

The invariant and template: back-of-the-envelope estimation

QPS_avg   = daily_actions / 86,400            (≈ daily / 10⁵)
QPS_peak  = QPS_avg × peak_factor            (2–10)
storage   = new_items/day × bytes/item × 365 × years × replication (3)
bandwidth = QPS × response_bytes
cache     = hot fraction (often 20%) × daily read set     (the 80/20 rule)
servers   = QPS_peak / per_server_QPS × headroom (1.5–2)

Round aggressively (powers of 10 and 2), and say your assumptions out loud. An estimate that's within 2× and fast beats a precise one that eats ten minutes.

A thinking trace: sizing a URL shortener

  1. Requirements: shorten (write) and redirect (read); 100M new URLs/day; reads 10× writes; keep URLs 5 years; redirects should take < 20 ms at the server.
  2. QPS: writes 10⁸ / 10⁵ ≈ 1,000/s (peak ~5,000); reads ≈ 10,000/s (peak ~50,000).
  3. Storage: 10⁸ × 365 × 5 ≈ 1.8 × 10¹¹ URLs × ~500 bytes ≈ 90 TB (× 3 replicas). So it must be sharded.
  4. Key length: base62 with 7 characters gives 62⁷ ≈ 3.5 × 10¹², enough for 1.8 × 10¹¹ with room to spare.
  5. Key generation: a counter per shard (or a distributed ID service, Snowflake-style) encoded in base62, which avoids collision checks. Hashing the URL needs collision handling, but deduplicates.
  6. Reads: a cache (Redis) in front of a KV store sharded by key. The hot set is small, so most redirects are cache hits at ~1 ms.
  7. Bottleneck discussion: hot links (celebrity tweets) are handled by the cache plus CDN-level redirects. Analytics (click counts) are written asynchronously through a queue, never on the redirect path.

The habit: let the numbers choose the architecture. "90 TB" forces sharding; "50k reads/s with a small hot set" forces a cache; "analytics on every click" forces async.

Traps and variations

  • Jumping to a diagram before requirements. Spend the first five minutes asking questions.
  • Buzzword components without reasons ("add Kafka"). Every box needs a sentence on why it's there and what it costs.
  • Ignoring failure: what happens when a node, an availability zone, the cache or the queue dies? Mention replication, retries with backoff, and idempotency.
  • One giant design: scale the simple version first, and grow it only when the numbers demand.
  • Not driving: the interviewer expects you to lead and check in ("I'll go deeper on the fan-out unless you'd prefer the storage layer").
