The signal

"Implement a single-producer single-consumer ring buffer", "what is false sharing?", "what is the ABA problem?", "is a lock-free queue always faster?". These are core questions at HFT and low-latency firms, where a mutex's occasional sleep (a context switch of microseconds) breaks the latency budget.

The core idea: one writer per variable, and keep writers on separate cache lines

The fastest shared structure is one where each variable has exactly one writer. A single-producer single-consumer (SPSC) ring buffer is the archetype: only the producer writes tail, only the consumer writes head, and each reads the other's index with acquire semantics. There are no compare-and-swap loops and no locks, and each operation is a few nanoseconds.

False sharing: cores keep cache lines coherent (MESI). If the producer's tail and the consumer's head sit in the same 64-byte line, every write invalidates the other core's copy, and the line ping-pongs at ~50–100 ns per transfer even though the variables are independent. Fix it with alignas(64) (or std::hardware_destructive_interference_size) on each hot variable.

Multi-producer structures need compare-and-swap (CAS) loops: read, compute, and CAS the new value in, retrying on failure. They bring the ABA problem: a CAS succeeds because the value is the same pointer, though the node was freed and reallocated in between. Mitigations are tagged pointers (a version counter beside the pointer), hazard pointers, or epoch-based reclamation.

The invariant and template: SPSC ring buffer

template <class T, size_t N>                     // N a power of two
class SpscRing {
    static_assert((N & (N - 1)) == 0);
    alignas(64) std::atomic<size_t> head_{0};    // written only by the consumer
    alignas(64) std::atomic<size_t> tail_{0};    // written only by the producer
    alignas(64) T buf_[N];
public:
    bool push(const T& v) {                      // producer thread only
        size_t t = tail_.load(std::memory_order_relaxed);
        if (t - head_.load(std::memory_order_acquire) == N) return false;   // full
        buf_[t & (N - 1)] = v;
        tail_.store(t + 1, std::memory_order_release);   // publish the slot
        return true;
    }
    bool pop(T& out) {                           // consumer thread only
        size_t h = head_.load(std::memory_order_relaxed);
        if (h == tail_.load(std::memory_order_acquire)) return false;      // empty
        out = buf_[h & (N - 1)];
        head_.store(h + 1, std::memory_order_release);   // free the slot
        return true;
    }
};

Invariant: 0 ≤ tail − head ≤ N; slots in [head, tail) hold published values. Monotonic counters with a power-of-two mask avoid a separate full/empty flag. A known optimisation is for each side to cache the other's index and re-read the atomic only when the cached value says full or empty, which cuts cross-core traffic.

A thinking trace: "our lock-free queue is slower than the mutex one"

  1. Setup: 4 producers, 1 consumer; a CAS-based MPSC queue against a mutex-protected deque. Under load the lock-free one has worse throughput.
  2. Contention: every producer CASes the same tail pointer. Under contention most CASes fail and retry, and each attempt moves the cache line to that core: one line bouncing among 5 cores.
  3. Allocation: each push calls new for a node: a malloc, possibly contended, plus a cache miss when the consumer touches the node.
  4. Why the mutex wins here: it serialises producers cheaply when critical sections are tiny, and the deque allocates in chunks.
  5. Better design: one SPSC ring per producer (no shared writes at all), with the consumer polling them round-robin. Or batch: producers enqueue arrays of items.
  6. Also report the tail: lock-free mainly improves worst-case latency (no thread is ever blocked behind a descheduled lock holder), not average throughput. Measure p99/p99.9, not just the mean.

The habit: "lock-free" describes a progress guarantee, not speed. Reason about cache-line ownership transfers to predict the throughput.

Traps and variations

  • Lock-free ≠ wait-free: lock-free means some thread always makes progress; wait-free means every thread finishes in bounded steps.
  • Memory reclamation is the hard part of lock-free structures in C++. Without GC you need hazard pointers or epochs.
  • Busy-polling: spinning consumers burn a whole core; that's acceptable (and standard) in HFT with pinned, isolated cores, and wasteful elsewhere. Add a _mm_pause() in spin loops.
  • std::atomic<T>::is_lock_free: large T may silently use a lock.
  • Memory ordering bugs often don't show on x86; test on ARM, or reason formally.
  • Disruptor pattern (LMAX): a ring buffer with sequence barriers, consumers chained in a pipeline, and pre-allocated entries. Worth knowing by name.
