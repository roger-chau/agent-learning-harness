The signal

"Why is iterating a linked list slower than a vector of the same size?", "what happens on a page fault?", "why does this run 3× slower on the second socket?", "what are huge pages for?". Systems interviewers want a working model of the memory hierarchy, with numbers, that you can use to predict performance before you measure it. (The GPU course's Part 1 covers the hardware in depth; this chapter is the CPU-side interview version.)

The core idea: latency numbers and the unit of transfer

OperationRough latency
L1 hit~1 ns (4–5 cycles)
L2 hit~4 ns
L3 hit~10–20 ns
DRAM (local NUMA node)~80–100 ns
DRAM (remote socket)~130–200 ns
branch mispredict~5 ns (15–20 cycles)
mutex lock/unlock, uncontended~20 ns
system call~100 ns – 1 µs
context switch~1–5 µs
minor / major page fault~1 µs / ~ms (disk)
same-datacentre round trip~50–500 µs

Data moves in 64-byte cache lines. Sequential access lets the hardware prefetcher stream lines ahead of use; pointer chasing defeats it, since each load's address depends on the previous load. That's why a vector scan runs at memory bandwidth while a list traversal runs at memory latency, often a 10–50× difference.

Virtual memory: each process sees its own address space; the MMU translates virtual pages (4 KB) to physical frames through page tables, cached in the TLB. A TLB miss costs a page-table walk; a page that isn't mapped yet costs a page fault. 2 MB or 1 GB huge pages cover far more memory per TLB entry. NUMA: on multi-socket machines, memory attached to the other socket is slower. Pin threads and allocate memory on the same node ("first touch" places pages on the node of the thread that first writes them).

The invariant and template: estimate before you measure

time ≈ max( bytes_moved / bandwidth ,  dependent_misses × miss_latency ,  instructions / IPC / f )
# e.g. sum 10⁸ ints in a vector: 400 MB / ~20 GB/s ≈ 20 ms (bandwidth-bound)
#      walk 10⁸-node shuffled list: 10⁸ dependent misses × ~90 ns ≈ 9 s (latency-bound)

The three regimes: bandwidth-bound (streaming), latency-bound (dependent misses), compute-bound. Memory-level parallelism (several independent misses in flight) is how real code escapes the latency regime: walk several lists at once, or prefetch.

A thinking trace: "the hash map got slower as it grew"

  1. Observation: lookups take 20 ns at 10⁴ keys, 100 ns at 10⁷ keys, though the hash map is "O(1)".
  2. Working set: 10⁴ entries (~0.5 MB) fit in L2/L3; 10⁷ entries (~500 MB with node overhead) don't, so each lookup becomes 1–2 DRAM misses (bucket array + node).
  3. TLB: random access over 500 MB with 4 KB pages touches about 125,000 pages; the TLB covers only about 1,500 entries (~6 MB), so most lookups also take a page walk, which can miss in cache too.
  4. Fixes: an open-addressing (flat) table removes the node indirection (1 miss instead of 2); huge pages cut TLB misses; batching lookups and prefetching overlap misses; shrinking entries (32-bit keys, a separate value array) fits more per line.
  5. Verify: perf counters for LLC misses and dTLB misses before and after.

The habit: big-O tells you how the operation count grows; the memory hierarchy tells you what each operation costs. When performance falls off a cliff as data grows, look for a cache or TLB capacity boundary.

Traps and variations

  • False sharing (Chapter 10.3): independent variables on the same line written by different cores.
  • Struct of arrays vs array of structs: scanning one field of an AoS drags every other field through the cache.
  • fork() and copy-on-write: pages are shared until written; a write after fork triggers a fault and a copy.
  • mmap vs read: mmap avoids a copy but costs page faults and TLB pressure; read with a big buffer is often comparable.
  • Stack vs heap: both are just memory. The difference is the allocator's cost and lifetime management, not access speed.
  • Measure with: perf stat -e cache-misses,dTLB-load-misses, perf record, and numactl --hardware.
