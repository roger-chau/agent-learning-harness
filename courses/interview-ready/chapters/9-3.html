The signal

"Static vs dynamic polymorphism", "what does a virtual call cost?", "write a generic function constrained to numbers", "compute this at compile time", "what is CRTP / type erasure?". Templates matter in quant C++ (zero-cost abstractions on the hot path) and compilers and GPU work (heavily templated kernels like CUTLASS).

The core idea: decide at compile time what you can, and pay at run time only for what you must

Templates are code generators: each instantiation is a separate, fully typed function the optimiser can inline. Virtual functions decide at run time through a vtable: one indirect call per dispatch, and usually no inlining across it. The trade-off is flexibility vs speed and code size.

Constraining templates: C++20 concepts (template <std::integral T>) give readable errors and overload by property. The older tool is SFINAE (enable_if): a substitution failure removes an overload instead of erroring. constexpr / consteval run code in the compiler; if constexpr discards untaken branches per instantiation.

The invariant and template

// CRTP: static polymorphism, no vtable
template <class Derived>
struct Strategy {
    double on_tick(double px) { return static_cast<Derived*>(this)->signal(px); }  // resolved at compile time
};
struct MeanRevert : Strategy<MeanRevert> { double signal(double px) { return -px; } };

// Concepts + if constexpr
template <class T> concept Number = std::integral<T> || std::floating_point<T>;
template <Number T>
T safe_avg(T a, T b) {
    if constexpr (std::integral<T>) return a / 2 + b / 2 + (a % 2 + b % 2) / 2;   // no overflow
    else return (a + b) / 2;
}

constexpr int fib(int n) { return n < 2 ? n : fib(n - 1) + fib(n - 2); }
static_assert(fib(10) == 55);                         // evaluated by the compiler

A thinking trace: "how expensive is a virtual call?"

  1. Mechanics: load the vptr from the object, load the function pointer from the vtable, then make an indirect call. That's two dependent loads and an indirect branch.
  2. When it's cheap: the vtable is hot in L1 and the branch predictor learns the target. Then it's a few cycles, often indistinguishable from a direct call.
  3. When it hurts: (a) no inlining, so the compiler can't vectorise or constant-fold through the call, which is the big cost in tight loops; (b) mixed concrete types in one container make the indirect branch unpredictable (about 15–20 cycles per mispredict); (c) objects scattered through the heap, the usual companion of polymorphic containers, cost cache misses.
  4. Mitigations: mark classes final (enables devirtualisation); sort or partition objects by type and process each type in a batch; switch to CRTP or templates when the set of types is known at compile time; std::variant for a closed set.
  5. Measure rather than assert: a microbenchmark with representative type mixing, plus perf counters for branch misses.

The habit: answer cost questions with mechanism → best case → worst case → mitigation → measurement. The same structure works for exceptions, atomics, allocation and system calls.

Traps and variations

  • Templates must be visible where they're instantiated, so they go in headers (or use explicit instantiation).
  • Code bloat: every type combination is a new function. Factor type-independent code out of templates.
  • Two-phase lookup: inside a template deriving from a dependent base, call base members as this->f().
  • std::function may allocate (beyond its small buffer) and always costs an indirect call. On the hot path, take the callable as a template parameter.
  • constexpr isn't a guarantee of compile-time evaluation unless used in a constant expression; consteval forces it.
  • Virtual functions in constructors dispatch to the class being constructed, not the most-derived one.
