The signal

Trading-firm systems rounds: "design an order book", "how would you measure tick-to-trade latency?", "where do the microseconds go between the NIC and your strategy?", "why is p99.9 more important than the mean?". The judged problem below is the order book itself, the data structure at the centre of every exchange and every market-making system.

The core idea: the latency budget is spent in the tails

A tick-to-trade path (packet arrives, is parsed, the book updates, the strategy decides, an order is encoded and sent) can run in a few microseconds in software (sub-microsecond on FPGAs). Every component must be predictable, because one slow event (a page fault, a cache miss storm, a context switch, an allocation, a log write) dominates the tail.

  • Kernel bypass: the kernel network stack costs ~5–10 µs; user-space NIC access (DPDK, Solarflare/OpenOnload, ef_vi) cuts it to ~1 µs.
  • Core isolation and pinning: isolcpus, IRQ affinity, one busy-polling thread per pinned core, no context switches.
  • No allocation on the hot path: pre-allocate pools at start-up; no new, no std::string growth, no exceptions thrown.
  • Warm caches: keep the hot path warm by exercising it with dummy work when idle; avoid cold code layout.
  • Log asynchronously: write binary records into an SPSC ring; another core formats and writes them.

Order book design: per side, price levels (price → FIFO queue of orders) plus an order-id → order map for O(1) cancel and modify. If prices lie in a known band of ticks, an array indexed by price tick beats a tree: O(1) level access and contiguous memory, with a tracked best-price index.

The invariant and template: measuring latency honestly

  • Timestamps: rdtsc (invariant TSC) for nanosecond-scale in-process timing; NIC hardware timestamps for wire-to-wire.
  • Report percentiles: p50, p99, p99.9, max, and a histogram (HdrHistogram). The mean hides exactly the events that lose money.
  • Coordinated omission: a load generator that waits for each response before sending the next under-samples the slow periods. Send on a fixed schedule and measure from the intended send time.
  • Isolate variables: pin the benchmark, disable frequency scaling (or record it), warm up, and repeat with confidence intervals.

Invariant of the book: the best bid < the best ask after every operation (no crossed book); each level's queue is in arrival order; every live order appears exactly once in both the level queue and the id map.

A thinking trace: designing the matching engine

  1. Clarify the rules: price-time priority, trades at the resting price, partial fills, cancels by id, one instrument. Ask about order types (market, IOC, iceberg) and leave them as extensions.
  2. Operations and frequencies: in real markets, adds and cancels vastly outnumber trades (cancel-to-trade ratios of 10–100×), so cancel must be cheap.
  3. Structure v1 (interview-sized): two heaps keyed by (price, sequence), with lazy cancels: mark the order dead and skip it when it surfaces. O(log n) everything, simple, and correct. This is the judged problem below.
  4. Structure v2 (production): a price-level map/array + an intrusive doubly-linked FIFO per level + id → node map: O(1) cancel, O(1) best price with a cached index, no dead entries accumulating.
  5. Edge cases: an incoming order sweeping several levels; cancel of an unknown or already-filled id; zero-quantity remainders; equal prices arriving in sequence.
  6. Testing: a reference implementation (simple, slow) against the optimised one on random order flow, exactly how this course's judge validated the two reference solutions.

Traps and variations

  • Floating-point prices: use integer ticks. 0.1 + 0.2 ≠ 0.3 breaks price equality.
  • Self-trade prevention, market orders, IOC/FOK, and modify (which loses time priority if the quantity increases) are standard follow-ups.
  • Market data feeds: incremental updates with sequence numbers, so detect gaps and recover from a snapshot.
  • Throughput vs latency: batching improves the first and hurts the second; trading systems usually optimise the tail latency of each event.
  • Clock sync: cross-machine latency needs PTP-synchronised clocks; NTP is too coarse for microseconds.
