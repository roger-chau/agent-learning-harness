The signal

The question asks for all solutions (all subsets, permutations, combinations, partitions, board placements), or for one solution of a constraint puzzle (sudoku, N-queens, word search) where no polynomial algorithm is expected. Output size is often exponential, so the goal isn't polynomial time. It's generating each answer once, and abandoning dead branches early.

The core idea: choose, explore, un-choose

Backtracking is DFS over a tree of partial solutions. Each level makes one decision; each leaf is a complete candidate. Three questions design it:

  1. What is one decision? Include element i or not (subsets); which element goes next (permutations); which column for row r's queen (N-queens). The right granularity can remove whole dimensions.
  2. How do I avoid generating duplicates? A start index for combinations (non-decreasing order); sort and skip equal siblings; use equal values in left-to-right order for permutations of multisets.
  3. How do I prune? Feasibility checks in O(1) (sets or bitmasks for columns and diagonals), bounds ("the remainder is negative, stop"; "the sorted remaining candidates are too large, break"), and necessary conditions checked up front (letter counts in word search).

The invariant and template

def backtrack(state):
    if is_complete(state):
        output.append(snapshot(state)); return
    for choice in choices(state):          # ordered so duplicates are skippable
        if not feasible(state, choice): continue   # prune
        apply(state, choice)               # choose
        backtrack(state)                   # explore
        undo(state, choice)                # un-choose: restore EXACTLY

The invariant: on return, the state is exactly as it was on entry. Most backtracking bugs break it: forgetting to undo, undoing the wrong thing, or appending a reference to a mutable list (out.append(cur) instead of cur[:]).

Count the cost: subsets 2ⁿ · n, permutations n! · n, combinations C(n, k) · k. Saying these numbers is how you show the brute force is the intended solution.

A thinking trace: combination sum II

  1. Decision: which candidate to add next. Combinations ignore order, so impose one: only choose indices at or after the last one (a start index).
  2. Duplicates in the input ([1, 1, 2] with target 3) would produce [1, 2] twice, once for each 1. They come from choosing equal values as siblings at the same depth. Sort, then skip cands[i] when i > start and cands[i] == cands[i − 1]. Choosing the second 1 after the first (deeper) is still allowed, so [1, 1, x] is generated once.
  3. Pruning: sorted ascending, if cands[i] > remaining then every later candidate is too, so break, not continue.
  4. Snapshot: append a copy of the path.
  5. Test: all equal values, a target smaller than the minimum, and a target that is exactly one element.

The habit: distinguish "the same value at the same depth" (a duplicate) from "the same value deeper" (a legitimate repeat). Draw the recursion tree for [1, 1, 2] once and you'll never get it wrong again.

Traps and variations

  • Mutable snapshots: out.append(cur[:]).
  • Restore the grid after marking a cell in word search, including on success paths if you continue searching.
  • Exponential worst cases on purpose: adversarial inputs (a grid of 'A's searching for "AAAA…B") need pruning by counts or reversal.
  • Subsets: the include/exclude recursion, or iterate masks 0 … 2ⁿ − 1 (bitmask enumeration).
  • Sudoku: choose the empty cell with the fewest candidates first (most-constrained variable). It's dramatically faster.
  • Generate parentheses: prune with counts (open ≤ n, close ≤ open). The number of results is the Catalan number C(2n, n)/(n + 1).
  • When to switch to DP: if you only need the count or the best, and states repeat, memoise. Counting N-queens can't be memoised easily; counting combinations to a target can (that's coin change).
