The signal

Quant developer (and HFT software engineer) loops combine Track A coding, Part 9–10 C++ and systems depth, and domain problems: parse a feed, maintain a book, compute signals on a stream, all fast and correct. This Part turns those pieces into the tasks you'll actually be given, and connects them to your GPU and performance background.

The core idea: correctness first, then the hot path, then the tail

  1. Correct on edge cases: empty books, crossed or locked markets, out-of-order or duplicate messages, sequence gaps, price precision.
  2. Make the hot path cheap: no allocation (pools, fixed arrays), contiguous data (struct of arrays, price-indexed arrays), branch-light code, no virtual calls or exceptions, no locks (SPSC rings).
  3. Control the tail: pin threads, pre-fault memory, warm caches, async logging; measure p99/p99.9 honestly (Part 10.4).

Your GPU-performance background transfers directly: the memory hierarchy, roofline-style reasoning (is this bandwidth- or latency-bound?), measuring before optimising, and reading compiler output. Say so in interviews, with numbers from your labs.

The invariant and template: a feed-handler skeleton

recv packet (kernel bypass) → check sequence number (gap? → request snapshot / recover)
  → decode fixed-layout binary message (no parsing allocations; memcpy into a POD struct)
  → apply to the book (price-indexed levels; O(1) best-price tracking)
  → publish top-of-book / signals to strategy (SPSC ring, cache-line aligned)
  → strategy decides → order encoder → send
Logging: binary records into a ring; a non-critical thread formats them.

Invariants: book state equals the exchange's after applying every message in sequence; the hot thread never blocks; every message is processed exactly once (dedupe by sequence number).

A thinking trace: "our book-update path has a 40 µs p99.9 but a 2 µs median"

  1. Tail ≫ median means rare slow events, not uniform slowness. List the candidates: allocation, page faults, cache-cold paths, context switches, logging, rehashing.
  2. Measure: timestamp each stage with rdtsc; histogram per stage; correlate slow events with perf counters (page faults, context switches) and with message types.
  3. Finding (typical): an unordered_map of orders rehashes as it grows, a multi-microsecond pause that happens rarely. Also, the first message after a quiet period runs cache-cold.
  4. Fixes: reserve the map at start-up (or use a pre-sized open-addressing table or an array indexed by order id); keep the path warm with periodic dummy work; pre-fault and lock memory (mlockall).
  5. Verify: the p99.9 drops to about 4 µs; record the fix and add a regression benchmark to CI.

The habit: a tail is a list of rare events; find them by measuring per stage, then remove each one structurally.

Traps and variations

  • Floating-point prices: use integer ticks. Floating point is for signals, not book keys.
  • Endianness and alignment in binary protocols: decode explicitly; use memcpy for unaligned fields (avoid UB from casting).
  • Clocks: monotonic clocks for intervals; PTP-synchronised clocks for cross-machine timestamps.
  • Testing: replay recorded market data through the system deterministically; fuzz against a simple reference implementation (as the judges here do).
