The problem with "practise a lot"

Solving hundreds of problems makes you good at problems you've seen. Interviews ask ones you haven't. What transfers is a method: a sequence of moves you can run on any problem, that reliably produces a decent solution and often the optimal one. This chapter gives you the method this course uses everywhere. Every worked solution in the course is written as a trace of it, so you see it applied hundreds of times.

The six moves

  1. Restate and clarify. Inputs, outputs, sizes, edge cases. Write the signature.
  2. Examples by hand. One normal, one edge. Solve them manually and watch what your brain does: the manual procedure is often the algorithm.
  3. Brute force with its cost. The most direct correct solution, and its complexity.
  4. Find the bottleneck. What does the brute force do repeatedly or wastefully? Ask: what work is repeated, what's recomputed from scratch, what's searched for again and again, what's impossible and needn't be checked?
  5. Apply a transformation that removes that bottleneck (the table below).
  6. Argue correctness and test. State the invariant your loop maintains, then trace an example and an edge case through your code.

Two meta-transformations sit above the table: sort first (creating order that two pointers, binary search and greedy can exploit), and change the question (count the complement, reverse time, think about where each element contributes instead of what each answer contains).

Invariants: how to be right the first time

Most bugs in interview code are off-by-one errors and wrong loop updates. Both disappear if you can state, for every loop, what is true at the start of each iteration. For two-sum with a hash map: "seen holds every value before index i, mapped to its index". For a sliding window: "s[left..i) has no repeated character". Then each line of the loop body has one job: restore the invariant after the window moves. Saying the invariant out loud also scores communication points, and it's the proof of correctness the interviewer wants.

Testing like an engineer

Don't "run the example and see". Choose tests that attack your code: empty input, one element, all equal, already sorted, reverse sorted, negative numbers, the answer at the first or last position, no valid answer, duplicates at the boundary. Then trace the code on the smallest interesting one, line by line, with the variable values written down. Interviewers notice when you find your own bug; it's one of the strongest positive signals there is.
