The signal

"The k largest / smallest / most frequent / closest", "the k-th something", "merge k sorted things", "repeatedly take the best remaining option". A heap gives the extreme element in O(1) and updates in O(log n). It sits between "sort everything" (O(n log n), more than you need) and "scan for the max each time" (O(n) per query).

The core idea: the heap holds what you might evict

To keep the k largest items, use a min-heap of size k. That's backwards to most people at first. The heap's top is the weakest of your current top k: the one a new arrival must beat, and the one you throw away when it does. Once the stream ends, the top is the k-th largest.

For merging, the heap holds a frontier: the next unconsumed element from each source. Popping the minimum and pushing its successor keeps the frontier exact. That one idea gives merging k lists, the k-th smallest in a sorted matrix, the k smallest pair sums, and Dijkstra (whose frontier is the tentative distances).

The invariant and template

import heapq
# top-k largest. Invariant: h holds the k largest seen so far; h[0] is the k-th largest.
h = []
for x in stream:
    if len(h) < k: heapq.heappush(h, x)
    elif x > h[0]: heapq.heapreplace(h, x)

# k-way merge. Invariant: h holds the smallest unconsumed element of every source.
h = [(src[0], i, 0) for i, src in enumerate(sources) if src]
heapq.heapify(h)
while h:
    v, i, j = heapq.heappop(h)
    emit(v)
    if j + 1 < len(sources[i]):
        heapq.heappush(h, (sources[i][j + 1], i, j + 1))

Python's heapq is a min-heap: negate the keys for a max-heap, and use tuples for (key, tie-breaker, payload) so you never compare payloads. In C++, priority_queue is a max-heap by default. Write priority_queue<T, vector<T>, greater<T>> for a min-heap. Getting the direction backwards in C++ is the most common heap bug.

A thinking trace: k-th smallest in a sorted matrix

  1. Clarify: rows and columns are sorted, so the matrix is not globally sorted ([[1, 5], [2, 6]]). Duplicates count.
  2. Brute force: flatten and sort, O(n² log n). That ignores all the structure.
  3. View 1, a merge: the rows are n sorted lists. A k-way merge pops the k-th element after k − 1 pops: O(k log n). That's good when k is small.
  4. View 2, binary search on the answer: "how many elements are ≤ x?" is monotone in x and can be counted in O(n) with a staircase walk from the bottom-left (move up while the value is too big, add the column index + 1). Search for the smallest x with count ≥ k: O(n log(max − min)). That's good when k is near n².
  5. Choose by the constraints, and say why. Offering both views shows range: one uses the rows, the other uses the order of values.

The habit: one structure, two orderings. Many "k-th" problems can be attacked by position (merge or select) or by value (binary search plus counting). Try both.

Traps and variations

  • Ties and determinism: ask how ties break, and encode the rule in the key tuple.
  • Floating distances: compare squared integer distances; never take square roots.
  • heapify is O(n), not O(n log n). If you have all the data, heapify and pop k times for O(n + k log n).
  • Quickselect is O(n) on average, but O(n²) with bad pivots: randomise. C++ nth_element is introselect, worst-case safe. Mention it when n is large and k is about n/2.
  • Bucket sort by count: frequencies are at most n, so top-k-frequent is O(n) with buckets.
  • Find the k pairs with the smallest sums: a frontier heap over the implicit matrix a[i] + b[j], pushing (i, j + 1), plus (i + 1, j) only when j = 0, so no pair is pushed twice.
