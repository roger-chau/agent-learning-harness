The signal

"Implement a thread-safe queue", "what's a deadlock and how do you prevent it?", "explain memory_order_acquire", "why is double-checked locking broken without atomics?", "what's the difference between a mutex and a spinlock?". Concurrency questions probe whether your mental model of what other threads can observe is correct, because concurrency bugs don't show up in testing.

The core idea: happens-before

Without synchronisation, the compiler and the CPU may reorder memory operations, and other cores may see your writes late or in a different order. A data race (two threads access the same non-atomic location, at least one writes, no synchronisation) is undefined behaviour in C++. Synchronisation establishes happens-before edges: everything before a release (unlock, a store with memory_order_release) is visible to a thread after the matching acquire (lock, a load with acquire that reads the stored value).

Deadlock needs four conditions at once: mutual exclusion, hold-and-wait, no pre-emption, and circular wait. Break circular wait by always acquiring locks in a global order, or use std::scoped_lock(a, b), which locks several mutexes deadlock-free.

The invariant and template: a bounded blocking queue

template <class T>
class BoundedQueue {
    std::mutex m_;
    std::condition_variable not_full_, not_empty_;
    std::deque<T> q_;                       // invariant (under m_): q_.size() <= cap_
    const size_t cap_;
public:
    explicit BoundedQueue(size_t cap) : cap_(cap) {}
    void push(T v) {
        std::unique_lock lk(m_);
        not_full_.wait(lk, [&] { return q_.size() < cap_; });   // loop inside: handles spurious wakeups
        q_.push_back(std::move(v));
        lk.unlock();
        not_empty_.notify_one();
    }
    T pop() {
        std::unique_lock lk(m_);
        not_empty_.wait(lk, [&] { return !q_.empty(); });
        T v = std::move(q_.front()); q_.pop_front();
        lk.unlock();
        not_full_.notify_one();
        return v;
    }
};

Publishing with acquire/release:

Data payload; std::atomic<bool> ready{false};
// producer                                // consumer
payload = make();                          while (!ready.load(std::memory_order_acquire)) {}
ready.store(true, std::memory_order_release);   use(payload);   // guaranteed to see make()'s writes

A thinking trace: lazy initialisation

Widget* instance = nullptr; std::mutex m;
Widget* get() {
    if (!instance) {                       // check 1 (unlocked)
        std::lock_guard g(m);
        if (!instance) instance = new Widget;   // check 2 (locked)
    }
    return instance;
}
  1. Intent: double-checked locking, so the lock is taken only during initialisation.
  2. Find the race: check 1 reads instance without synchronisation while another thread writes it, which is a data race and UB.
  3. Concrete failure: instance = new Widget may become visible before the Widget's fields are written (the store of the pointer is reordered with the constructor's stores). A thread passing check 1 then uses a half-built object.
  4. Fix 1: make instance a std::atomic<Widget*>; load with acquire, store with release.
  5. Fix 2 (best): a function-local static, static Widget w; return &w;, whose initialisation C++11 guarantees is thread-safe; or std::call_once.

The habit: for every shared variable, name the synchronisation that orders each access to it. If you can't name one, it's a data race.

Traps and variations

  • volatile is not a synchronisation primitive in C++ (it's for memory-mapped I/O). Use atomics.
  • Lost wakeup: checking the predicate without holding the mutex, or notifying before the state change, can sleep forever.
  • Priority inversion: a low-priority thread holds a lock that a high-priority thread needs while a medium one runs. Real-time systems use priority inheritance.
  • Read-mostly data: shared_mutex, RCU, or seqlocks (readers retry if a sequence number changed) avoid writer starvation and reader cache-line bouncing.
  • Thread pools: creating a thread costs ~10–50 µs, so reuse threads for short tasks.
  • x86 is strongly ordered (TSO: only store→load reordering), so acquire/release loads and stores compile to plain moves. ARM isn't, so code that "works on x86" can fail on ARM servers and phones.
