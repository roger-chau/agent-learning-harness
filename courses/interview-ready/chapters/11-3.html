The signal

Three classics that show up again and again and exercise different building blocks: a rate limiter (algorithms + distributed state), a news feed (fan-out and caching), and a distributed key-value store (partitioning, replication, consistency). Each one teaches a decision you'll reuse in other designs.

The core idea: three decisions

Rate limiter, which algorithm? A fixed window (simple; allows 2× bursts at window edges), a sliding log (exact; memory per request), a sliding-window counter (approximates with two windows), or a token bucket (allows controlled bursts, two numbers per client, the usual default). Where it lives: at the API gateway. Distributed state: Redis with an atomic Lua script, or local buckets with a share of the global limit.

News feed, push or pull? Fan-out on write (push each post into followers' timelines) makes reads cheap but celebrity posts expensive (10⁷ writes per post). Fan-out on read (merge followees' posts at read time) makes writes cheap and reads expensive. The real answer is hybrid: push for normal users, pull for celebrities, merged at read time.

KV store, which consistency? A Dynamo-style design: consistent hashing for partitioning; N replicas; tunable quorums R and W; hinted handoff and read repair for temporary failures; Merkle trees for anti-entropy; vector clocks or last-writer-wins for conflicts.

The invariant and template: quorum arithmetic

N replicas, write waits for W acks, read waits for R responses
R + W > N   → every read set overlaps every write set → reads see the latest acknowledged write
W = N, R = 1 → fast reads, writes fail if any replica is down
W = 1, R = N → fast writes, slow reads
typical: N = 3, W = 2, R = 2 (tolerates one node down for both reads and writes)

Overlap is necessary but not sufficient for linearisability (concurrent writes, sloppy quorums during failures). Say so if pushed.

A thinking trace: the news feed

  1. Requirements: 300M daily users, each loads the feed about 10 times a day, each posts about once a day; the average user has 200 followers, and some have 10⁷. A feed should load in < 200 ms.
  2. Load: reads 3 × 10⁹ / 10⁵ ≈ 30,000/s; posts 3,000/s; fan-out writes if pushing everything ≈ 3,000 × 200 = 600,000 timeline inserts/s on average, with celebrity spikes of 10⁷ per post.
  3. Choose hybrid: push posts into followers' timeline caches (Redis lists of post ids, capped at ~800) for users with < ~10⁴ followers; celebrities' posts are pulled at read time and merged.
  4. Read path: fetch the cached timeline ids, plus recent posts of followed celebrities; merge by time (or rank); hydrate post content from a post cache; paginate with a cursor, not an offset.
  5. Write path: store the post, then enqueue a fan-out job; workers push ids to follower timelines asynchronously, so posting returns immediately.
  6. Failure and scale: fan-out workers scale horizontally; inactive users' timelines aren't maintained (rebuild on login); the ranking model is a separate service.

Traps and variations

  • Pagination with offsets breaks when new items arrive; use cursors (the last seen id or time).
  • Distributed rate limiting with a central Redis adds a network hop to every request; local token buckets with periodic sync trade accuracy for latency.
  • Conflict resolution: last-writer-wins silently loses writes. Shopping carts famously use merge (union) semantics.
  • Other classics worth one practice run each: chat (WebSockets, per-conversation ordering), typeahead (a trie of top-k per prefix, precomputed), web crawler (politeness, dedupe with Bloom filters), distributed job scheduler, metrics pipeline (Part 12 overlaps).
