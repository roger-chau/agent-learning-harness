The signal

"Why is LLM generation slow?", "how many concurrent users fit on one GPU?", "what does the KV cache cost?", "why does batching help decode but not prefill?". ML-infra and GPU-performance interviews (inference teams at labs and clouds, and the GPU roles you're aiming for) expect you to derive these from first principles: parameters, bytes, FLOPs, bandwidth. It's the roofline model from the GPU course, Part 2, applied to transformers.

The core idea: prefill is compute-bound, decode is memory-bound

A decoder-only transformer with P parameters does about 2P FLOPs per token in the forward pass (one multiply-add per weight).

  • Prefill processes the whole prompt in parallel: big matrix multiplies, high arithmetic intensity, so it's compute-bound. Time ≈ 2P × prompt_tokens / (achieved FLOP/s). This sets the time to first token (TTFT).
  • Decode generates one token at a time per sequence. Each step must read every weight (and that sequence's KV cache) from HBM to do only 2P FLOPs per sequence, so at batch size 1 it's bandwidth-bound: time per token ≈ (weight bytes + KV bytes) / HBM bandwidth. This sets the time per output token (TPOT).
  • Batching decode reuses each weight read across B sequences: B× the FLOPs for nearly the same bytes, so throughput grows almost linearly in B until either compute saturates or the KV caches fill memory.

KV cache: each layer stores the keys and values of every previous token, 2 × layers × kv_heads × head_dim × bytes per token. Grouped-query attention (fewer KV heads) shrinks it; for long contexts it can exceed the weights' size. It's usually what limits batch size.

The invariant and template: the inference envelope

weights_bytes   = P × bytes_per_param                 (2 for BF16, 1 for INT8/FP8, 0.5 for INT4)
kv_per_token    = 2 × L × n_kv_heads × d_head × bytes
decode_step     ≈ max( (weights_bytes + B × ctx × kv_per_token) / HBM_bw ,  2P × B / FLOPs )
prefill_time    ≈ 2P × prompt_tokens / (MFU × peak_FLOPs)
max_batch       ≈ (HBM − weights − activations) / (ctx × kv_per_token)
crossover batch ≈ peak_FLOPs / HBM_bw / 2 × bytes_per_param     (above it, decode turns compute-bound)

For an H100 (989 TFLOP/s dense BF16, 3.35 TB/s): FLOPs/byte ≈ 295, so BF16 decode stays memory-bound until the batch is in the hundreds.

A thinking trace: how many users can one H100 serve with a 7B model?

  1. Weights: 7 × 10⁹ × 2 bytes = 14 GB in BF16.
  2. Batch-1 decode: 14 GB / 3.35 TB/s ≈ 4.2 ms per token, about 240 tokens/s for one user. Fast for one user, a waste of the GPU's compute.
  3. KV cache (Llama-2-7B shape: 32 layers, 32 KV heads, d_head 128, BF16): 2 × 32 × 32 × 128 × 2 = 512 KB per token. At a 4,096-token context that's 2 GB per sequence.
  4. Memory budget: 80 GB − 14 GB weights − ~6 GB activations and overhead ≈ 60 GB for KV, so about 30 sequences at full context.
  5. Decode step at B = 30: it reads 14 GB of weights + 30 × (avg ctx 2,048 × 0.5 MB ≈ 1 GB) = 44 GB → ~13 ms per step, giving 30 tokens per 13 ms ≈ 2,300 tokens/s total, about 75 tokens/s per user.
  6. Levers: GQA (Llama-3-8B has 8 KV heads, 4× less KV), FP8/INT4 weights and KV, paged KV allocation (no fragmentation), shorter contexts or eviction. Each one raises the batch, and with it the throughput.

The habit: bytes moved per token over bandwidth, and KV bytes per sequence into memory. Those two numbers answer most inference questions.

Traps and variations

  • "More FLOPs = faster decode" is wrong at small batch: decode speed tracks HBM bandwidth.
  • Quantisation helps decode roughly in proportion to the bytes saved (INT4 weights ≈ 4× fewer bytes), if the kernels are efficient.
  • Speculative decoding: a small draft model proposes k tokens and the big model verifies them in one batched forward pass. It converts memory-bound sequential steps into one compute-heavier step, and helps when the acceptance rate is high.
  • Attention cost grows with context: decode reads the whole KV cache every step (O(context) bytes per token); prefill attention is O(n²) compute, hence FlashAttention-style tiling (the GPU course, Part 7).
  • Tensor parallelism splits weights over GPUs to cut per-GPU bytes (faster decode) at the cost of an all-reduce per layer.
