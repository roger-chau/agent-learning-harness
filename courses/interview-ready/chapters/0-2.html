Complexity as a design tool

Big-O isn't something you compute after writing code; it's a tool for choosing what to write. Before designing anything, read the constraints and ask: what complexity does this input size allow? A modern machine does roughly 10⁸ simple operations per second in compiled code (10⁷ in Python). Judges give about a second.

This table is one of the strongest hints an interviewer gives you without saying anything: "n up to 10⁵" means "don't even propose O(n²)".

Counting, honestly

  • Loops multiply, sequences add. A loop of n containing a loop of m is O(nm); two loops one after the other are O(n + m).
  • Hidden costs. String concatenation in a loop (O(n²) in total), slicing (O(k) per slice), x in list (O(n)), sorting inside a loop, copying a dict. These are the most common way to write O(n²) while thinking O(n).
  • Hash maps are O(1) expected per operation, O(n) worst case under adversarial collisions. Say "expected".
  • Recursion: work per call × number of calls. Use the recurrence: T(n) = 2T(n/2) + O(n) is O(n log n); T(n) = 2T(n − 1) + O(1) is O(2ⁿ).
  • Space includes the recursion stack (depth × frame), and say whether you count the output.

Amortised analysis: the most useful proof you'll give

Many optimal solutions have a nested loop that is nevertheless O(n) in total. The argument is always the same: count how many times each element can be touched over the whole run, not how many times the inner loop can run per iteration.

  • A sliding window's left pointer only moves forward: it moves at most n times in total, however the inner while looks.
  • A monotonic stack pushes and pops each element at most once: O(n) total pops.
  • A dynamic array that doubles when full copies 1 + 2 + 4 + … + n < 2n elements over n appends: O(1) amortised per append.

In an interview, saying "the inner loop looks quadratic, but each index enters and leaves the window once, so it's O(n) amortised" is exactly the sentence that earns the complexity row.

Lower bounds: when to stop optimising

Know when you're done. Any solution must at least read its input (Ω(n)) and write its output. Comparison sorting is Ω(n log n). If you've reached the lower bound, say so: "this is O(n), and we have to look at every element, so it's optimal". If the interviewer pushes further, they usually want a constant-factor or space improvement, or they're probing whether you know you're done.

Reality

Constants matter more than textbooks admit. O(n log n) with a sort of 10⁶ integers takes milliseconds; O(n) with a hash map of 10⁶ entries may take longer because of cache misses (the GPU course's memory wall, on a CPU). In performance-team interviews, being able to say why the asymptotically better solution might be slower in practice is a strong signal.
